Context Managers: what does with really do?

First, look at this code and guess where the trap is:

Python· Run it on your own computer
f = open('/tmp/two_drops_of_water.txt', 'w')
f.write("Two Drops' diary: I clocked in three minutes late today.")
f.close()

"What's wrong with that? Open the file, write to it, close it – done in one go." That's what you might say if you like to think things through.

But what if the f.write line raises an exception?

Then close never runs, and the file handle is just left hanging there. Once or twice is fine. But if it's a web service running all day, and a few dozen out of thousands of requests fail to write a file, the operating system's file handles slowly get used up. Eventually you get a "Too many open files" error that seems to have nothing to do with anything. Bugs like this are really painful to track down.

So what do you do? The old way is of course try/finally:

Python· Run it on your own computer
f = open('/tmp/two_drops_of_water.txt', 'w')
try:
    f.write("Two Drops' diary: I clocked in three minutes late today.")
finally:
    f.close()

This is safe, but ugly. A simple file write gets wrapped in try/finally, adding an extra level of indentation. If you then need to open a second file, and a third, the indentation keeps stacking up, and you soon end up with "pyramid code".

You've surely seen Python's other way of writing this:

Python· Run it on your own computer
with open('/tmp/two_drops_of_water.txt', 'w') as f:
    f.write("Two Drops' diary: I clocked in three minutes late today.")

Just two lines – no try, no finally, no manual close. And yet, whether or not write raises an exception, the file is always closed properly.

So what exactly is this with? How can it do something so magical? In this chapter, we'll explain it inside and out.

The essence of with: the context manager protocol

What comes after with isn't a "file", a "connection" or a "lock" – it's a kind of thing. Python calls it a context manager.

What kind of object counts as a context manager? Any object with these two methods:

  • __enter__(self): called when you enter the with block. Its return value is assigned to the variable after as
  • __exit__(self, exc_type, exc_val, tb): called when you leave the with block – whether you leave normally or because of an exception

This is the context manager protocol. Those are all its rules – just these two, no third one.

Let's use our old friend, clocking in, to write the simplest context manager by hand, so you get a feel for it:

Python· Runs on this page
class Punch:
    def __enter__(self):
        print('Two Drops enters the clock-in area')
        return self

    def __exit__(self, exc_type, exc_val, tb):
        print('Two Drops leaves the clock-in area')


with Punch() as p:
    print('Two Drops is goofing off at the desk')

Output:

Text
Two Drops enters the clock-in area
Two Drops is goofing off at the desk
Two Drops leaves the clock-in area

What do you see? The line with Punch() as p does three things:

  1. Creates a Punch() instance
  2. Calls that instance's __enter__() method
  3. Assigns the return value of __enter__() to p

Only then does it run the code inside the with block. When the with block ends (normally or because of an exception), it calls __exit__().

Does this look familiar? Yes – it's really hiding this chunk of boilerplate:

Python· Read with the text above
p_obj = Punch()
p = p_obj.__enter__()
try:
    print('Two Drops is goofing off at the desk')
finally:
    p_obj.__exit__(None, None, None)

behind the with syntactic sugar. That's how one line of with does the job of six.

    Let's look back at open
    

    Now that we understand the protocol, let's look at open() again:
    

    Python· Run it on your own computer
    with open('/tmp/two_drops_of_water.txt', 'w') as f:
    f.write('One line of text.')
    

    The file object returned by open() implements __enter__ and __exit__ itself. Its __enter__ just does return self, so f gets the file object itself. Its __exit__ calls close(). Simple – but it covers every exception path.
    

    You can check it yourself:
    

    Python· Run it on your own computer
    f = open('/tmp/two_drops_of_water.txt', 'w')
print(hasattr(f, '__enter__'))
print(hasattr(f, '__exit__'))
f.close()
    

    Output:
    

    Text
    True
True
    

    It's not just files. In the standard library, socket, threading.Lock, sqlite3.Connection, and in third-party libraries, requests.Session and so on – almost every resource that needs paired operations implements the context manager protocol. Open/close, acquire/release, connect/disconnect – whenever you "borrow something and must give it back", let with look after it.
    

    Let's look at one more example to see how a context manager hides the details of "paired operations". threading.Lock should be familiar – you can hardly do multithreaded programming without it:
    

    Python· Run it on your own computer
    import threading


lock = threading.Lock()

# Without with, you have to acquire and release by hand
lock.acquire()
try:
    print('Two Drops is hard at work inside the critical section')
finally:
    lock.release()

# With with, Python arranges acquire and release for us
with lock:
    print('Two Drops enters the critical section again')
    

    Output:
    

    Text
    Two Drops is hard at work inside the critical section
Two Drops enters the critical section again
    

    Note that with lock: has no as .... That's because the lock's __enter__ returns the lock itself, which isn't useful in most cases – what we care about is the state "it's locked", not the return value. So as can be left out. This is the usual way to write most locks, semaphores, events and similar context managers.
    

    Teaching 04 / 19· read
    

    A slightly more useful example: a clock-in context
    

    Printing a few lines is a bit thin. Let's make Punch do something real – record when an employee enters and leaves, and write it to a "log":
    

    Python· Runs on this page
    import time


class PunchLog:
    def __init__(self, name):
        self.name = name
        self.records = []

    def __enter__(self):
        self.start = time.time()
        self.records.append(f'{self.name} arrives at the desk')
        return self

    def __exit__(self, exc_type, exc_val, tb):
        cost = time.time() - self.start
        self.records.append(f'{self.name} leaves the desk after {cost:.4f} seconds')


log = PunchLog('Two Drops')
with log:
    time.sleep(0.05)
    print('Goofing off...')

for line in log.records:
    print(line)
    

    The output is roughly:
    

    Text
    Goofing off...
Two Drops arrives at the desk
Two Drops leaves the desk after 0.0507 seconds
    

    This time it wouldn't even matter if __enter__ didn't return self, because we wrote with log: – no as to receive a return value, and the variable log is the context manager itself. But if you change it to with log as l:, l would be None if __enter__ returned nothing, because __enter__ returns None by default. This is the trap beginners fall into most: "Why is my as x None?" Nine times out of ten, __enter__ forgot to return.

      Managing several contexts at once
      

      In real projects, you often need to open two or even three files at once – read one, write one, and write an error log. Early Python could only do this:
      

      Python· Run it on your own computer
      with open('/tmp/in.txt', 'w') as fin:
    pass

with open('/tmp/in.txt') as fin:
    with open('/tmp/out.txt', 'w') as fout:
        fout.write(fin.read())
      

      Two levels of indentation. Add an err.log, and it's three.
      

      Later, Python allowed several contexts in one with, separated by commas:
      

      Python· Run it on your own computer
      with open('/tmp/in.txt') as fin, open('/tmp/out.txt', 'w') as fout:
    fout.write(fin.read())
      

      Much neater than nesting. But a new problem appears – with many contexts, the line gets really long, and you can't break it.
      

      Python 3.10 added new syntax, PEP 617 "parenthesised context managers", which lets you wrap several contexts in brackets:
      

      Python· Run it on your own computer
      with (
    open('/tmp/in.txt') as fin,
    open('/tmp/out.txt', 'w') as fout,
):
    fout.write(fin.read())
      

      Note three things:
      

        

      1. Each line inside the brackets can end with a comma, including the last one – PEP 617 allows a trailing comma
        2. 

      2. This syntax only exists in Python 3.10+
        3. 

      3. For code style, this is the recommended way to manage three or more contexts at once
        4. 

      

      If you're still on 3.9 or older, either use the one-line comma version, or ExitStack, which we'll cover later.
      

      One more detail: several context managers __enter__ in order from left to right, and __exit__ in order from right to left. This is a really important guarantee – for example, code that "takes a lock, then opens a file" will always "close the file, then release the lock" when it exits. Let's test it with a small demo:
      

      Python· Runs on this page
      from contextlib import contextmanager


@contextmanager
def stage(name):
    print(f'{name} __enter__')
    try:
        yield name
    finally:
        print(f'{name} __exit__')


with stage('A') as a, stage('B') as b, stage('C') as c:
    print(f'Inside the with block: {a} {b} {c}')
      

      Output:
      

      Text
      A __enter__
B __enter__
C __enter__
Inside the with block: A B C
C __exit__
B __exit__
A __exit__
      

      See? C was the last to enter and the first to exit. It works exactly like the function call stack and nested try/finally.

      The three parameters of __exit__: handling exceptions
      

      We said __exit__'s signature is __exit__(self, exc_type, exc_val, tb), but haven't explained what these three parameters are for.
      

      Normally, if nothing in the with block raises an exception, all three are None. If there's an exception, they are:
      

        

      • exc_type: the type of the exception (e.g. ZeroDivisionError)
        • 

      • exc_val: the exception instance
        • 

      • tb: the traceback object
        • 

      

      Even more important is the return value of __exit__:
      

        

      • Return True (or anything "truthy"): the exception is swallowed and doesn't go any further
        • 

      • Return False, None, or no return at all: the exception keeps going outwards
        • 

      

      Let's write a context manager that swallows ZeroDivisionError:
      

      Python· Runs on this page
      class IgnoreZeroDivision:
    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc_val, tb):
        if exc_type is ZeroDivisionError:
            print(f'Swallowed a division-by-zero exception: {exc_val}')
            return True
        return False


with IgnoreZeroDivision():
    x = 1 / 0
    print('This will not print, because the line above raised an exception')

print('But this will print, because __exit__ swallowed the exception')
      

      Output:
      

      Text
      Swallowed a division-by-zero exception: division by zero
But this will print, because __exit__ swallowed the exception
      

      If the with block raises anything other than ZeroDivisionError – say, ValueError – __exit__ returns False, and the exception bubbles out as normal.
      

      I must stress this: swallowing exceptions is a very powerful ability, so please use it carefully. Generally, a context manager's job is to "clean up the resource no matter what", not to "pretend the exception never happened". Blindly writing return True can hide real bugs. Very few context managers in the standard library swallow exceptions – the most common one is contextlib.suppress, which we'll see later.
      

      Another common question: "Can I swap the exception for a different one in __exit__?" Yes, but with care. Raising a new exception directly in __exit__ replaces the exception currently being passed along, and the original becomes the new one's __context__. Here's an example to make it clear:
      

      Python· Runs on this page
      class TranslateException:
    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc_val, tb):
        if exc_type is not None:
            raise RuntimeError(f'I translated {exc_type.__name__} into RuntimeError') from exc_val


try:
    with TranslateException():
        1 / 0
except RuntimeError as e:
    print(f'What we got outside: {e}')
    print(f'The cause: {e.__cause__}')
      

      Output:
      

      Text
      What we got outside: I translated ZeroDivisionError into RuntimeError
The cause: division by zero
      

      This "translate the exception" pattern is really useful when writing libraries. For example, a database driver can translate all sorts of low-level network errors into one DatabaseError, so the outer code doesn't need to care whether a socket disconnected, the SSL handshake failed, or the protocol couldn't be read. We covered raise X from Y in the exceptions chapter – this is just a quick review.

      contextlib: the standard library's good friend
      

      Writing a whole class with two dunder methods just to manage a few lines of code – isn't that a bit heavy?
      

      The standard library has a module called contextlib with lots of tools to make this easier. The most important is the @contextmanager decorator.
      

      Remember generators? @contextmanager turns a generator function into a context manager. The rules are very simple:
      

        

      • Code before yield = __enter__
        • 

      • The value that's yielded = the return value of __enter__
        • 

      • Code after yield = __exit__
        • 

      

      Let's rewrite PunchLog from above with @contextmanager and compare:
      

      Python· Runs on this page
      import time
from contextlib import contextmanager


@contextmanager
def punch_log(name):
    records = []
    start = time.time()
    records.append(f'{name} arrives at the desk')
    try:
        yield records
    finally:
        cost = time.time() - start
        records.append(f'{name} leaves the desk after {cost:.4f} seconds')


with punch_log('Two Drops') as records:
    time.sleep(0.05)
    print('Still goofing off...')

for line in records:
    print(line)
      

      Output:
      

      Text
      Still goofing off...
Two Drops arrives at the desk
Two Drops leaves the desk after 0.0506 seconds
      

      Much cleaner, right? The class turned into a function, and the two dunder methods turned into one yield.
      

      Notice the try/finally inside. Why do we need it?
      

      Because the with block might raise an exception, and that exception "drills" back into the generator function at the yield line. Without try/finally, the exception would skip right past the clean-up code, and the resource would leak. Only try/finally guarantees "whether or not yield raises an exception, the clean-up code in finally always runs".
      

      This is the most important rule when writing context managers with @contextmanager: put the clean-up code inside finally. The most common beginner bug is leaving out try/finally, so resources aren't released when there's an exception.

        @contextmanager + handling exceptions
        

        What if I want to swallow an exception? How do I write that with @contextmanager?
        

        Easy – wrap yield in try/except:
        

        Python· Runs on this page
        from contextlib import contextmanager


@contextmanager
def ignore_zero_division():
    try:
        yield
    except ZeroDivisionError as e:
        print(f'Swallowed with @contextmanager: {e}')


with ignore_zero_division():
    x = 1 / 0
    print('This line will not run')

print('But this line will')
        

        Output:
        

        Text
        Swallowed with @contextmanager: division by zero
But this line will
        

        After except catches the exception, the function returns normally – that's the same as __exit__ returning True. If the exception isn't caught and the generator raises it again unchanged, that's the same as __exit__ letting the exception carry on outwards. @contextmanager connects both paths for you, so you just write normal Python exception handling.

        Some regulars in contextlib
        

        contextlib doesn't just have @contextmanager. It also has a few ready-to-use tools that you'll find you can't do without once you've used them:
        

        closing: wrap an object that doesn't support with
        

        Not every object that needs closing implements the context manager protocol. Typical examples are objects returned by urllib.request.urlopen in some old versions, and some custom resource objects. closing adds this layer for us:
        

        Python· Runs on this page
        from contextlib import closing


class Connection:
    def __init__(self, name):
        self.name = name

    def close(self):
        print(f'{self.name} closed')


with closing(Connection('Database connection')) as conn:
    print(f'Using {conn.name}')
        

        Output:
        

        Text
        Using Database connection
Database connection closed
        

        closing(obj) acts as a context manager: its __enter__ returns obj, and its __exit__ calls obj.close(). Simple and direct.
        

        Teaching 10 / 19· read
        

        suppress: ignore exceptions neatly
        

        Python· Run it on your own computer
        from contextlib import suppress


with suppress(FileNotFoundError):
    open('/tmp/this_file_definitely_does_not_exist_12345.txt').read()

print('Even if the file does not exist, I can carry on')
        

        Output:
        

        Text
        Even if the file does not exist, I can carry on
        

        suppress is the general standard-library version of IgnoreZeroDivision above. It takes any number of exception types – if one matches, it's swallowed; if not, it's raised as normal.
        

        suppress is shorter than try: ... except SomeError: pass, and it shows the intention "I really mean to ignore this exception" more clearly. But again, use it carefully – don't use it to hide real bugs.
        

        redirect_stdout / redirect_stderr: temporarily redirect standard output
        

        Sometimes we want to capture the print output of some code into a string, or write it to a file, without changing its source code:
        

        Python· Runs on this page
        import io
from contextlib import redirect_stdout


buf = io.StringIO()
with redirect_stdout(buf):
    print('This will not appear in the terminal')
    print('Instead it gets captured in buf')

captured = buf.getvalue()
print('I captured:')
print(captured)
        

        Output:
        

        Text
        I captured:
This will not appear in the terminal
Instead it gets captured in buf
        

        These two tools are really handy for test code, or for redirecting a third-party library's output to your own logger.
        

        nullcontext: a placeholder context that does nothing
        

        Think about this: sometimes your function needs to run inside a lock, and sometimes it doesn't. How can you write that neatly?
        

        Python· Run it on your own computer
        from contextlib import nullcontext
import threading


def do_stuff(lock=None):
    cm = lock if lock is not None else nullcontext()
    with cm:
        print('Doing stuff')


lock = threading.Lock()
do_stuff(lock)
do_stuff()
        

        Output:
        

        Text
        Doing stuff
Doing stuff
        

        nullcontext()'s __enter__ and __exit__ do nothing at all – it exists purely so the with line can be written the same way every time. No more long, messy branches like if lock: with lock: ... else: ....
        

        nullcontext can also carry a value and pretend it's what __enter__ returned. This is really handy when "sometimes you already have an open object, and sometimes you need to open a new one":
        

        Python· Run it on your own computer
        from contextlib import nullcontext


def read_text(source):
    cm = nullcontext(source) if hasattr(source, 'read') else open(source)
    with cm as f:
        return f.read()


import io
text1 = read_text(io.StringIO('I am an object that is already open'))
print(text1)

with open('/tmp/two_drops_e.txt', 'w') as f:
    f.write('I am content written on disk')

text2 = read_text('/tmp/two_drops_e.txt')
print(text2)
        

        Output:
        

        Text
        I am an object that is already open
I am content written on disk
        

        One function that can take either a string path or a file object that's already open – written in one smooth go. This little "accept two kinds of input" trick is used all the time in real projects.

          In practice: temporarily changing environment variables
          

          Here's a very common need: test how some code behaves when a certain environment variable is set, without messing up the current process's environment.
          

          How would you write it?
          

          Python· Run it on your own computer
          import os
from contextlib import contextmanager


@contextmanager
def set_env(**kwargs):
    old = {}
    for k, v in kwargs.items():
        old[k] = os.environ.get(k)
        os.environ[k] = v
    try:
        yield
    finally:
        for k, v in old.items():
            if v is None:
                os.environ.pop(k, None)
            else:
                os.environ[k] = v


os.environ.pop('TWO_DROPS_OF_WATER', None)
print('Before:', os.environ.get('TWO_DROPS_OF_WATER'))

with set_env(TWO_DROPS_OF_WATER='hello'):
    print('Inside with:', os.environ.get('TWO_DROPS_OF_WATER'))

print('After:', os.environ.get('TWO_DROPS_OF_WATER'))
          

          Output:
          

          Text
          Before: None
Inside with: hello
After: None
          

          Look carefully: before entering with, note down the original values of the environment variables we'll change. Inside the with block, change them to the new values. When leaving – normally or not – put the original values back. This is the most classic use of a context manager: "change it temporarily, and restore it when you leave".
          

          You can use the same pattern for "temporarily switch the working directory", "temporarily change sys.path", "temporarily raise the log level" and so on. Once you've got the hang of it, it feels very natural to write.
          

          Teaching 12 / 19· read
          

          Temporarily switching the working directory
          

          Here's one more demo while we're at it:
          

          Python· Run it on your own computer
          import os
from contextlib import contextmanager


@contextmanager
def chdir(path):
    old = os.getcwd()
    os.chdir(path)
    try:
        yield
    finally:
        os.chdir(old)


before = os.getcwd()
with chdir('/tmp'):
    print('Inside with:', os.getcwd())

print('Back where we started after leaving:', os.getcwd() == before)
          

          Output (your paths may differ):
          

          Text
          Inside with: /tmp
Back where we started after leaving: True
          

          One more note: Python 3.11 added contextlib.chdir to the standard library. It does the same thing as the one we wrote, so you can just from contextlib import chdir. If you're on 3.11+, no need to reinvent the wheel.

          ExitStack: a variable number of contexts
          

          So far, we've assumed "I have N contexts, and I know N when I write the code". But sometimes N is only known at runtime – for example, "open a list of files the user gave me, and close them all when I'm done".
          

          You can't write it in one with line, because you don't know how many names there will be. You can't use nested withs either, because you don't know how many levels to nest. That's when ExitStack comes in.
          

          Python· Run it on your own computer
          from contextlib import ExitStack


def make_files(paths):
    with ExitStack() as stack:
        files = [stack.enter_context(open(p)) for p in paths]
        total = sum(len(f.read()) for f in files)
        print(f'Read {len(files)} files, {total} bytes in total')


with open('/tmp/two_drops_a.txt', 'w') as f:
    f.write('a' * 100)
with open('/tmp/two_drops_b.txt', 'w') as f:
    f.write('bb' * 50)
with open('/tmp/two_drops_c.txt', 'w') as f:
    f.write('ccc' * 30)

make_files(['/tmp/two_drops_a.txt', '/tmp/two_drops_b.txt', '/tmp/two_drops_c.txt'])
          

          Output:
          

          Text
          Read 3 files, 290 bytes in total
          

          stack.enter_context(cm) "pushes" a context manager onto the stack – the same as putting it in the outermost with. When with ExitStack() exits, every context on the stack is exited one by one in "last in, first out" order – exactly the same as normal nested withs.
          

          ExitStack also has a really handy method called callback, which registers an ordinary clean-up function – it doesn't need to be a context manager:
          

          Python· Runs on this page
          from contextlib import ExitStack


def cleanup(name):
    print(f'Cleaning up {name}')


with ExitStack() as stack:
    stack.callback(cleanup, 'A')
    stack.callback(cleanup, 'B')
    stack.callback(cleanup, 'C')
    print('Inside the with block')
          

          Output:
          

          Text
          Inside the with block
Cleaning up C
Cleaning up B
Cleaning up A
          

          The clean-up order is C → B → A – backwards. That matches the natural feeling of "opened first, closed last".
          

          ExitStack has some more advanced uses too, like pop_all, which moves the stack into another ExitStack to make "transaction-style clean-up". But that's an advanced topic – look it up in the docs when you actually need it.
          

          Here's a really practical pattern: open a variable number of files, and if one of them fails partway, close all the ones already opened. ExitStack does this for us automatically:
          

          Python· Run it on your own computer
          from contextlib import ExitStack


def open_safely(paths):
    with ExitStack() as stack:
        files = []
        for p in paths:
            files.append(stack.enter_context(open(p)))
        return [f.name for f in files]


# Prepare three files that really exist
for name in ['/tmp/two_drops_x.txt', '/tmp/two_drops_y.txt', '/tmp/two_drops_z.txt']:
    with open(name, 'w') as f:
        f.write('hi')

names = open_safely(['/tmp/two_drops_x.txt', '/tmp/two_drops_y.txt', '/tmp/two_drops_z.txt'])
print(f'Safely handled {len(names)} files')

try:
    open_safely(['/tmp/two_drops_x.txt', '/tmp/this_does_not_exist_99999.txt'])
except FileNotFoundError as e:
    print(f'The second file failed, but the first one was closed automatically: {e.filename}')
          

          Output:
          

          Text
          Safely handled 3 files
The second file failed, but the first one was closed automatically: /tmp/this_does_not_exist_99999.txt
          

          This is where ExitStack is worth the most in real projects: "open in bulk, and roll everything back together if anything fails". Writing that by hand with try/finally would be very wordy, and it would be easy to miss an exception path.
          

          Teaching 14 / 19· read
          

          async with: with in the async world
          

          Finally, a quick word about the async version. Python 3.5 added the async/await syntax, and from 3.7 it gradually became mainstream. Inside an async def function, if you want to use a context manager, you write async with:
          

          Python· Read with the text above
          # This is just an illustration; it needs to run inside an async function
# async with httpx.AsyncClient() as client:
#     resp = await client.get('https://example.com')
          

          The matching protocol methods are __aenter__ and __aexit__, and contextlib also has an @asynccontextmanager decorator. We'll go deeper in the async/await chapter. For now, just know it exists, so you're not confused when you see async with in async code.
          

          Teaching 15 / 19· read
          

          Mini project: writing a timer context
          

          Let's tie together what we've learned in this chapter with a little tool: record the time when entering with, and print "this code took X milliseconds" when leaving.
          

          First, the class version:
          

          Python· Runs on this page
          import time


class Timer:
    def __init__(self, name='Unnamed block'):
        self.name = name

    def __enter__(self):
        self.start = time.perf_counter()
        return self

    def __exit__(self, exc_type, exc_val, tb):
        cost_ms = (time.perf_counter() - self.start) * 1000
        print(f'{self.name} took {cost_ms:.2f} ms')


with Timer("Two Drops' nap time"):
    time.sleep(0.05)
    s = sum(range(10000))
          

          The output is roughly:
          

          Text
          Two Drops' nap time took 50.46 ms
          

          Now rewrite it with @contextmanager and compare:
          

          Python· Runs on this page
          import time
from contextlib import contextmanager


@contextmanager
def timer(name='Unnamed block'):
    start = time.perf_counter()
    try:
        yield
    finally:
        cost_ms = (time.perf_counter() - start) * 1000
        print(f'{name} took {cost_ms:.2f} ms')


with timer('Clocking in'):
    time.sleep(0.03)
    sum(range(5000))
          

          The output is roughly:
          

          Text
          Clocking in took 30.21 ms
          

          Which version would you pick? I personally prefer the @contextmanager version – it's more compact. But when a context manager needs to keep complicated state, be reused, or be inherited from, the class version fits better. Both have the same abilities – choose based on the situation.
          

          One more bonus: what if you want Timer to work both as a context manager and as a decorator? These two needs often come together. contextlib already thought of this – the base class ContextDecorator does it in one line:
          

          Python· Runs on this page
          import time
from contextlib import ContextDecorator


class Timer(ContextDecorator):
    def __init__(self, name='Unnamed block'):
        self.name = name

    def __enter__(self):
        self.start = time.perf_counter()
        return self

    def __exit__(self, exc_type, exc_val, tb):
        cost_ms = (time.perf_counter() - self.start) * 1000
        print(f'{self.name} took {cost_ms:.2f} ms')


@Timer("Two Drops' function")
def work():
    time.sleep(0.02)


work()
          

          The output is roughly:
          

          Text
          Two Drops' function took 20.34 ms
          

          And functions written with @contextmanager can be used as decorators too, with no extra work:
          

          Python· Runs on this page
          import time
from contextlib import contextmanager


@contextmanager
def timer(name='Unnamed block'):
    start = time.perf_counter()
    try:
        yield
    finally:
        cost_ms = (time.perf_counter() - start) * 1000
        print(f'{name} took {cost_ms:.2f} ms')


@timer('Clock-in function')
def punch():
    time.sleep(0.01)


punch()
          

          The output is roughly:
          

          Text
          Clock-in function took 10.32 ms
          

          Notice that @contextmanager comes with ContextDecorator's abilities built in? So one function being both a decorator and a context manager feels perfectly natural. That's why lots of logging, performance-monitoring and tracing libraries like writing their core APIs with @contextmanager: one implementation, two ways to use it.
          

          Teaching 16 / 19· read
          

          Common anti-patterns
          

          Finally, a few words about the traps beginners fall into most:
          

          Anti-pattern 1: using a with variable outside the with
          

          Python· Run it on your own computer
          with open('/tmp/two_drops_d.txt', 'w') as f:
    f.write('hi')

print(f.closed)
          

          Output:
          

          Text
          True
          

          The variable f still exists after with exits, but the file object it points to has been closed. This isn't an error, but it's very misleading – many beginners think f becomes None or gives a NameError after with, but it doesn't. You can still get the variable, but it's "dead". That's a design choice in Python's context managers.
          

          Remember: after a with block exits, the variable after as still exists in the current scope, but its resource has been released. Touching it will probably cause an error.
          

          Anti-pattern 2: forgetting try/finally
          

          If you leave out try/finally when writing @contextmanager, it looks fine on the normal path, but as soon as there's an exception, the resource leaks:
          

          Python· Runs on this page
          from contextlib import contextmanager


@contextmanager
def bad():
    print('Opening the resource')
    yield
    print('Closing the resource')


try:
    with bad():
        raise ValueError('Raising an exception on purpose')
except ValueError:
    print('The outer code caught the exception')
          

          Output:
          

          Text
          Opening the resource
The outer code caught the exception
          

          "Closing the resource" was never printed, because the exception skipped all the code after yield. That's why we stressed it earlier: clean-up logic must go in finally.
          

          Anti-pattern 3: yielding more than once in a @contextmanager function
          

          Python· Runs on this page
          from contextlib import contextmanager


@contextmanager
def double_yield():
    print('Getting ready')
    yield 1
    yield 2
    print('Done')


try:
    with double_yield() as v:
        print(f'Got {v}')
except RuntimeError as e:
    print(f'Error: {e}')
          

          Output:
          

          Text
          Getting ready
Got 1
Error: generator didn't stop
          

          A generator decorated with @contextmanager can only yield once. Before the yield is __enter__; after the yield is __exit__. If it yields twice, Python notices at the second yield that "this generator didn't end straight after the yield as expected", and raises a RuntimeError. This is an easy bug for beginners to write, because normal generator functions are allowed to yield many times – but inside @contextmanager, only once.
          

          Anti-pattern 4: abusing return True to swallow exceptions
          

          Python· Runs on this page
          class SwallowEverything:
    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc_val, tb):
        return True


with SwallowEverything():
    1 / 0
    raise RuntimeError('what?')

print('Somehow I am still running')
          

          Output:
          

          Text
          Somehow I am still running
          

          A "swallow everything" context manager like this is a huge anti-pattern. It eats real bugs too, letting the program keep running in a broken state, and making debugging impossible. return True should be a very narrow, very deliberate "I mean to ignore exactly this one exception" action – not a lazy way to "make the world a bit quieter".
          

          Teaching 17 / 19· read
          

          A combined example: a reusable "Brother Shui clock-in auditor"
          

          To tie everything together, let's finish with a slightly more complicated example. The task: every time an employee arrives at their desk, record the start time; when they leave, record the end time; if the code raises an exception in between, record the exception type too. Finally, add a summary report.
          

          Python· Runs on this page
          import time
from contextlib import contextmanager


class Auditor:
    def __init__(self):
        self.events = []

    @contextmanager
    def shift(self, name):
        start = time.perf_counter()
        self.events.append({'name': name, 'phase': 'enter'})
        try:
            yield
        except Exception as e:
            self.events.append({
                'name': name,
                'phase': 'error',
                'exception': type(e).__name__,
            })
            raise
        finally:
            cost_ms = (time.perf_counter() - start) * 1000
            self.events.append({
                'name': name,
                'phase': 'leave',
                'cost_ms': round(cost_ms, 2),
            })

    def report(self):
        print(f'Recorded {len(self.events)} events in total:')
        for e in self.events:
            print(f'  - {e}')


auditor = Auditor()

with auditor.shift('Two Drops'):
    time.sleep(0.01)

try:
    with auditor.shift('Student A'):
        raise ValueError('The code blew up')
except ValueError:
    pass

with auditor.shift('Student B'):
    time.sleep(0.005)

auditor.report()
          

          The output is roughly:
          

          Text
          Recorded 7 events in total:
  - {'name': 'Two Drops', 'phase': 'enter'}
  - {'name': 'Two Drops', 'phase': 'leave', 'cost_ms': 10.42}
  - {'name': 'Student A', 'phase': 'enter'}
  - {'name': 'Student A', 'phase': 'error', 'exception': 'ValueError'}
  - {'name': 'Student A', 'phase': 'leave', 'cost_ms': 0.16}
  - {'name': 'Student B', 'phase': 'enter'}
  - {'name': 'Student B', 'phase': 'leave', 'cost_ms': 5.21}
          

          This code gets several important things right. Check them one by one:
          

            

          1. @contextmanager decorates a method of a class – that's completely allowed, and the method's self is still available inside the generator
            2. 

          2. It has the full try/except/finally trio: the exception path goes through except, and every path goes through finally
            3. 

          3. except Exception as e: ...; raise: record it first, then re-raise it unchanged – no swallowing
            4. 

          4. The report shows the full life cycle of an error event: enter → error → leave
            5. 

          

          This is how context managers are typically used in real projects – one object and a few lines of code wrap up "timing, recording exceptions and cleaning up resources" together. In performance monitoring, APM tools and tracing, almost every library's core API looks like this.
          

          Teaching 18 / 19· read
          

          Summary
          

          with isn't an isolated bit of syntactic sugar – behind it is the context manager protocol:
          

            

          • __enter__ to go in, __exit__ to leave
            • 

          • __exit__ receives three exception-related parameters; returning True swallows the exception (use carefully)
            • 

          • Several contexts can be separated by commas; in 3.10+ you can wrap them in brackets over several lines
            • 

          • contextlib.contextmanager lets one yield replace two dunder methods – but you must use try/finally to make sure clean-up code runs
            • 

          • Little tools like closing, suppress, redirect_stdout and nullcontext save a lot of boilerplate
            • 

          • ExitStack handles "a variable number of contexts"
            • 

          • async with is the async version – same idea; we'll look closer in the async/await chapter
            • 

          

          Anywhere you have "paired operations", "borrow and return a resource", "temporary switches" or "enter/leave", you can wrap it in a context manager. Once you build this habit, your code will not only be shorter, it'll also handle exception paths naturally – that's what makes with really valuable.
          

          In the next chapter, we'll dive into the world of async/await, and see how Python uses one async keyword to unlock the whole async ecosystem. Get comfortable with with first, and async with will feel like the obvious next step.
          

          Teaching 19 / 19· read
          

          Keep the result, close the resource
          

          with isn't just about saving one line of close(). Let's use some in-memory text to see what's still usable before and after leaving the block:
          

          Python· Runs on this page
          from io import StringIO

with StringIO('Python:15') as stream:
    content = stream.read()
print(content)
print(stream.closed)
          

          Output:
          

          Text
          Python:15
True
          

          The text has already been read into content, and that string is still usable. But stream has been closed. Don't assume the resource is still readable or writable just because the variable name still exists.
          

          Try moving stream.read() to after the with yourself, and look at the error from reading after it's closed. Then raise an exception on purpose inside the block, catch it outside, and check stream.closed. For this object, the resource is still closed on the way out.
          

          Also remember: what with does depends on the specific context manager. It does not promise to automatically undo everything that already happened. For example, if you open a file, write some content, and then an exception happens, using with doesn't automatically restore the old file. Cleaning up resources, whether an exception is passed on, and data transactions are different problems.
