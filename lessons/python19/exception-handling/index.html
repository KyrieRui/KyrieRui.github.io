Exception handling

5 exercises·about 100 min·solve one to unlock the next part

Read the whole chapter →

Teaching 01 / 28· read

When you write code, what's the moment that makes beginners panic the most? Don't answer yet – let me describe a scene. You've just learned the syntax, you excitedly write a few dozen lines of code, press Enter, and the terminal spits out a pile of red text:

Text
Traceback (most recent call last):
  File "main.py", line 5, in <module>
    print(10 / 0)
ZeroDivisionError: division by zero

Totally confused. What is this? What did I do wrong? Why did the program crash?

Actually, this is Python's exception mechanism at work. The program met a situation it couldn't handle – like dividing by zero, reading a file that doesn't exist, or adding a string to a number – so it raises an exception. Then the whole program stops and tells you: "I quit – you clean this up."

But think about it: in the real world, how could programs stop working because of one small problem? If you type the wrong PIN three times at a bank ATM, it shows a message – it doesn't freeze. If a web page can't load an image, it shows a placeholder – the whole page doesn't go blank. If a chat app can't reach the network, it retries – it doesn't crash. Behind all of these, exception handling is doing the work.

Python has a whole set of tools ready for you: try / except / else / finally / raise / custom exception classes, plus exception groups (ExceptionGroup) and except*, added in 3.11. The whole system is very complete. In this article, let's go from the simplest form all the way to the latest PEP 654, so that after reading it, you'll never be scared of a red traceback again.

Teaching 02 / 28· read

Why do programs "blow up"?

Let's start with the simplest example. Open the Python interpreter and type one line:

Python· Read with the text above
print(10 / 0)

Output:

Text
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
ZeroDivisionError: division by zero

This is called an exception. When Python runs 10 / 0, it finds the divisor is zero, which is impossible in maths. So it creates a ZeroDivisionError object and raises (throws) it. If nobody catches it, the exception "bubbles up" all the way to the top, where the Python interpreter catches it, prints the traceback, and exits the program.

Here's another one:

Python· Read with the text above
nums = [1, 2, 3]
print(nums[10])

Output:

Text
Traceback (most recent call last):
  File "<stdin>", line 2, in <module>
IndexError: list index out of range

IndexError – the index is out of range. One more:

Python· Read with the text above
d = {'name': 'Two Drops'}
print(d['age'])

Output:

Text
Traceback (most recent call last):
  File "<stdin>", line 2, in <module>
KeyError: 'age'

KeyError – that key isn't in the dictionary.

Notice? Each kind of "error" has its own name. These names are the types of exceptions – a set of classes built into Python. They're not just for show – they're for you to catch precisely, handling different types in different ways.

Teaching 03 / 28· read

The simplest try / except

Let's fix the first example. We don't want dividing by zero to crash the whole program. Instead, we want a friendly message before it crashes, and then carry on:

Python· Runs on this page
try:
    result = 10 / 0
    print(result)
except ZeroDivisionError:
    print('Oops, you cannot divide by zero')

print('The program keeps running')

Output:

Text
Oops, you cannot divide by zero
The program keeps running

See? The red traceback is gone, the program didn't crash, and the last line "The program keeps running" printed as normal.

The try / except syntax is that simple. Remember three things:

  • Put code that might go wrong in the try: block
  • Put what to do if it goes wrong in the except XxxError: block
  • If the try block has no error, the except block is skipped completely, as if it wasn't there

Now think: if the try block has ten lines, and line three blows up, will the other seven lines still run?

Answer: No. As soon as Python finds an exception in try, it jumps straight to the matching except, and skips the rest of the try block. Let's test it:

Python· Runs on this page
try:
    print('Line one')
    print(10 / 0)
    print('Line three – this line will not run')
except ZeroDivisionError:
    print('Caught it')

print('Program continues')

Output:

Text
Line one
Caught it
Program continues

Sure enough, "Line three" wasn't printed. This detail is really important. Lots of beginners spend ages debugging because they think the code after an exception in try still runs – it doesn't, it's skipped.

    Catching several kinds of exceptions
    

    The example above only caught ZeroDivisionError. But in real code, one piece of code can often raise several kinds of exceptions. For example:
    

    Python· Runs on this page
    def parse_age(s):
    try:
        age = int(s)
        return 100 / age
    except ZeroDivisionError:
        return 'Age cannot be 0'
    except ValueError:
        return 'That is not a number'


print(parse_age('25'))
print(parse_age('0'))
print(parse_age('abc'))
    

    Output:
    

    Text
    4.0
Age cannot be 0
That is not a number
    

    See? Two except branches, each handling a different type of exception. Python checks them in order, runs the first one that matches, and skips the rest.
    

    What if you want to handle two exceptions with the same code? Writing it twice is wordy. There's a shortcut:
    

    Python· Runs on this page
    def parse_age(s):
    try:
        age = int(s)
        return 100 / age
    except (ZeroDivisionError, ValueError):
        return 'Something is wrong with the input'


print(parse_age('25'))
print(parse_age('0'))
print(parse_age('abc'))
    

    Output:
    

    Text
    4.0
Something is wrong with the input
Something is wrong with the input
    

    Put several exception types inside round brackets, separated by commas, and you catch them all at once. Note the brackets – without them, the syntax is wrong.

      Getting the exception object – as e
      

      Knowing "something went wrong" isn't always enough. Sometimes you need to know exactly what went wrong. Python lets you use as to grab the exception object:
      

      Python· Runs on this page
      def parse_age(s):
    try:
        age = int(s)
        return 100 / age
    except (ZeroDivisionError, ValueError) as e:
        return f'Error: {type(e).__name__} - {e}'


print(parse_age('0'))
print(parse_age('abc'))
      

      Output:
      

      Text
      Error: ZeroDivisionError - division by zero
Error: ValueError - invalid literal for int() with base 10: 'abc'
      

      e is the exception object itself. type(e).__name__ is its class name, and str(e) is its error message. For logging and debugging, this is much more useful than just printing "Error!".
      

      Teaching 06 / 28· read
      

      The catch-all – except Exception
      

      Sometimes you don't know exactly what exceptions your code might raise, and you don't want to write a long list of excepts. Then you can use a parent class as a catch-all:
      

      Python· Runs on this page
      try:
    risky_operation()
except Exception as e:
    print(f'Unknown error: {e}')
      

      Exception is the "ancestor" of almost all exceptions, so writing it means "catch almost every exception".
      

      But! There's a trap here. Lots of beginners like to write except: with no type at all, or except BaseException:. Both of these go too far – they also catch KeyboardInterrupt (when you press Ctrl+C to stop the program) and SystemExit (when the program calls sys.exit() itself). Then your program can't even be stopped with Ctrl+C.
      

      Remember: for a catch-all, use Exception – not BaseException, and never a bare except:. That's the golden rule.
      

      Teaching 07 / 28· read
      

      The exception family – the inheritance tree
      

      You might ask: "If Exception is the ancestor of almost all exceptions, what's above it? And what's below it?"
      

      Let's look at the exception family tree:
      

      Text
      BaseException
 ├── SystemExit
 ├── KeyboardInterrupt
 ├── GeneratorExit
 └── Exception
      ├── ArithmeticError
      │    ├── ZeroDivisionError
      │    └── OverflowError
      ├── LookupError
      │    ├── IndexError
      │    └── KeyError
      ├── ValueError
      ├── TypeError
      ├── AttributeError
      ├── NameError
      ├── OSError
      │    └── FileNotFoundError
      └── ...
      

      Key points about this tree:
      

        

      • At the very top is BaseException. Every exception inherits from it
        • 

      • SystemExit / KeyboardInterrupt / GeneratorExit are about controlling the program's flow, and shouldn't be caught by an ordinary try/except
        • 

      • All the other, business-related exceptions are under Exception
        • 

      • Exception is split into several big families: arithmetic errors, lookup errors, value errors, type errors and so on
        • 

      

      Once you understand this tree, you can use a little trick: catching a parent class catches all its child classes. For example:
      

      Python· Runs on this page
      try:
    nums = [1, 2, 3]
    print(nums[10])
except LookupError as e:
    print(f'Lookup error: {e}')
      

      Output:
      

      Text
      Lookup error: list index out of range
      

      IndexError is a child of LookupError, so catching it with the parent works fine.
      

      Now think: if you write several excepts, should the parent go first or the child?
      

      Python· Runs on this page
      # Bad example
try:
    nums = [1, 2, 3]
    print(nums[10])
except LookupError:
    print('Lookup error')
except IndexError:  # This line can never run
    print('Index error')
      

      LookupError already catches IndexError, so the except IndexError after it is useless. So the rule is: children first, parents last. Write the specific exceptions first, and put the broad catch-all at the end.
      

      Teaching 08 / 28· read
      

      else – runs only when nothing went wrong
      

      try / except has two good partners: else and finally. Let's look at else first.
      

      Python· Runs on this page
      def divide(a, b):
    try:
        result = a / b
    except ZeroDivisionError:
        print('You cannot divide by zero')
    else:
        print(f'Success, the result is {result}')


divide(10, 2)
divide(10, 0)
      

      Output:
      

      Text
      Success, the result is 5.0
You cannot divide by zero
      

      The else block only runs when the try block raised no exception. You might ask: "Isn't it the same if I just put the print(f'...') inside try?"
      

      No, it's not. The difference is what gets caught. Look:
      

      Python· Read with the text above
      def divide(a, b):
    try:
        result = a / b
        print(f'Success, the result is {result}')   # Pretend this could raise an exception too
    except ZeroDivisionError:
        print('You cannot divide by zero')
      

      If the print line also raised a ZeroDivisionError (just as an example), it would be caught by the same except – that's a mistake, because you only meant to catch errors in the "calculation" step.
      

      else separates "things to do only after success", so the try block only contains the line that might really go wrong. The logic is cleaner. That's its main value.
      

      Teaching 09 / 28· read
      

      finally – runs no matter what
      

      finally goes even further: whether the try block succeeds or fails, and whether the exception is caught or not, finally always runs.
      

      Python· Run it on your own computer
      def read_first_line(path):
    f = open(path, 'r')
    try:
        return f.readline()
    finally:
        f.close()
        print(f'Closed {path}')
      

      Why do we need finally? Think about what you do in code: open files, connect to databases, ask for resources… When you're done, these all need to be closed or released. If something goes wrong in the middle and the code jumps away, the resource leaks. finally makes sure that "this clean-up code runs no matter what".
      

      finally can also be used together with except:
      

      Python· Run it on your own computer
      def safe_read(path):
    try:
        f = open(path, 'r')
        return f.readline()
    except FileNotFoundError:
        print(f'File {path} does not exist')
        return None
    finally:
        print('Clean-up done')


print(safe_read('not_exist.txt'))
      

      Output:
      

      Text
      File not_exist.txt does not exist
Clean-up done
None
      

      Notice? "Clean-up done" printed whether or not try had an error.
      

      But for opening files, modern Python recommends the with statement. It uses the finally mechanism inside, and is simpler to write:
      

      Python· Run it on your own computer
      def safe_read(path):
    try:
        with open(path, 'r') as f:
            return f.readline()
    except FileNotFoundError:
        print(f'File {path} does not exist')
        return None
      

      with already knows how to "close the file no matter what" – underneath, it's the same thing as finally.

        Raising exceptions yourself – raise
        

        So far, we've only been catching exceptions. Can we raise one? Of course. That's what the raise keyword does.
        

        Python· Runs on this page
        def set_age(age):
    if age < 0:
        raise ValueError(f'Age cannot be negative, you passed {age}')
    if age > 200:
        raise ValueError(f'Age cannot be over 200, you passed {age}')
    return age


try:
    set_age(-5)
except ValueError as e:
    print(f'Bad argument: {e}')
        

        Output:
        

        Text
        Bad argument: Age cannot be negative, you passed -5
        

        raise XxxError('msg') means "raise an XxxError right now, carrying this message". When you write functions, and the caller passes an unreasonable argument or a business rule isn't met, you should raise an exception, so the caller knows "I won't accept this data" – instead of quietly returning some strange value.
        

        Why? Think about it:
        

        Python· Read with the text above
        def set_age(age):
    if age < 0:
        return None      # Bad style
    return age
        

        When the caller gets None, they have no idea whether it means "no data this time" or "I passed something wrong". But with raise ValueError('Age cannot be negative'), the caller understands straight away: "Ah, my argument broke the rules."
        

        Exceptions are Python's standard way of passing error information. They say much more than return None, return -1 or return False.

          Exception chaining – raise ... from e
          

          Let's look at a slightly more advanced situation. Say we have this function:
          

          Python· Run it on your own computer
          def load_config(path):
    with open(path, 'r') as f:
        return f.read()
          

          If path doesn't exist, it raises FileNotFoundError. But from the point of view of "using the config", "file not found" is too low-level. I'd like to raise a more business-like error, like ConfigError('Failed to load config'), but without losing the information about what really went wrong underneath. What do I do?
          

          PEP 3134 gives the answer – exception chaining:
          

          Python· Run it on your own computer
          class ConfigError(Exception):
    pass


def load_config(path):
    try:
        with open(path, 'r') as f:
            return f.read()
    except FileNotFoundError as e:
        raise ConfigError(f'Failed to load config: {path}') from e


try:
    load_config('not_exist.json')
except ConfigError as e:
    print(f'Business error: {e}')
          

          Output:
          

          Text
          Business error: Failed to load config: not_exist.json
          

          Look at raise ConfigError(...) from e. from e attaches the original exception to the new exception's __cause__. If nothing outside catches it, the traceback prints both errors, like this:
          

          Text
          Traceback (most recent call last):
  File "...", line X, in load_config
    with open(path, 'r') as f:
FileNotFoundError: [Errno 2] No such file or directory: 'not_exist.json'

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  File "...", line Y, in <module>
    load_config('not_exist.json')
  File "...", line Z, in load_config
    raise ConfigError(...) from e
ConfigError: Failed to load config: not_exist.json
          

          "The above exception was the direct cause of the following exception" – this sentence is the sign of an exception chain. When you see a traceback like this, know that the error at the top is the root cause, and the one below it was wrapped around it.
          

          What if you leave out from e and just raise ConfigError(...)? Python automatically adds a __context__ for you, and the traceback says "During handling of the above exception, another exception occurred". This is called an implicit chain.
          

          An explicit from e says "I deliberately wrapped a low-level exception in a business exception". Leaving out from e says "while I was handling the last exception, something else went wrong by accident". They mean different things, so when you deliberately wrap an exception, always add from e.
          

          Teaching 12 / 28· read
          

          Custom exception classes
          

          Did you see that ConfigError just now? A custom exception class really is just one line:
          

          Python· Read with the text above
          class ConfigError(Exception):
    pass
          

          Just inherit from Exception. But why make your own? Can't you just use built-in ones like ValueError or RuntimeError?
          

          Let's explain with a "clock-in" example. "Brother Shui" built a clock-in system for the "Coding Dept", with these business rules:
          

            

          • You can't clock in before work starts
            • 

          • You can't clock in twice in one day
            • 

          • You can't clock in if you're not on the office network
            • 

          

          With built-in exceptions:
          

          Python· Read with the text above
          def punch(user, time, ip):
    if time < 9:
        raise ValueError('Work has not started yet')
    if user.already_punched_today:
        raise ValueError('You already clocked in today')
    if not ip.startswith('192.168.'):
        raise ValueError('Not on the office network')
          

          When the caller catches a ValueError, they can't tell which situation it is. If they want to handle each one differently, they'd have to compare message strings – which is very fragile.
          

          With a custom exception family:
          

          Python· Runs on this page
          class PunchError(Exception):
    """Base class for clock-in errors."""
    pass


class PunchTimeError(PunchError):
    pass


class PunchDuplicateError(PunchError):
    pass


class PunchLocationError(PunchError):
    pass


def punch(user_already_punched, hour, ip):
    if hour < 9:
        raise PunchTimeError('Work has not started yet')
    if user_already_punched:
        raise PunchDuplicateError('You already clocked in today')
    if not ip.startswith('192.168.'):
        raise PunchLocationError('Not on the office network')
    return 'Clocked in'


# The caller
try:
    punch(False, 8, '192.168.1.1')
except PunchTimeError as e:
    print(f'Time problem: {e}, please wait until 9')
except PunchDuplicateError as e:
    print(f'Already clocked in: {e}')
except PunchLocationError as e:
    print(f'Location problem: {e}, please connect to the office wifi')
except PunchError as e:
    print(f'Clock-in failed: {e}')
          

          Output:
          

          Text
          Time problem: Work has not started yet, please wait until 9
          

          See?
          

            

          • Each kind of error has its own class, so the caller can catch it precisely
            • 

          • There's a shared parent class PunchError, so the caller can also catch them all at once
            • 

          • The class name itself is documentation – just from the class name, you know what happened, without reading the message
            • 

          

          That's the value of custom exception classes – errors become part of your code's structure too.
          

          Custom exception classes can carry data too, for example:
          

          Python· Runs on this page
          class PunchError(Exception):
    def __init__(self, message, user_id=None, hour=None):
        super().__init__(message)
        self.user_id = user_id
        self.hour = hour


try:
    raise PunchError('Work has not started yet', user_id=123, hour=8)
except PunchError as e:
    print(f'Message: {e}')
    print(f'User: {e.user_id}')
    print(f'Hour: {e.hour}')
          

          Output:
          

          Text
          Message: Work has not started yet
User: 123
Hour: 8
          

          When you need more context, put it in the exception object. For back-end logging and monitoring, structured errors like this are really valuable.

            Teaching 14 / 28· read
            

            Want to report several errors at once? – Exception groups (Python 3.11+)
            

            By now, you know all the normal exception handling. Next is a fairly new feature added in Python 3.11: exception groups (PEP 654).
            

            First, the problem. Say "Brother Shui" has a batch job in the "Coding Dept": send requests to five URLs and save all the results. The code looks roughly like this:
            

            Python· Read with the text above
            def fetch_one(url):
    # Pretend this might fail
    if 'bad' in url:
        raise ValueError(f'Bad argument: {url}')
    if 'down' in url:
        raise ConnectionError(f'Cannot connect: {url}')
    return f'Content of {url}'


def fetch_all(urls):
    results = []
    for url in urls:
        results.append(fetch_one(url))
    return results
            

            Think: if two of the urls raise ValueError and one raises ConnectionError, what happens with the traditional approach?
            

            After the first URL raises an error, fetch_all exits straight away, and the rest never run. You'd never know about the other two errors. But your task needs to "see all the failing URLs at once", so the operations team can fix them all in one go, without running it again and again.
            

            Traditional try/except can only tell you about the first error. It can't handle this. So what do you do?
            

            The home-made way is to collect each URL's exception yourself:
            

            Python· Read with the text above
            def fetch_all(urls):
    results = []
    errors = []
    for url in urls:
        try:
            results.append(fetch_one(url))
        except Exception as e:
            errors.append(e)
    return results, errors
            

            It works, but there are a few problems:
            

              

            • The caller gets a (results, errors) pair, which makes the signature ugly
              • 

            • Errors come back as a "list", so the caller has to check with if and write their own loop to report them
              • 

            • This is a home-made system, so every library does it differently – nothing's standard
              • 

            

            PEP 654 solves this. Python 3.11 added ExceptionGroup, made specifically to "package several exceptions into one" and raise them:
            

            Python· Read with the text above
            def fetch_all(urls):
    results = []
    errors = []
    for url in urls:
        try:
            results.append(fetch_one(url))
        except Exception as e:
            errors.append(e)
    if errors:
        raise ExceptionGroup('Some URLs failed', errors)
    return results
            

            Let's call it:
            

            Python· Read with the text above
            urls = ['ok-1', 'bad-2', 'down-3', 'ok-4', 'bad-5']
try:
    fetch_all(urls)
except ExceptionGroup as eg:
    print(f'There are {len(eg.exceptions)} errors')
    for e in eg.exceptions:
        print(f'  - {type(e).__name__}: {e}')
            

            Output (on Python 3.11+):
            

            Text
            There are 3 errors
  - ValueError: Bad argument: bad-2
  - ConnectionError: Cannot connect: down-3
  - ValueError: Bad argument: bad-5
            

            That's the heart of exception groups: raise a group of exceptions at once, and the caller gets all the errors at once.
            

            This needs Python 3.11+ – older versions can't run it. Run python3 --version to check whether yours is 3.11+.

            Splitting an exception group with except*
            

            You might ask: "After catching an ExceptionGroup, can I handle it by exception type, like a normal except?"
            

            Yes. Python 3.11 also added new syntax: except* (with a star). It's made to split an exception group by type. Look:
            

            Python· Read with the text above
            def fetch_all(urls):
    results = []
    errors = []
    for url in urls:
        try:
            results.append(fetch_one(url))
        except Exception as e:
            errors.append(e)
    if errors:
        raise ExceptionGroup('Some URLs failed', errors)
    return results


urls = ['ok-1', 'bad-2', 'down-3', 'ok-4', 'bad-5']
try:
    fetch_all(urls)
except* ValueError as eg:
    print(f'{len(eg.exceptions)} argument errors:')
    for e in eg.exceptions:
        print(f'  - {e}')
except* ConnectionError as eg:
    print(f'{len(eg.exceptions)} connection errors:')
    for e in eg.exceptions:
        print(f'  - {e}')
            

            Output:
            

            Text
            2 argument errors:
  - Bad argument: bad-2
  - Bad argument: bad-5
1 connection errors:
  - Cannot connect: down-3
            

            See? The two except* branches automatically split the ExceptionGroup into two parts by type, and handle each one. A normal except can't do this – once a normal except matches, it runs once and that's it. But except* goes through the whole group and picks out everything of the matching type.
            

            Key points about except*:
            

              

            • The syntax is except* ExceptionType: – note the star right after except
              • 

            • The eg you get is a new ExceptionGroup containing only the matching exceptions
              • 

            • Every except* branch is checked (not just the first). Exceptions that don't match are "re-packaged" and keep going outwards
              • 

            • You can't mix it with normal except. A try must use either all except, or all except*
              • 

            

            Now think: if a group has both ValueError and OSError, but you only wrote except* ValueError, what happens to the OSErrors?
            

            Answer: they're re-packaged into a new ExceptionGroup and raised again. This is the most basic difference between except* and except – except "takes one", while except* "takes the matching group, and passes the rest on".

            add_note – adding notes to exceptions (Python 3.11+)
            

            Next to exception groups, there's a small feature called add_note, also added in 3.11. It's really handy for debugging.
            

            When debugging, do you often wonder: "Which line raised this KeyError? Which user or which request caused it?" The exception itself only shows the key name, with no context. add_note is for adding that context:
            

            Python· Read with the text above
            def process_user(user_id, data):
    try:
        return data['name']
    except KeyError as e:
        e.add_note(f'Error while processing user {user_id}')
        e.add_note(f'Data keys: {list(data.keys())}')
        raise


process_user(123, {'age': 18})
            

            Output (end of the traceback):
            

            Text
            KeyError: 'name'
Error while processing user 123
Data keys: ['age']
            

            add_note adds the string to the exception object's __notes__ list. When the traceback is printed, these notes appear automatically after the exception message.
            

            Why not just raise a new KeyError('Error while processing user 123, data keys: [age]')? Because that would lose part of the original traceback. add_note "keeps the original exception + adds a note", which is lighter and more elegant.
            

            You can call add_note many times, adding one note each time. It's especially useful when debugging library code or writing middleware.

            Mini project: safe_divide and batch division
            

            We've covered a lot. Let's finish with a small project. The task:
            

              

            • Write a function safe_divide(a, b) that returns the result normally, returns None when dividing by zero, and also returns None for other errors
              • 

            • Write a function batch_divide(pairs) that divides a list of (a, b) pairs, and reports all the errors together using an ExceptionGroup
              • 

            

            First, the first one:
            

            Python· Runs on this page
            def safe_divide(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        print(f'  Division by zero: {a} / {b}')
        return None
    except TypeError as e:
        print(f'  Type error: {e}')
        return None


print(safe_divide(10, 2))
print(safe_divide(10, 0))
print(safe_divide('a', 1))
            

            Output:
            

            Text
            5.0
  Division by zero: 10 / 0
None
  Type error: unsupported operand type(s) for /: 'str' and 'int'
None
            

            Simple, but good enough. Now the batch version – using an exception group:
            

            Python· Read with the text above
            def divide_strict(a, b):
    if b == 0:
        raise ZeroDivisionError(f'{a} / 0')
    if not isinstance(a, (int, float)) or not isinstance(b, (int, float)):
        raise TypeError(f'{a!r} / {b!r} has the wrong type')
    return a / b


def batch_divide(pairs):
    results = []
    errors = []
    for a, b in pairs:
        try:
            results.append(divide_strict(a, b))
        except Exception as e:
            errors.append(e)
    if errors:
        raise ExceptionGroup(f'Batch division had {len(errors)} errors', errors)
    return results


pairs = [(10, 2), (10, 0), ('a', 1), (8, 4), (5, 0)]

try:
    print(batch_divide(pairs))
except* ZeroDivisionError as eg:
    print(f'{len(eg.exceptions)} division-by-zero errors:')
    for e in eg.exceptions:
        print(f'  - {e}')
except* TypeError as eg:
    print(f'{len(eg.exceptions)} type errors:')
    for e in eg.exceptions:
        print(f'  - {e}')
            

            Output (Python 3.11+):
            

            Text
            2 division-by-zero errors:
  - 10 / 0
  - 5 / 0
1 type errors:
  - 'a' / 1 has the wrong type
            

            See how it all works:
            

              

            1. divide_strict strictly raises exceptions – if the arguments are wrong, it never quietly returns None
              2. 

            2. batch_divide collects all the exceptions and raises them together in an ExceptionGroup
              3. 

            3. The caller uses except* to group them by type, and reports all the errors at once
              4. 

            

            This is the partial failure pattern that exception groups bring: whatever should succeed succeeds, whatever should fail fails, and all errors are reported together. This pattern is very common in asyncio concurrency, batch RPC calls and parallel fetching. Before Python 3.11 you had to build it yourself; from 3.11, it's built into the language.

            Nested exception groups – a tree structure
            

            Let's go a bit deeper. An ExceptionGroup is itself an exception. So can it go inside another ExceptionGroup?
            

            Yes. Exception groups form a tree – a group can hold normal exceptions, and also other groups. This nesting is common in situations like "distributed tasks, where sub-tasks have their own sub-tasks".
            

            Here's an example. Say "Brother Shui" wants to update lots of employees' information. For each employee, two parts need updating separately – "basic info" and "clock-in records" – and either part might fail:
            

            Python· Read with the text above
            def update_employee(emp):
    sub_errors = []
    try:
        update_basic_info(emp)
    except Exception as e:
        sub_errors.append(e)
    try:
        update_punch_record(emp)
    except Exception as e:
        sub_errors.append(e)
    if sub_errors:
        raise ExceptionGroup(f'Failed to update employee {emp}', sub_errors)


def batch_update(employees):
    errors = []
    for emp in employees:
        try:
            update_employee(emp)
        except Exception as e:
            errors.append(e)
    if errors:
        raise ExceptionGroup('Some updates in the batch failed', errors)
            

            An exception group from this structure is nested: the outermost group holds several "Failed to update employee X" sub-groups. The clever thing about except* is that it can see through any number of nesting levels and pull out all exceptions of the given type.
            

            Python· Read with the text above
            try:
    batch_update(employees)
except* ConnectionError as eg:
    print(f'Network errors: {len(eg.exceptions)} groups')
except* ValueError as eg:
    print(f'Argument errors: {len(eg.exceptions)} groups')
            

            Whether a ConnectionError is in the first level or the second, except* will find it. This is the biggest difference from a normal except.

            eg.subgroup and eg.split – working with exception groups by hand
            

            except* is usually enough, but sometimes you want finer control – for example, handling only exceptions that meet a specific condition, not just grouping by type. ExceptionGroup has two useful methods for this: subgroup and split.
            

            Python· Read with the text above
            errors = [
    ValueError('bad value 1'),
    TypeError('bad type'),
    ValueError('bad value 2'),
    ConnectionError('network down'),
]
eg = ExceptionGroup('a pile of errors', errors)

# subgroup picks out by condition
value_eg = eg.subgroup(ValueError)
print(f'ValueError sub-group: {len(value_eg.exceptions)}')

# split splits it into two parts: "matching" and "not matching"
matched, rest = eg.split(ValueError)
print(f'Matched: {len(matched.exceptions)}; rest: {len(rest.exceptions)}')
            

            Output (Python 3.11+):
            

            Text
            ValueError sub-group: 2
Matched: 2; rest: 2
            

            Both subgroup and split take either a type or a checking function as their argument. The function version is especially flexible:
            

            Python· Read with the text above
            matched, rest = eg.split(lambda e: 'bad' in str(e))
            

            This picks out every error whose message contains the word "bad". When you write complicated middleware or scheduler code, these two methods are very useful.

            Don't make these mistakes (anti-patterns)
            

            Almost all badly-written exception handling falls into the following anti-patterns. Let's go through them one by one, each with a "wrong" and a "right" version.
            

            Anti-pattern 1: swallowing exceptions
            

            Python· Read with the text above
            # Wrong
try:
    do_something()
except Exception:
    pass
            

            This is called swallowing an exception. Something went wrong, but you don't log it, don't re-raise it, and don't return a special value – you'll never be able to find the root cause of problems.
            

            Python· Run it on your own computer
            # Right
import logging

try:
    do_something()
except Exception:
    logging.exception('do_something failed')
    raise
            

            At the very least, log it. If you decide not to re-raise it, you must have a clear business reason – and I strongly recommend adding a comment explaining "why we don't re-raise".
            

            Anti-pattern 2: catching too widely
            

            Python· Run it on your own computer
            # Wrong
try:
    age = int(input('Age: '))
    save_to_db(age)
except Exception:
    print('Something went wrong')
            

            This try does two things: converting and saving to the database. An error in either step gets caught the same way, and the error information is lost.
            

            Python· Run it on your own computer
            # Right
try:
    age = int(input('Age: '))
except ValueError:
    print('Please enter a valid number')
    return

try:
    save_to_db(age)
except OSError as e:
    print(f'Failed to write to the database: {e}')
    return
            

            Each try block wraps one thing only, and catches the exception types specific to it. This is the "smallest scope" rule for exception handling.
            

            Anti-pattern 3: using exceptions for normal flow control
            

            Python· Read with the text above
            # Wrong – checking whether a key is in a dict
try:
    val = d['key']
    use(val)
except KeyError:
    use_default()
            

            It's not that it doesn't work – but if the logic can be written with if / else, don't use exceptions. Exceptions cost more than normal branches, and they make the code's intention less clear.
            

            Python· Read with the text above
            # Right
val = d.get('key')
if val is not None:
    use(val)
else:
    use_default()
            

            So when are exceptions the right choice? When "normally, this shouldn't go wrong" – like reading files, network requests, or checking user input. These are really "error handling" situations, so exceptions fit naturally.
            

            Anti-pattern 4: forgetting the caller needs the original information
            

            Python· Read with the text above
            # Wrong
try:
    do_thing()
except SomeError as e:
    raise MyError('Operation failed')
            

            This throws away the original exception completely. The caller gets MyError, but the traceback has no information about SomeError – the root cause is lost.
            

            Python· Read with the text above
            # Right
try:
    do_thing()
except SomeError as e:
    raise MyError('Operation failed') from e
            

            Remember from e. It's a tiny effort, but it can save you during a real production incident.
            

            Anti-pattern 5: using except instead of type checking
            

            Python· Read with the text above
            # Wrong
try:
    n = int(x)
except (TypeError, ValueError):
    n = 0
            

            If x's type should really be checked, checking it directly is clearer than relying on an exception as a safety net. Of course, a safety net for outside input is reasonable – but your internal logic shouldn't be written like this.

            assert – lightweight checks while debugging
            

            Besides exception handling, Python has a cousin called assert. Its job is to put "I assume X is definitely true" checks into your code. If it's not true, it raises an AssertionError.
            

            Python· Runs on this page
            def calculate_average(nums):
    assert len(nums) > 0, 'Cannot average an empty list'
    return sum(nums) / len(nums)


print(calculate_average([1, 2, 3]))
            

            Output:
            

            Text
            2.0
            

            The syntax is assert expression, error message. If the expression is false, it raises AssertionError.
            

            But! assert has an important trap: when you run code with python -O (optimised mode), every assert statement is thrown away. So you must never use assert to check input in production. It should only be used for "development and debugging", "test assertions" and "protecting internal invariants" (things that should always be true inside your code).
            

            Wrong example:
            

            Python· Read with the text above
            def withdraw(account, amount):
    assert amount > 0, 'Withdrawal amount must be positive'   # Wrong – the check vanishes in optimised mode
    account.balance -= amount
            

            The right way:
            

            Python· Read with the text above
            def withdraw(account, amount):
    if amount <= 0:
        raise ValueError('Withdrawal amount must be positive')
    account.balance -= amount
            

            Remember a simple rule: assert is for programmers; raise is for the program.

            The traceback module – printing errors more nicely
            

            After catching an exception, sometimes you want to control how the error is printed – for example, when writing logs, or an error page for a web back end. The standard library's traceback module does this.
            

            Python· Read with the text above
            import traceback


def do_work():
    return 1 / 0


try:
    do_work()
except ZeroDivisionError:
    # Turn the full traceback into a string
    s = traceback.format_exc()
    print('--- Error log ---')
    print(s)
    print('--- End ---')
            

            Output:
            

            Text
            --- Error log ---
Traceback (most recent call last):
  File "...", line 8, in <module>
    do_work()
  File "...", line 5, in do_work
    return 1 / 0
           ~~^~~
ZeroDivisionError: division by zero

--- End ---
            

            traceback.format_exc() turns the full traceback of the exception currently being handled into a string. You can save that string to a log, send it in an email, or store it in a database.
            

            Similar functions:
            

              

            • traceback.print_exc(): print it straight to stderr
              • 

            • traceback.format_exception(exc): pass in an exception object, get a list of strings
              • 

            • traceback.print_exception(exc): pass in an exception object, print it to stderr
              • 

            

            These are really handy when writing your own middleware or logging framework.

            logging.exception – the recommended way to log
            

            In production code, you'll almost always use the logging module. It has special support for exceptions:
            

            Python· Run it on your own computer
            import logging

logging.basicConfig(level=logging.INFO)

def risky():
    return 1 / 0


try:
    risky()

            logger.exception(msg) is the same as logger.error(msg, exc_info=True). It automatically adds the current exception's traceback to the log.

            warnings – gentler than exceptions
            

            An exception means "it blew up". But sometimes you want to say "it works, but I don't recommend it" – for example, an old API that's about to be removed, or an argument combination with performance problems. That's when you use Python's warnings module.
            

            Python· Read with the text above
            import warnings


def old_api(x):
    warnings.warn('old_api is deprecated, please use new_api instead', DeprecationWarning)
    return x * 2


print(old_api(3))
            

            Output (the stderr part):
            

            Text
            warning: DeprecationWarning: old_api is deprecated, please use new_api instead
6
            

            warnings.warn(message, category) is a "gentle heads-up" – the program keeps running as normal, but the caller can see the message in stderr.
            

            The key difference between warnings and exceptions: warnings don't stop the program by default. But you can use warnings.filterwarnings('error') to upgrade them to exceptions – handy in tests, to force people to clean up deprecated usage.
            

            If you write libraries for other people, you must know this. It's much friendlier than just raising an exception.

            try/except inside an expression – not allowed
            

            You might have used try expressions in other languages, like Rust's ? or Kotlin's runCatching. Python does not have this. In Python, try/except can only be a statement, not an expression:
            

            Python· Read with the text above
            # Wrong – the syntax doesn't allow this
result = try:
    int(x)
except ValueError:
    0
            

            To get a one-line "use a default if conversion fails", the standard way is to wrap it in a small helper function:
            

            Python· Runs on this page
            def safe_int(x, default=0):
    try:
        return int(x)
    except (TypeError, ValueError):
        return default


print(safe_int('42'))
print(safe_int('abc'))
print(safe_int(None, default=-1))
            

            Output:
            

            Text
            42
0
-1
            

            "The Pythonic way is to wrap it in a small function" – remember this.

            EAFP vs LBYL – Python's philosophy
            

            Finally, let's compare two styles. Understanding this really helps you organise your code.
            

              

            • LBYL (Look Before You Leap): check the condition first with if, then do the operation
              • 

            • EAFP (Easier to Ask Forgiveness than Permission): just do the operation, and use try/except as a safety net if it fails
              • 

            

            For example, "open a file and read it":
            

            Python· Run it on your own computer
            # LBYL
import os

if os.path.exists('config.json'):
    with open('config.json', 'r') as f:
        data = f.read()
else:
    data = ''
            

            Python· Run it on your own computer
            # EAFP
try:
    with open('config.json', 'r') as f:
        data = f.read()
except FileNotFoundError:
    data = ''
            

            Many other languages (like Java) lean towards LBYL, but Python culture leans towards EAFP. There are two reasons:
            

              

            1. LBYL has a "checked, then it changed" risk when several things run at once (for example, os.path.exists says yes, but a second later someone else deletes the file, and open still blows up)
              2. 

            2. EAFP reads more like natural language – "I'll just do it, and deal with it if it doesn't work"
              3. 

            

            Of course, EAFP doesn't suit every situation. For example, dict.get(key, default) is clearer than try / except KeyError for dictionary lookups. Here's how to decide:
            

              

            • Usually succeeds, occasionally fails → use EAFP (exceptions)
              • 

            • Often needs to branch in normal use → use LBYL (if/else)
              •

            A few final words
            

            Let's review today's content:
            

              

            1. try / except is Python's core structure for handling errors. Remember: "children first, parents last"
              2. 

            2. Catch several exceptions with except (A, B); get the exception object with as e
              3. 

            3. Exceptions form a family tree – catching a parent catches all its children. Use Exception as a catch-all, never a bare except:
              4. 

            4. else runs "only if nothing went wrong"; finally runs "no matter what"
              5. 

            5. raise raises an exception yourself; raise ... from e makes an explicit exception chain, so you can find the root cause when debugging
              6. 

            6. Custom exception classes make errors part of your code's structure – essential when business logic gets complicated
              7. 

            7. ExceptionGroup + except* (Python 3.11+) solve the problem of "reporting several errors at once"
              8. 

            8. add_note (Python 3.11+) adds debugging context to an exception – more elegant than raising a new one
              9. 

            

            How well you handle exceptions is one of the biggest differences between beginners and experienced programmers. Beginners either don't handle them at all – the program blows up and that's it – or handle them badly – except Exception: pass swallows every error, and when something goes wrong, nobody can save it. Experienced programmers catch precisely, pass errors on sensibly, wrap them when needed, and never quietly swallow them.

            def parse_minutes(text):
