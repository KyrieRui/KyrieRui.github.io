What to do after you finish: three paths with Python

Dear old friends –

If you're reading this chapter, Brother Shui wants to congratulate you first.

From python0 all the way to python27, we've talked about variables, functions, object-oriented programming, exceptions, files, modules, virtual environments, type hints, pathlib, dataclass and Pydantic, context managers, async/await + httpx, pyproject.toml, uv, pytest, working together with Git, CI/CD, publishing to PyPI… twenty-eight whole chapters, hundreds of thousands of words, hundreds of pieces of code. If you've made it here, you're no longer a beginner who "can only write print('hello')". You're a real Python engineer who can build a project from scratch, write tests, publish packages and work with a team.

But have you noticed something? After reading these twenty-eight chapters, you seem to know a lot – yet as soon as you close the book, you're not sure what to write next.

Brother Shui knows this feeling very well. Python's syntax and engineering are only the foundations. Once the foundations are built, you have to choose what kind of house to build on top. The Python world is huge – too big to learn in a lifetime. But even though it's big, there are only a few main directions. Picking one and following it is a hundred times better than aimlessly working through tutorials.

In this chapter, Brother Shui won't teach syntax or write big chunks of code. Instead, here are the three most popular paths with Python:

  1. Data / AI / machine learning – the hottest direction in 2026; Python is the native language of AI
  2. Web back-end development – fast to build, highly visible, and lots of jobs
  3. Automation / scripts / tools – turning everyday work into code; this is how Python first became popular

For each direction, Brother Shui will cover three things: why choose it, a list of must-know libraries, and three starter projects. Pick the one that suits you best and work through the projects – that's more useful than reading ten books.

Let's go.

Teaching 02 / 11· read

Direction 1: Data / AI / machine learning

Why choose this direction

Look on job websites in 2026 and search for "Python engineer". Most of the jobs that come up include words like "data", "algorithms", "AI", "LLM", "large models" and "machine learning". That's not a coincidence – Python is the de facto native language of the AI era.

Why? Brother Shui gives three reasons –

The first is the ecosystem. From numpy/pandas in the early 2010s, to scikit-learn in 2015, to tensorflow/pytorch in 2017, to transformers/langchain and the openai/anthropic SDKs after 2022 – over twenty years, the first version of almost every important AI library was written for Python. It's not that other languages can't be used, but when you use them, you find "it doesn't connect with the main community". If everyone publishes papers using PyTorch and you rewrite things in Julia or Rust, nobody will talk to you about reproducing the paper.

The second is speed. The AI world is a place where "a paper comes out today, and someone open-sources the code tomorrow". At that speed, a Python library you can install with one pip install line is ten thousand times quicker to get going than a C++/Rust library that takes half an hour to compile. Language performance does matter, but the order "get it working first, optimise later" is pushed to the extreme in AI, and Python is the best answer for the "get it working first" step.

The third is money. In 2026, AI engineers have the highest pay of all the Python directions. Brother Shui isn't telling you to "learn AI for the money" – just that demand, earning potential and room for imagination in AI are all clearly there, so the rewards for going in this direction rise steeply.

So – if you're interested in topics like "letting machines learn by themselves", "having a model write code for me" or "making a program describe a picture", Brother Shui recommends you take a serious look at the AI path.

Must-know libraries

Libraries for data/AI come in layers, from bottom to top –

Layer Example libraries What they're for
Data basics numpy, pandas, matplotlib, jupyter Arrays, tables, charts and interactive notebooks – the "data starter kit"
Data extras polars, seaborn, plotly A Rust-powered upgrade to pandas, prettier statistics charts, interactive charts
Traditional ML scikit-learn, xgboost, lightgbm Classification, regression, clustering, decision trees, gradient boosting
Deep learning pytorch, transformers, huggingface_hub Neural network frameworks; load pre-trained models in one line
LLM apps anthropic, openai, langchain, llama-index Call commercial LLMs, build RAG, build agents

After seeing this table, you might feel a bit lost – "I have to learn all this?" Don't panic. This table is a map, not a checklist. A map shows you "what the scenery in this direction looks like". When you really start learning, follow this path –

  1. Master the four basics first: numpy for arrays, pandas for tables, matplotlib for charts and jupyter as your drawing board. Know these four well, and you can do 70% of data analysis tasks.
  2. scikit-learn is the way into traditional ML: decision trees, random forests, SVMs, KMeans and other classic algorithms are all inside, with a very consistent API – fit to train, predict to predict, a model in three lines of code.
  3. transformers is the shortcut to deep learning: HuggingFace packages all the main pre-trained models (BERT, GPT-2, Llama, Qwen) behind one interface. One line, pipeline('sentiment-analysis'), runs sentiment analysis. You don't need to start by chewing through PyTorch – use pre-trained models to get things done, and dig deeper when you hit a limit.
  4. LLM SDKs are the new infrastructure of 2026: anthropic calls Claude, openai calls GPT, plus langchain for orchestration and llama-index for RAG. This combination is the standard kit for the new job of "LLM application engineer".

"How can polars challenge pandas?" Brother Shui will say a little more about this – polars is a DataFrame library written in Rust. It's often 5–10 times faster than pandas, and its API is more modern (strict types, lazy evaluation, harder to get wrong). Since 2024, more and more new projects choose polars first. But pandas has a very mature ecosystem and many more tutorials, so I still recommend starting with pandas. Once you've written lots of pandas and think "this syntax is so annoying", you'll naturally go and look at polars.

Three starter projects

Project 1: Analyse a public dataset with pandas
  • What to do: Download a CSV from Kaggle (try Titanic or TMDB Movies), read it into jupyter, and do 5 analyses: count missing values, draw a histogram of a distribution, draw a correlation heatmap, do a group-by summary, and make one chart that tells a story
  • Difficulty: ★☆☆☆☆
  • Amount of code: 100–200 lines
  • What you learn: the basic pandas operations read_csv/groupby/merge/pivot_table; drawing charts with matplotlib and seaborn; writing an analysis report in jupyter that "you can show other people"

Brother Shui strongly recommends making this your first project. It doesn't just teach pandas – it builds a habit every AI engineer needs: when you meet unfamiliar data, your first move is to look at the distribution, the missing values and the outliers, not to dive straight into writing a model.

Project 2: Run a local classification model with transformers
  • What to do: Use HuggingFace's pipeline('sentiment-analysis') to make a "good or bad movie review detector". First run a pre-trained model as it is, then download the IMDB review dataset and fine-tune it, raising the accuracy from about 85% to about 92%
  • Difficulty: ★★★☆☆
  • Amount of code: 200–400 lines
  • What you learn: how to use transformers pipeline, how to find models on the HuggingFace Hub, the Trainer API fine-tuning process, switching between GPU and CPU, saving and loading models

"What if I don't have a graphics card?" Use Google Colab. It gives you a free T4 GPU, which is enough for small models like this. Or use the MPS back end on Apple Silicon – M-series chips can train locally too.

Project 3: Call the Claude API to make a "PDF summary" tool
  • What to do: Write a command-line tool that takes a PDF path and outputs a 200-word summary. The process is – extract the text with pypdf → cut it into chunks of about 2000 characters → call the anthropic SDK to have Claude summarise each chunk → finally have Claude combine all the chunk summaries into one
  • Difficulty: ★★☆☆☆
  • Amount of code: 100–200 lines
  • What you learn: how to use the anthropic SDK, managing API keys (.env + python-dotenv), strategies for splitting long text, an introduction to prompt engineering, streaming output

This project is the closest to real work in 2026. Write a tool like this at a company, and it immediately solves the pain of "reading 5 industry reports every week" – your boss will want to give you a raise.

Direction 2: Web back-end development

Why choose this direction

"Web back end" sounds old. Do people still write it in 2026?

Yes, and lots of them. The reason is simple – every company needs APIs. Front-end frameworks keep changing (Vue, React, Svelte), and apps have gone from native to hybrid to cross-platform, but the back end is always there, steadily handling requests, reading databases, calling outside services and returning JSON.

Web back ends won't disappear – they'll only get more important, because:

  1. AI apps are really web apps. Look at ChatGPT, Claude or Cursor – the front end is a chat box, and the back end is a pile of APIs calling models. 90% of an LLM engineer's work is actually writing back ends, just with an extra "call the model" step.
  2. Microservices are still spreading. One big app per company becomes dozens of small services, and each one is a web back-end project. Python is very fast to develop with for small services like these.
  3. The widest range of jobs. Search job sites for "Python back end", and big cities post hundreds of new jobs every day – more than AI jobs, and slightly easier to get into.

So what's Python's advantage for back ends compared with Java, Go or Node? Brother Shui gives three points –

  • Fast development: A CRUD API might be about 100 lines in Python; the same feature in Java is at least 300 lines
  • Seamless connection with the AI ecosystem: If the back end needs some "call an LLM to process user input" logic, in Python it's one import
  • Since 2024, Python back-end engineering has caught up: The modern stack of fastapi + pydantic + sqlmodel + uv has type safety, automatically generated docs and decent performance – it no longer gets crushed by Go

Must-know libraries

Role Example libraries What they're for
Web framework fastapi, starlette Writing APIs – the main first choice
Data validation pydantic Type checking for request and response bodies, deeply integrated with fastapi
ASGI server uvicorn, hypercorn, granian Servers that run fastapi; in production usually uvicorn + gunicorn
ORM sqlalchemy 2.x, sqlmodel Working with databases; sqlmodel is a simpler SQLAlchemy by the author of fastapi
Database migrations alembic Managing table structure changes – adding a field, changing a type
Caching redis-py, aiocache Redis client, in-memory cache
Background tasks celery, dramatiq, arq Running emails, scrapers and scheduled jobs in the background
Authentication python-jose, passlib, authlib JWT, password hashing, OAuth
HTTP client httpx Calling outside APIs, sync or async
Testing pytest, httpx.AsyncClient API tests

"So many – where do I start?" Go in stages, from the bottom up –

  1. Stage 1: a one-file API. Install fastapi and uvicorn, write a 50-line main.py and run it, then open http://localhost:8000/docs in a browser to see the automatically generated Swagger docs. This takes 30 minutes, and you'll be hooked straight away.
  2. Stage 2: add a database. Install sqlmodel, add a SQLite database (no separate install – Python comes with it), and write a set of CRUD endpoints (create, read, update, delete). Once this works, you can already write a decent API.
  3. Stage 3: add authentication. Install python-jose and passlib, add a /login endpoint that issues a JWT, and add Depends(get_current_user) to protect the other endpoints. After this, your API is "enterprise grade".
  4. Stage 4: add background tasks. Install celery or the lighter dramatiq, and send slow jobs like "send an email" or "generate a PDF" to the background. This step takes you to "real production" level.

"What about Django?" Django 5.x is still doing very well in 2026 – it and fastapi follow two different philosophies:

  • fastapi is "building blocks": start from nothing and install what you need – great for APIs, microservices and AI back ends
  • django is "everything included": an admin panel, ORM, templates, forms and a user system all come built in – great for "a team building a complete website from scratch"

If you later want to build content sites, online shops or company internal systems, Django is still a good choice. But if your goal is AI back ends, microservices or mobile app back ends, fastapi is the default answer in 2026.

Three starter projects

Project 1: A todo API (CRUD + sqlmodel)
  • What to do: Write a to-do list API with endpoints for "create a todo", "list all todos", "get a todo by ID", "update a todo" and "delete a todo". Store the data in SQLite, use sqlmodel as the ORM, and write 5 API tests with pytest
  • Difficulty: ★☆☆☆☆
  • Amount of code: 200–300 lines
  • What you learn: fastapi routes, pydantic models, select/session.add/session.commit in the sqlmodel ORM, writing API tests with pytest, how to use the Swagger docs

Brother Shui recommends that everyone who wants to learn web back ends does this project. It's small, but it has everything – after it, you'll really feel that "writing APIs in Python is fast".

Project 2: Add JWT authentication to the todo API
  • What to do: Building on project 1, add a user system – a User table, a /register endpoint, a /login endpoint (returning a JWT), and protect all the other endpoints with Depends(get_current_user). Each todo is linked to a user_id, and users can only see and change their own
  • Difficulty: ★★★☆☆
  • Amount of code: 300–500 lines
  • What you learn: how JWT works, how passlib hashes passwords, fastapi's Depends dependency injection, foreign keys and joins in relational databases, "row-level isolation" for permissions

JWT is one of the most commonly asked web back-end ideas in 2026. Once you've passed this level, no back-end project will scare you.

Project 3: Add background tasks (sending email with celery)
  • What to do: Building on project 2, add a feature – after a user registers, send them a welcome email, but without slowing down the API response. Install celery + redis, mark the email function with @app.task, and in the register endpoint call send_welcome_email.delay(user.email) and return straight away. A worker really sends the email in the background
  • Difficulty: ★★★★☆
  • Amount of code: 400–600 lines
  • What you learn: the idea of message queues, celery's broker and backend, how to use redis as a queue, how to deploy workers, why we need background tasks (user experience, stability)

After this project, you've reached the door of "distributed back ends". Learning Kafka or microservices later all builds out from this idea.

Direction 3: Automation / scripts / tools

Why choose this direction

Have you heard Python's nickname – "the glue language"?

This nickname isn't praising Python for being fast, or for type safety – it's praising Python because it "can stick anything together". Python's standard library is huge, its third-party ecosystem is enormous, and it works with system calls, HTTP, databases, files, Excel, PDFs, chat apps… almost any "repetitive work" can be turned into a Python script.

This direction has a few special features –

  1. Quick results. A 50-line script might immediately save half an hour of repetitive work every day. After writing it, you use it yourself and enjoy it yourself – no need for "launches", "reviews" or "gradual rollouts".
  2. You don't need a big company. The AI and back-end directions suit working in a company (you need data, servers, a business). Automation takes off with just a laptop. You could even use it for freelance work or a side project.
  3. The easiest to start, but the ceiling isn't low. Beginners can write the simplest scripts, and more complex things like "distributed web scrapers", "company automation platforms" and "DevOps toolchains" grow from this direction too – senior jobs here are just as well paid.

If your goal is "making my daily work easier", or "doing small projects where I can see results straight away", automation is the best value choice.

Must-know libraries

Purpose Example libraries What they're for
HTTP requests requests, httpx Calling APIs, fetching web pages; httpx supports async
Web scraping beautifulsoup4, lxml, playwright, selenium Parsing HTML, controlling a browser automatically
Scheduled tasks schedule, apscheduler Run once every day at 9, or every 5 minutes
Remote control paramiko, fabric SSH into a server and run commands
Terminal UI rich, textual Coloured output, tables, progress bars, TUI apps
CLI frameworks click, typer Writing command-line tools – argument parsing ten times more elegant than argparse
Config files pyyaml, tomllib, configparser Reading YAML, TOML and INI
Files pathlib, shutil, watchdog Path handling (standard library), watching files for changes
Office automation openpyxl, python-docx, pypdf Excel, Word, PDF
Notifications webhooks (Slack, DingTalk, Feishu, …) Send a message when something happens

"How do I learn this lot?" For automation, don't learn from the list – learn from projects. Think of "some annoying thing I do every day or every week", then use the libraries above to get rid of it, learning what you need as you go. After six months, you'll naturally know this list well.

Brother Shui has to give the rich library special praise. Written by Will McGugan, it makes Python terminal output colourful and nicely formatted, with progress bars, tables, Markdown and highlighted error tracebacks all built in. Install it, and your command-line tools immediately look "proper". textual is a TUI framework by the same author – it lets you build a responsive app inside the terminal, using components like on the web. It's loads of fun.

Three starter projects

Project 1: Web page change monitor + chat notifications
  • What to do: Watch a web page (for example "the price of a product", "a blogger's latest post" or "tickets left for a train"), fetch it every 10 minutes, and when something changes, send a notification to a group chat with a webhook (Slack, DingTalk, Feishu, etc.). Schedule the script with apscheduler, use httpx for HTTP and beautifulsoup4 to parse the HTML
  • Difficulty: ★★☆☆☆
  • Amount of code: 100–200 lines
  • What you learn: HTTP GET, parsing HTML (CSS selectors), comparing states (comparing hashes, diffs), scheduled tasks, how to send webhooks

Brother Shui has written several versions of this project himself – watching blog subscriptions, concert tickets and price drops on shopping sites are all variations. Once you've made one, you can start a new monitor for anything by changing two lines – very reusable.

Project 2: Automatically back up a folder to OSS / S3
  • What to do: Write a script that, at 2 a.m. every day, zips a chosen folder (for example ~/Documents/Important), names it by date (backup-2026-04-28.zip), uploads it to Alibaba Cloud OSS or AWS S3, then deletes backups older than 30 days. Schedule it with apscheduler, compress with the standard library's zipfile, and upload with oss2 or boto3
  • Difficulty: ★★★☆☆
  • Amount of code: 200–300 lines
  • What you learn: walking through files (pathlib), zip compression, using an object storage SDK, managing keys (.env), lifecycle management (cleaning up by date), logging (logging)

"What's the point?" The code, notes and designs on your computer – would they all be gone if the hard drive broke one day? Write a backup script like this once, and use it for ten years. Brother Shui's Mac is still running a backup script written in 2018 that's never been changed.

Project 3: An interactive TUI app (rich + textual)
  • What to do: Use textual to write a terminal todo app – a list of all todos on the left, editable details on the right, a status bar at the bottom showing statistics, n to create, d to delete, e to edit. Store the data in a local JSON file
  • Difficulty: ★★★★☆
  • Amount of code: 300–500 lines
  • What you learn: textual components, layout, events, CSS styling (yes, TUIs use CSS too), keyboard shortcut bindings, managing app state

This project is a bit harder, but when you finish, you'll discover that "you can write an app like VS Code right inside the terminal". No other project gives you this sense of achievement. When Brother Shui finished his first textual app, he was so excited he posted about it on social media.

Cross-cutting skills: things all three directions need

Whichever direction you choose in the end, you need to understand these cross-cutting skills – they're the "common base" of every Python engineer in 2026:

  • Git: As well as add / commit / push, learn branch / merge / rebase / cherry-pick, and be able to read git log --graph. The python25 chapter covered this – go back and look again.
  • Docker: Put your Python project into a container, write a Dockerfile, and run docker compose up to start the app + database + cache in one go. Especially important for back ends.
  • Linux basics: ssh / cd / ls / grep / awk / tail -f / ps / top / systemctl, and be able to edit a config file with vim. A must for operations work, and the other directions should know a little too.
  • SQL basics: SELECT / JOIN / GROUP BY / WHERE / INDEX. Essential for back ends and data; automation uses it sometimes too.
  • Basic HTTP / REST ideas: GET / POST / PUT / DELETE, status codes, cookies, JWT, CORS. Useful in all three directions.

You don't need to study these separately – fill them in when you meet them while doing projects, and after six months you'll know them. The key is not to avoid unfamiliar ideas when you see them. Learn them on the spot each time, and the knowledge will naturally stick.

Teaching 06 / 11· read

How to choose a direction

Having read this far, you might be feeling unsure – "which one should I choose?"

Brother Shui gives a simple rule –

  • Want to ride the LLM wave, fascinated by "making machines think" → choose Data / AI
  • Want to build visible products, love seeing your results running online → choose Web back end
  • Want to lighten your workload right now, love tinkering with everyday tools → choose Automation

Or even simpler – whichever direction's "starter projects" make you want to start right away, choose that one. That "I want to get going" feeling is the most accurate inner compass.

"Can I mix them?" Of course. Brother Shui is a "automation + AI" mix himself – writing little Python tools every day, with LLM calls inside, so each tool is ten times smarter than a plain script. There are no walls between the three directions. As long as your foundations in syntax and engineering are solid, any path can take you all the way.

But at the start, Brother Shui recommends you "focus" – choose one direction for six months and finish all three projects above, then think about branching out. If you learn all three at once at the start, you'll end up half-knowing all three, with nothing to show.

Keep learning: resources for the road ahead

At this point, you've graduated from "tutorial reader", and next you need to join the community yourself. Brother Shui recommends these places to follow long-term –

  • Real Python: The best Python tutorial site in the English-speaking community, from basic to advanced, with two or three in-depth articles every week
  • Talk Python To Me: A podcast hosted by Michael Kennedy – each episode invites a well-known community member to talk about one topic. Great for listening on the way to school or work
  • PyCon talks: Free to watch on YouTube – every year PyCon US / EU / China have hundreds of high-quality talks. Pick the ones that interest you
  • Python Weekly: One email a week that filters out the Python news, libraries and projects worth seeing that week
  • A new Python version comes out every October: Go to What's New in Python to see what the new version adds, and keep up with each version

The original Chinese tutorial by Brother Shui keeps being updated in the walter201230/Python repository – you're welcome to star it, watch it, and open issues and pull requests. Tutorials stay still, but communities are alive. Growing with a group of people is ten thousand times better than studying alone.

Dear old friends –

Writing this, Brother Shui can't help going back to the start of the python0 chapter – "Learning Python takes one step at a time, steadily and carefully."

First, finish a study-time tracker

The directions and resources above give you lots of choices. But first, let's use what you've already learned to make something real: a tool that records a subject and the minutes studied, lists the records, totals them by subject, and saves them to a local file.

Let's agree on the inputs and results first. Minutes are whole numbers that aren't negative, and 0 is allowed; the subject can't be empty. The same subject can appear in several records, and they're added up for the total. If the file doesn't exist, start with no records. If the file is damaged, report an error – don't treat it as an empty list and overwrite it.

Version What you do yourself How to check it
Version 1 Use a list and dictionaries to store Python 15 minutes, Reading 10 minutes, Python 5 minutes It shows the three records in order
Version 2 Use a loop to make the grand total and the total by subject Total 30, Python total 20
Version 3 Split it into functions, such as creating a record and totalling With no records, the total is 0; functions return results instead of only printing
Version 4 Save and load with UTF-8 JSON After restarting, the text and minutes are still the same
Version 5 Handle negative numbers, empty subjects and damaged files Errors are explained clearly, and an existing broken file isn't overwritten with empty data
Version 6 Add a command-line entry point and tests The help explains how to use it, and all the check cases pass

After each version, first explain in your own words its inputs, its outputs and the errors it might meet, then look at the next version. Don't paste in the complete reference code at the start and then treat "it runs" as "I can write it on my own".

Teaching 10 / 11· read

Download the reference files and run them locally

The reference version is in the tutorial repository: tracker.py, test_tracker.py and the usage guide. Save the files into a new practice folder, open a terminal in that folder and run:

Bash
python3 tracker.py --file practice-records.json add Python 15
python3 tracker.py --file practice-records.json add Reading 10
python3 tracker.py --file practice-records.json add Python 5
python3 tracker.py --file practice-records.json list
python3 tracker.py --file practice-records.json total
python3 tracker.py --file practice-records.json total --subject Python
python3 -m unittest -v

The last two totals are 30 and 20 minutes. Every add adds a new record, so running the whole set of commands again keeps adding up – use a fresh practice file when checking the example.

You can do the calculation practice for the first three versions in a browser first; command-line arguments, saving between runs and file tests are done on your own computer. It doesn't need an account, an API key or any online service. The records file is ordinary local JSON, with no transactions and no handling for several people writing at once – learn the process with practice data first.

Teaching 11 / 11· read

When you're done, try a new requirement

First add a record "Python 0 minutes", and check the total doesn't change but the record is still there. Then add a new subject, and check the subject filter isn't hard-coded. Finally, deliberately break the records file so it isn't valid JSON, and check the program reports an error and keeps the original file.

If you can explain and check all of these yourself, then think about adding dates or making a simple interface. Keep the current working version first, write down the new requirement and the result you expect, and then start changing things. You'll find that the lists, functions, exceptions and tests you learned bit by bit can now work together to finish one real job.
