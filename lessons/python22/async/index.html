Async programming: async/await lets one thread wait for a hundred things at once

Have you ever written a web scraper? Here's a quick one:

Python· Runs on this page
import time


def fake_get(url):
    time.sleep(0.01)
    return f'GOT {url}'


def main():
    urls = [f'https://example.com/{i}' for i in range(5)]
    start = time.perf_counter()
    results = []
    for u in urls:
        results.append(fake_get(u))
    cost = time.perf_counter() - start
    print(f'Got {len(results)} results in {cost:.3f} seconds')


main()

The output is roughly:

Text
Got 5 results in 0.05 seconds

Each request pretends to take 0.01 seconds, so 5 in a row take 0.05 seconds. With real network requests of 200 milliseconds each, 100 in a row would take 20 seconds – painfully slow.

"Easy – use threads!" someone says straight away. "100 URLs, 100 threads, run them all together."

Threads can solve this, of course. But isn't 100 threads a bit extravagant? 99% of the time, those 100 threads are all doing the same thing: waiting for network packets to come back. This is really a waiting problem, not a computing problem. Starting 100 operating-system threads just to "wait" makes neither the CPU nor the memory happy.

And with lots of threads, old friends like "locks", "race conditions" and "deadlocks" start knocking on your door one by one. You just wanted to fetch some web pages – why are you suddenly studying operating systems?

Python gives us another way: asyncio. Its selling point is simple – one thread, waiting for a hundred things at once. Your first reaction to that is probably: "That can't be right – how can one thread do a hundred things at once?"

That's the question this chapter answers.

Teaching 02 / 17· read

A gut-feeling comparison: 3 seconds in a row vs 1 second together

Let's skip the theory and see the effect first. Below is "normal" code that runs one after another. Three tasks, each waiting 1 second:

Python· Read with the text above
import time


def task(name):
    time.sleep(1)
    return f'{name} done'


start = time.perf_counter()
r1 = task('Clock in')
r2 = task('Query')
r3 = task('Upload')
cost = time.perf_counter() - start
print(r1, r2, r3)
print(f'{cost:.2f} seconds in total')

Output:

Text
Clock in done Query done Upload done
3.01 seconds in total

Each one politely waits its turn, one second at a time. Nothing special.

Now the async version:

Python· Read with the text above
import asyncio
import time


async def task(name):
    await asyncio.sleep(1)
    return f'{name} done'


async def main():
    start = time.perf_counter()
    r1, r2, r3 = await asyncio.gather(
        task('Clock in'),
        task('Query'),
        task('Upload'),
    )
    cost = time.perf_counter() - start
    print(r1, r2, r3)
    print(f'{cost:.2f} seconds in total')


asyncio.run(main())

Output:

Text
Clock in done Query done Upload done
1.00 seconds in total

3 seconds became 1 second – the three tasks really did finish "at the same time". Don't worry yet about what async, await and gather mean. Just remember one fact: while one coroutine is waiting in asyncio.sleep(1), another coroutine can use the CPU for its own work. The three coroutines' waits overlap, so the total time is the longest one, not all three added together.

That's the core magic of asyncio. It doesn't secretly start threads, and it doesn't make the CPU faster. What it does is simple: when a coroutine is waiting for I/O (input/output), it gives the CPU to other coroutines, and carries on when the wait is over.

By now you should have a bit of a feel for it. Let's take the syntax apart step by step.

Teaching 03 / 17· read

Your first async function: how is it different from a normal function?

A normal function looks like this:

Python· Runs on this page
def hello():
    return 'Hello, Two Drops'


print(hello())

Output:

Text
Hello, Two Drops

Add the async keyword, and it becomes a coroutine function:

Python· Read with the text above
async def hello():
    return 'Hello, Two Drops'


print(hello())

Output:

Text
<coroutine object hello at 0x...>
RuntimeWarning: coroutine 'hello' was never awaited

Do you see the difference? It's the same print(hello()), but the normal function returns the string 'Hello, Two Drops', while the coroutine function returns a coroutine object – a <coroutine object>, not a string.

Even worse, Python adds a warning: "this coroutine was never awaited".

What does that mean? Here's the key idea:

  • async def does not define "a function that runs straight away"
  • When you call a function defined with async def, it doesn't run at all – it just gives you back a "to-do slip"

Think of it like this: calling a normal function hello() is like "sending someone to do a job and getting the result immediately". Calling a coroutine function hello() is like "writing a job slip and handing it to you – when and who does it is another matter".

This "job slip" is the coroutine object. It must be awaited, or handed to the event loop to run, before the code inside it actually runs.

Teaching 04 / 17· read

await: making a coroutine run

So how do you make the job slip actually happen? With await:

Python· Read with the text above
import asyncio


async def hello():
    return 'Hello, Two Drops'


async def main():
    result = await hello()
    print(result)


asyncio.run(main())

Output:

Text
Hello, Two Drops

Now we get the string. You can read await hello() as "please finish the hello() job slip for me, and give me the result".

But there's a very important limit: await can only be written inside an async def function. Try writing await in a normal function, and Python tells you SyntaxError: 'await' outside async function.

"So what if I want to call an async def function from a normal script?" That's where the next character comes in – asyncio.run().

Teaching 05 / 17· read

asyncio.run(): the door into the async world

asyncio.run() is the "door" between synchronous (normal) code and asynchronous code. It takes a coroutine object, starts an event loop, runs the coroutine to the end, and then closes the event loop:

Python· Read with the text above
import asyncio


async def main():
    print('I am in the async world')
    await asyncio.sleep(0.01)
    print('I am in the async world again')


asyncio.run(main())

Output:

Text
I am in the async world
I am in the async world again

There's a very important design hidden here: a whole program usually has only one event loop, started by asyncio.run(). Every coroutine runs inside this loop. You can picture it like this:

  • The synchronous world → one straight road, one step after another
  • The async world → a control centre (the event loop) with lots of coroutines hanging on it; whoever can run gets to run

asyncio.run() is the entrance from the synchronous world into the async world. A program should only call it once (calling it inside itself gives an error).

So far, you've learned three basic ideas: async def defines a coroutine function, await waits for a coroutine's result, and asyncio.run() starts the event loop. With these three, you can already write the smallest working async program.

      What happens if you don't await a coroutine object?
      

      How serious is that "coroutine was never awaited" warning? Here's some code where it's very easy to fall into the trap:
      

      Python· Read with the text above
      import asyncio


async def punch():
    print('Two Drops starts clocking in')
    await asyncio.sleep(0.01)
    print('Two Drops finished clocking in')


async def main():
    punch()
    print('main is finished')


asyncio.run(main())
      

      Output:
      

      Text
      main is finished
RuntimeWarning: coroutine 'punch' was never awaited
      

      Can you see what's wrong? The punch() line never printed "Two Drops starts clocking in". punch() only created a coroutine object, which was then thrown away – not a single line inside it ran.
      

      This is one of asyncio's most classic traps: forgetting await. In the synchronous world, writing a function name with brackets means running it. In the async world, writing a function name with brackets only "gets you a job slip" – without await, you've thrown the slip in the bin.
      

      The correct way, of course, is:
      

      Python· Read with the text above
      import asyncio


async def punch():
    print('Two Drops starts clocking in')
    await asyncio.sleep(0.01)
    print('Two Drops finished clocking in')


async def main():
    await punch()
    print('main is finished')


asyncio.run(main())
      

      Output:
      

      Text
      Two Drops starts clocking in
Two Drops finished clocking in
main is finished
      

      Remember this: a coroutine that isn't awaited might as well not exist.
      

      Teaching 07 / 17· read
      

      Waiting for several at once: asyncio.gather
      

      Now you can write async code that runs one after another. But back to the first example – 3 tasks done in 1 second – how does "waiting for several at once" work? The answer is asyncio.gather.
      

      First, the wrong way:
      

      Python· Read with the text above
      import asyncio
import time


async def task(name):
    await asyncio.sleep(0.5)
    return f'{name} done'


async def main():
    start = time.perf_counter()
    r1 = await task('A')
    r2 = await task('B')
    r3 = await task('C')
    cost = time.perf_counter() - start
    print(r1, r2, r3)
    print(f'Took {cost:.2f} seconds')


asyncio.run(main())
      

      Output:
      

      Text
      A done B done C done
Took 1.50 seconds
      

      "Isn't async supposed to be fast? Why is it still 1.5 seconds?"
      

      Look carefully. await task('A') comes first, meaning "wait for A to finish, then carry on". One await after another is really just running them in a row. async/await does not make things run together automatically.
      

      To run them together, you must clearly tell the event loop "these can all start at the same time". That's what asyncio.gather does:
      

      Python· Read with the text above
      import asyncio
import time


async def task(name):
    await asyncio.sleep(0.5)
    return f'{name} done'


async def main():
    start = time.perf_counter()
    r1, r2, r3 = await asyncio.gather(
        task('A'),
        task('B'),
        task('C'),
    )
    cost = time.perf_counter() - start
    print(r1, r2, r3)
    print(f'Took {cost:.2f} seconds')


asyncio.run(main())
      

      Output:
      

      Text
      A done B done C done
Took 0.50 seconds
      

      That's the concurrency you wanted. asyncio.gather takes any number of coroutines, gives them all to the event loop together, waits for all of them to finish, and then returns the results packed up in order.
      

      Key points to underline:
      

        

      • gather returns a list of all the results, in the same order you passed them in
        • 

      • If any coroutine raises an exception, by default the whole gather raises it
        • 

      • You can pass in coroutines, or Task objects (covered below)
        • 

      

      gather is one of the most-used functions in asyncio. Whenever you need "run several at once", it should be your first thought (or TaskGroup, which we'll see later).

          Task: "sending out" a coroutine
          

          gather is great, but sometimes we want finer control: "send the job out first, let it run in the background, go do something else, and come back for the result when I need it".
          

          This "send it out" action is called a Task, created with asyncio.create_task():
          

          Python· Read with the text above
          import asyncio
import time


async def slow_job(name, delay):
    await asyncio.sleep(delay)
    return f'{name} done'


async def main():
    start = time.perf_counter()
    t1 = asyncio.create_task(slow_job('A', 0.3))
    t2 = asyncio.create_task(slow_job('B', 0.5))
    print('Both tasks have been sent out; main can do other things')
    await asyncio.sleep(0.1)
    print('Let me clock in first')
    r1 = await t1
    r2 = await t2
    cost = time.perf_counter() - start
    print(r1, r2)
    print(f'Took {cost:.2f} seconds')


asyncio.run(main())
          

          Output:
          

          Text
          Both tasks have been sent out; main can do other things
Let me clock in first
A done B done
Took 0.50 seconds
          

          Look at the time – 0.5 seconds, not 0.3 + 0.5 = 0.8 seconds. Why? create_task registers the coroutine with the event loop and starts it running straight away, without waiting for await. The line await t1 only says "I want this result now – if it's not ready, I'll wait here". While it waits, t2 is also running at the same time.
          

          So what's the difference between create_task and gather?
          

            

          • gather(coros...) sends them all out at once and collects them all at once – compact
            • 

          • create_task(coro) sends them out one by one; you can await each one separately, and cancel them – flexible
            • 

          

          A common combination in real code: use lots of create_task calls to send tasks out, and at the end use await asyncio.gather(*tasks) to collect them all at once. That way you get Task objects for fine control, and the convenience of gather.
          

          A small trap: passing coroutines vs Tasks to gather
          

          gather's arguments can be coroutine objects or Task objects. They look about the same, but there's a detail:
          

          Python· Read with the text above
          import asyncio


async def job(name):
    await asyncio.sleep(0.01)
    return name


async def main():
    coro = job('A')
    await asyncio.gather(coro, job('B'))


asyncio.run(main())
          

          Here job('A') and job('B') are both coroutine objects. gather automatically wraps them into Tasks and puts them in the event loop. So both ways work the same.
          

          Just be careful: a coroutine object can only be awaited once. You can't pass the same coro to gather twice:
          

          Python· Read with the text above
          import asyncio


async def job():
    return 1


async def main():
    coro = job()
    await asyncio.gather(coro, coro)


asyncio.run(main())
          

          This gives an error saying the coroutine was awaited more than once. To run the same coroutine function N times at once, write N calls, like [job() for _ in range(N)].

          asyncio.sleep vs time.sleep: the blocking trap
          

          There's one trap in async programming that's the most common of all: time.sleep freezes the entire event loop.
          

          Here's the bad example:
          

          Python· Read with the text above
          import asyncio
import time


async def task(name):
    time.sleep(0.5)
    return f'{name} done'


async def main():
    start = time.perf_counter()
    await asyncio.gather(task('A'), task('B'), task('C'))
    cost = time.perf_counter() - start
    print(f'Took {cost:.2f} seconds')


asyncio.run(main())
          

          Output:
          

          Text
          Took 1.50 seconds
          

          "Isn't this gather? Why is it 1.5 seconds again?"
          

          The reason is time.sleep. It's a synchronous blocking function – when called, it does not give the CPU back to the event loop. Writing time.sleep(0.5) is like telling the operating system "put this whole thread to sleep for 0.5 seconds". The whole event loop – meaning every coroutine – is frozen.
          

          asyncio.sleep(0.5) is completely different. It's a coroutine, and when used with await, it tells the event loop: "I'm going to sleep for 0.5 seconds – feel free to schedule others in the meantime."
          

          Remember this golden rule: inside an async function, every synchronous call that blocks must be swapped for an async version.
          

          


          
Synchronous (blocking – don't use)
Async (the replacement)

          
          


          
time.sleep(s)
await asyncio.sleep(s)

          

          
requests.get(url)
await httpx.AsyncClient().get(url)

          

          
Standard open(f).read()
the aiofiles library, or hand it to a thread pool

          
          

          

          What if you really have to call a synchronous blocking library? asyncio has an escape hatch – asyncio.to_thread – which hands the call to a thread pool:
          

          Python· Run it on your own computer
          import asyncio
import time


def blocking_call():
    time.sleep(0.5)
    return 'Sync task done'


async def main():
    start = time.perf_counter()
    r1, r2 = await asyncio.gather(
        asyncio.to_thread(blocking_call),
        asyncio.to_thread(blocking_call),
    )
    cost = time.perf_counter() - start
    print(r1, r2)
    print(f'Took {cost:.2f} seconds')


asyncio.run(main())
          

          Output:
          

          Text
          Sync task done Sync task done
Took 0.50 seconds
          

          asyncio.to_thread is a compromise: the event loop doesn't freeze, but you still pay the cost of threads. If there's a native async library you can use (like httpx, below), prefer that.

          Timeouts: wait_for and timeout
          

          If you write network requests, you'll have this worry: "What if the server on the other end never replies? Will my coroutine wait forever?"
          

          That's when you need a timeout. asyncio gives you two ways.
          

          First: asyncio.wait_for – the old way, which "wraps" the coroutine:
          

          Python· Read with the text above
          import asyncio


async def slow_job():
    await asyncio.sleep(2)
    return 'Finally done'


async def main():
    try:
        r = await asyncio.wait_for(slow_job(), timeout=0.5)
        print(r)
    except asyncio.TimeoutError:
        print('Timed out – not waiting any more')


asyncio.run(main())
          

          Output:
          

          Text
          Timed out – not waiting any more
          

          wait_for(coro, timeout=0.5) means "give this coroutine 0.5 seconds; if it takes longer, cancel it and raise TimeoutError".
          

          Second: asyncio.timeout (Python 3.11+) – the new way, using async with as a context:
          

          Python· Read with the text above
          import asyncio


async def slow_job():
    await asyncio.sleep(2)
    return 'Finally done'


async def main():
    try:
        async with asyncio.timeout(0.5):
            r = await slow_job()
            print(r)
    except TimeoutError:
        print('Timed out – not waiting any more')


asyncio.run(main())
          

          Output:
          

          Text
          Timed out – not waiting any more
          

          Same effect, but nicer to write – if you want a timeout on "this section", just wrap it in async with. The second way is especially handy for putting one timeout on several awaits. For new code, asyncio.timeout is recommended.
          

          Note a small change: since 3.11, asyncio.TimeoutError is the built-in TimeoutError, so except TimeoutError catches it too – no need to write asyncio.TimeoutError.
          

          Teaching 11 / 17· read
          

          Cancelling: Task.cancel()
          

          A timeout is really "automatic cancelling". Cancelling by hand is easy too:
          

          Python· Read with the text above
          import asyncio


async def long_running():
    try:
        for i in range(10):
            print(f'Still running {i}')
            await asyncio.sleep(0.05)
    except asyncio.CancelledError:
        print('I was cancelled – cleaning up')
        raise


async def main():
    t = asyncio.create_task(long_running())
    await asyncio.sleep(0.12)
    t.cancel()
    try:
        await t
    except asyncio.CancelledError:
        print('The task really was cancelled')


asyncio.run(main())
          

          Output:
          

          Text
          Still running 0
Still running 1
Still running 2
I was cancelled – cleaning up
The task really was cancelled
          

          Task.cancel() raises a CancelledError inside the coroutine. The coroutine can catch it to clean up, but I strongly recommend raise-ing it again after cleaning up, so the outside knows the task really was cancelled. Quietly swallowing CancelledError is another very sneaky trap.
          

          Teaching 12 / 17· read
          

          TaskGroup: the upgraded gather from 3.11
          

          gather works well, so why did Python 3.11 add TaskGroup?
          

          Let's look at an awkward situation with gather. Three tasks; one raises an error. What should happen to the other two?
          

          Python· Read with the text above
          import asyncio


async def good(name, delay):
    await asyncio.sleep(delay)
    return f'{name} ok'


async def bad():
    await asyncio.sleep(0.1)
    raise ValueError('Broken')


async def main():
    try:
        await asyncio.gather(good('A', 0.5), bad(), good('B', 0.5))
    except ValueError as e:
        print('main caught', e)


asyncio.run(main())
          

          The output is roughly:
          

          Text
          main caught Broken
          

          Looks fine. But think – what about A and B, the two 0.5-second tasks? They're actually still quietly running in the background. gather's default behaviour is "if one fails, raise the exception outwards, and let the other tasks keep running in the event loop". If A is writing a file and B is sending a request, they'll run to the end (and maybe raise errors too) before stopping. This "walk off and leave others working behind your back" behaviour isn't safe.
          

          TaskGroup solves this:
          

          Python· Read with the text above
          import asyncio


async def good(name, delay):
    await asyncio.sleep(delay)
    return f'{name} ok'


async def bad():
    await asyncio.sleep(0.1)
    raise ValueError('Broken')


async def main():
    try:
        async with asyncio.TaskGroup() as tg:
            t_a = tg.create_task(good('A', 0.5))
            t_bad = tg.create_task(bad())
            t_b = tg.create_task(good('B', 0.5))
    except* ValueError as eg:
        print('TaskGroup caught an exception group:', eg.exceptions)


asyncio.run(main())
          

          The output is roughly:
          

          Text
          TaskGroup caught an exception group: (ValueError('Broken'),)
          

          The advantages of TaskGroup:
          

            

          • It automatically waits for everything to finish: before async with exits, every task is definitely done
            • 

          • One fails, all are cancelled: after bad raises an error, A and B are cancelled straight away – they don't keep running in the background
            • 

          • Exception groups (ExceptionGroup): when several tasks fail at once, all the exceptions are packed into one ExceptionGroup, which you catch with the except* syntax
            • 

          

          In new code, use TaskGroup whenever you can – it's safer and more controllable than gather. gather suits simple situations with one or two tasks, where you don't care much about cancelling.
          

          

          Don't panic about the strange except* syntax – it's the special syntax for "exception groups" from PEP 654, added in Python 3.11. Simply put, it means "pick out one type of exception from an exception group and catch it". If you don't need it yet, that's fine – just know it exists.
          

          

          Teaching 13 / 17· read
          

          async with and async for
          

          In the asyncio.timeout(0.5) example, you saw async with. That's an asynchronous context manager – its __enter__ and __exit__ are replaced by async versions called __aenter__ and __aexit__.
          

          When do you need async with? The most common case is network clients:
          

          Python· Run it on your own computer
          import asyncio
import httpx


async def main():
    async with httpx.AsyncClient() as client:
        r = await client.get('https://httpbin.org/get')
        print(r.status_code)


asyncio.run(main())
          

          It's async with because "closing this connection pool" might itself involve I/O, so it can't be a normal synchronous __exit__.
          

          Similarly, there are asynchronous iterators – async for. For example, some libraries support streaming data:
          

          Python· Run it on your own computer
          import httpx
import asyncio


async def main():
    async with httpx.AsyncClient() as client:
        async with client.stream('GET', 'https://httpbin.org/stream/3') as resp:
            async for line in resp.aiter_lines():
                print('line:', line)


asyncio.run(main())
          

          async for line in resp.aiter_lines() means: each time a line is read (which may mean waiting for the network), give it to me, then keep waiting for the next line. A normal for can't do this – only async for can.
          

          Remember the pattern:
          

            

          • Normal objects and contexts → with, for
            • 

          • Objects involving I/O and coroutines → async with, async for
            • 

          

          Teaching 14 / 17· read
          

          When to use async, and when not to
          

          After all that, let's get back to the basic question: what situations suit async?
          

          asyncio's strength is I/O-bound work – where the program spends most of its time waiting: for the network, the disk, a database, or user input. In these situations, the waiting can overlap, so async lets one thread wait for countless things at once, with immediate results.
          

          asyncio's weakness is CPU-bound work – where the program spends most of its time calculating: encryption, image processing, machine-learning inference. There's no "waiting" to take advantage of – the CPU is busy all the time – so async can't help. One thread can only use one core, while the other seven cores sit idle.
          

          A comparison table:
          

          


          
Situation
What to use

          
          


          
Fetching 100 URLs
asyncio + httpx

          

          
Reading and writing lots of files at once
asyncio + aiofiles

          

          
A high-traffic web service (one machine handling thousands of connections)
asyncio + FastAPI / aiohttp

          

          
Video conversion, big matrix calculations
multiprocessing or C extensions

          

          
Sorting huge amounts of data locally
Multiple processes + splitting into chunks

          

          
A bit of I/O and a bit of CPU at the same time
An async main framework + asyncio.to_thread or run_in_executor

          
          

          

          Remember it like this: async is for "waiting", not for "calculating".
          

          Teaching 15 / 17· read
          

          In practice: 100 URLs, one-by-one vs together
          

          Theory's done. Time for a real comparison, to see how much faster asyncio + httpx really is than requests.
          

          First, install httpx:
          

          Text
          pip install httpx
          

          The code below runs two versions: a synchronous one using httpx's synchronous client (which behaves like requests), and a concurrent one using httpx.AsyncClient with asyncio.gather. Both make 50 requests, and we compare the total time:
          

          Python· Run it on your own computer
          import asyncio
import time
import httpx

URLS = [f'https://httpbin.org/delay/1?i={i}' for i in range(50)]


def fetch_sync():
    with httpx.Client(timeout=30) as client:
        return [client.get(u).status_code for u in URLS]


async def fetch_async():
    async with httpx.AsyncClient(timeout=30) as client:
        tasks = [client.get(u) for u in URLS]
        responses = await asyncio.gather(*tasks)
        return [r.status_code for r in responses]


def main():
    start = time.perf_counter()
    sync_codes = fetch_sync()
    sync_cost = time.perf_counter() - start
    print(f'Synchronous, 50 requests: {sync_cost:.2f} seconds, all 200 = {all(c == 200 for c in sync_codes)}')

    start = time.perf_counter()
    async_codes = asyncio.run(fetch_async())
    async_cost = time.perf_counter() - start
    print(f'Concurrent, 50 requests: {async_cost:.2f} seconds, all 200 = {all(c == 200 for c in async_codes)}')

    print(f'Speed-up: {sync_cost / async_cost:.1f} times')


main()
          

          The httpbin.org/delay/1 endpoint deliberately waits 1 second before replying, so we can see the difference. One run looks roughly like this:
          

          Text
          Synchronous, 50 requests: 53.21 seconds, all 200 = True
Concurrent, 50 requests: 1.62 seconds, all 200 = True
Speed-up: 32.8 times
          

          50 requests, squeezed from 53 seconds down to under 2 – that's the power of asyncio + httpx. You can change this code to the URL list you care about – fetching blog posts, calling internal APIs, pinging services in bulk – and see results straight away.
          

          A few things to watch out for in practice:
          

            

          1. Give httpx.AsyncClient a timeout, or it will hang forever when it meets a "zombie" service
            2. 

          2. Don't blindly run thousands at once – the server on the other end might not cope, and could rate-limit you or even block your IP. Usually you use asyncio.Semaphore to limit the maximum number running at once:
            3. 

          

          Python· Run it on your own computer
          import asyncio
import httpx


async def fetch_one(client, sem, url):
    async with sem:
        r = await client.get(url)
        return r.status_code


async def fetch_many(urls, max_concurrency=10):
    sem = asyncio.Semaphore(max_concurrency)
    async with httpx.AsyncClient(timeout=30) as client:
        tasks = [fetch_one(client, sem, u) for u in urls]
        return await asyncio.gather(*tasks)


urls = [f'https://httpbin.org/delay/1?i={i}' for i in range(100)]
codes = asyncio.run(fetch_many(urls, max_concurrency=10))
print(len(codes))
          

          Semaphore(10) means "at most 10 tasks may come in at once" – the 11th has to queue. That way you get the benefit of running things together, without knocking the other server over.
          

            

          1. Error handling: by default, gather raises as soon as one fails, and you lose the whole batch. If you're OK with "partial failure", pass return_exceptions=True, so gather returns exceptions as results:
            2. 

          

          Python· Run it on your own computer
          import asyncio
import httpx


async def fetch(client, url):
    r = await client.get(url, timeout=5)
    r.raise_for_status()
    return r.status_code


async def main():
    urls = ['https://httpbin.org/get', 'https://httpbin.org/status/500', 'https://httpbin.org/get']
    async with httpx.AsyncClient() as client:
        results = await asyncio.gather(
            *(fetch(client, u) for u in urls),
            return_exceptions=True,
        )
    for u, r in zip(urls, results):
        if isinstance(r, Exception):
            print(f'{u} failed: {r}')
        else:
            print(f'{u} succeeded: {r}')


asyncio.run(main())
          

          This is especially useful when scraping lots of data – it keeps going even if 99 succeed and 1 fails.
          

          Teaching 16 / 17· read
          

          Summary
          

          By now, you should have a complete feel for asyncio. Let's quickly look back at the path we took:
          

            

          • The problem: 100 network requests one-by-one are painfully slow, and threads are heavy and messy
            • 

          • Gut-feeling comparison: 3 tasks in 1 second vs 3 seconds – the difference comes from overlapping the "waiting"
            • 

          • The basic trio: async def defines a coroutine function, await waits for a result, asyncio.run() enters the event loop
            • 

          • Coroutine objects: not awaiting one is like not writing it – the most common trap
            • 

          • Concurrency tools: asyncio.gather waits for several at once; asyncio.create_task sends a task out
            • 

          • The blocking trap: time.sleep freezes the whole event loop – use asyncio.sleep instead
            • 

          • Timeouts and cancelling: asyncio.wait_for (old way), asyncio.timeout (new way), Task.cancel (by hand)
            • 

          • TaskGroup: the safer upgrade from 3.11 – waits for everything automatically, cancels everything on error
            • 

          • Async contexts: async with and async for are standard for I/O situations
            • 

          • When to use it: only use async for I/O-bound work; for CPU-bound work, stick with multiple processes
            • 

          • In practice: asyncio + httpx fetching 50 URLs – a speed-up of over 30 times you can see with your own eyes
            • 

          

          asyncio's syntax looks fancy, but really it just adds scheduling to "waiting". When you write code, ask yourself: "Is this step waiting for something?" If so, try an await – you might be pleasantly surprised.
          

          In the next article, we'll talk about something else that's fun. First, run all the code in this chapter yourself, and get a feel for what "one thread waiting for a hundred things at once" is like.
          

          Teaching 17 / 17· read
          

          Look at the waiting and the results – don't compare seconds yet
          

          If you only look at "how many seconds faster" in async examples, it's easy to miss what's actually being waited for. Below, each task returns a number of minutes. Focus first on how the tasks are created, waited for, and in what order the results come back:
          

          Python· Runs on this page
          import asyncio


async def read_minutes(value):
    await asyncio.sleep(0)
    return value


async def main():
    tasks = [read_minutes(15), read_minutes(10)]
    results = await asyncio.gather(*tasks)
    print(results)


asyncio.run(main())
          

          Output:
          

          Text
          [15, 10]
          

          read_minutes(15) creates a coroutine object. gather waits for these jobs to finish and arranges the results by the position you passed them in. It's not "whoever finishes first goes first in the results list".
          

          Change tasks to an empty list yourself – the result should be []. Then add read_minutes(0) – you should get [15, 10, 0]. This checks whether we understand the results better than using a tiny delay to "prove" speed.
          

          Local scripts start with asyncio.run(). If an interactive environment already has an event loop running, follow that environment's way of running things. The learning website has already adapted to this, so you can run the existing exercises here. Also, async doesn't automatically turn pure calculation into parallel calculation. Before choosing it, check whether your task is actually waiting for work it can step aside from.
