# Threads and Processes #

**Threads** and **processes** are operating system terms. Simply put, every application has its own process.

The operating system gives each process some resources to run with, like memory space.

Inside a process, you can create threads. Threads share the process's memory space, and the operating system schedules them so they can work in parallel.

We all know modern operating systems like Mac OS X, UNIX, Linux and Windows can run many tasks at the same time.

For example, you might be browsing the web, listening to music while coding, and writing a blog post in Markdown, all at once. That's **multitasking** – at least 3 tasks running at the same time.

And lots of other tasks are quietly running in the background too – they just don't show on your desktop.

To the operating system, one task is one **process**. Opening a browser starts a browser process, opening PyCharm starts a PyCharm process, and opening a Markdown editor starts a Markdown process.

These days, multi-core CPUs are very common.

But a CPU runs code one instruction after another. So you might wonder: how does a **single-core** CPU run many tasks at once?

Actually, the operating system makes the tasks **take turns**. Task 1 runs for 0.01 seconds, then it switches to task 2, which runs for 0.01 seconds, then task 3 for 0.01 seconds… and so on, again and again.

On the surface, each task takes turns. But the CPU is so fast that we can't see or feel it – it seems like all the tasks are running at the same time.

Truly running tasks in parallel can only happen on a multi-core CPU. But because there are far more tasks than CPU cores, the operating system still automatically schedules lots of tasks to take turns on each core.


Some processes don't just do one thing. A browser, for example, can play video, play audio, show articles, let you edit text and so on. These are all **sub-tasks** inside the browser process. To do several things at once inside one process, you need to run several "sub-tasks" at the same time. We call these sub-tasks inside a process **threads**.

Every process does at least one thing, so every process has at least one thread.

Of course, a process can also have many threads, and they can run at the same time. Multiple threads work the same way as multiple processes: the operating system switches quickly between threads, letting each one run briefly in turn, so they look like they're running at the same time.

So in Python, how do we run several tasks at once?

There are two options:

One is to start several processes. Each process has only one thread, but together the processes can do several tasks.

The other is to start one process, and start several threads inside it. Then the threads can do several tasks together.

There's also a third option: start several processes, and start several threads in each one. That runs even more tasks at once, but it's much more complicated, so it's rarely used in practice.

To sum up, there are 3 ways to do multitasking:

* Multi-process
* Multi-thread
* Multi-process + multi-thread

When you run several tasks at once, they usually aren't completely separate. They need to communicate and coordinate. Sometimes task 1 has to pause and wait for task 2 to finish. Sometimes task 3 and task 4 can't run at the same time. So multi-process and multi-thread programs are much more complicated than the single-process, single-thread programs we've written so far.

Because they're complicated and hard to debug, we don't want to write multitasking code unless we have to.

But very often, we really can't do without it.

Think about watching a movie on a computer. One thread must play the video, and another must play the audio. With only one thread, you'd have to play all the video first and then all the audio, or the other way round. Clearly that won't work.




## First, check which tasks can be done on their own

Before talking about threads and processes, let's break the task down clearly: does the calculation for each record depend on the others? Do the results need to be shown in the same order as the input, or can each one be shown as soon as it's done? These choices affect how you write the code.

The thread pool example below is for Python on your own computer. The Python that runs in a browser doesn't have the same thread and process abilities as your computer, so please run this one in a local terminal.

```python no-run
from concurrent.futures import ThreadPoolExecutor


def double_minutes(minutes):
    return minutes * 2


with ThreadPoolExecutor(max_workers=2) as pool:
    results = list(pool.map(double_minutes, [15, 0, 10]))
print(results)
```

Output:

```text
[30, 0, 20]
```

The results from this `map` come out in the same order as the input. That doesn't mean the tasks themselves ran strictly in that order. Try changing the input to an empty list – the result should be `[]`.

This task is too small. We're only using a thread pool here to see how it works – it can't prove that threads are always faster. To compare speed, you must keep the amount of work, the environment and the way you measure the same. When people talk about the **GIL**, they also need to say which interpreter and build they mean – you can't apply a conclusion about one CPython setup to every Python environment. First learn to tell apart **computing**, **waiting** and **shared state**, then choose your tool.
