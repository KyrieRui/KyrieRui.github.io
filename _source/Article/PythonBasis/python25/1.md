# pytest: the testing framework that runs 100 test cases in 30 seconds

When you write code, do questions like these often bother you?

"I just changed one line of this function – will it break something somewhere else?"

"The boss wants a new feature, but I'm scared to touch this mess of code. What if I break it and the live app crashes?"

"A teammate sent me a pull request. It looks fine, but I'm not confident."

Experienced programmers know this fear of "not daring to touch the code". The first time Brother Shui maintained an old 3,000-line project, every single line he changed made him nervous, because there were no tests – nobody knew whether a change would break something. In the end, he could only click through a few pages by hand and build a few requests to check, spending ten minutes before daring to commit. Painfully slow.

"Is my change OK?" The answer to this question is always: **run the tests and find out.**

So how much trouble is writing tests? Lots of people get a headache when they hear "write tests" – it sounds like extra work. But in the Python world, there's a tool that runs 100 test cases in 30 seconds, where a test takes just three lines of code. It's `pytest`.

`pytest` is the standard for testing in Python. `Django`, `FastAPI`, `Pandas`, `NumPy`, `SQLAlchemy`, `Pydantic`, `Requests`, `httpx` – almost every Python project you can name uses it to run tests. It has 12k+ stars on GitHub and hundreds of millions of downloads a month on PyPI.

In this chapter, we'll take `pytest` from zero to ready-to-use. After it, you should be able to:

1. Write your first `pytest` test, run it, and see a green PASS
2. Understand what the `tests/` folder is doing in other people's projects
3. Use core tools like `fixture`, parametrisation, `tmp_path` and `monkeypatch` to write tests that are short and strong
4. Add coverage to your project, so you know which lines haven't been tested yet
5. Connect tests to `CI`, so they run automatically when you submit a pull request

Let's go.



## Your first test

Let's feel how simple `pytest` is. Make a new folder:

```bash
mkdir test-demo
cd test-demo
uv init
uv add --dev pytest
```

Write a perfectly ordinary Python file, `mymath.py`:

```python
def add(a, b):
    return a + b


def divide(a, b):
    if b == 0:
        raise ValueError("Cannot divide by 0")
    return a / b
```

Then write a test file, `test_mymath.py`:

<!-- skip-ci -->
```python
from mymath import add, divide


def test_add():
    assert add(2, 3) == 5


def test_add_negative():
    assert add(-1, 1) == 0


def test_divide():
    assert divide(10, 2) == 5
```

Notice three details: the file name starts with `test_`, the function names start with `test_`, and checks use Python's built-in `assert` keyword. That's all.

Run it:

```bash
uv run pytest
```

The output looks roughly like this:

```
============================= test session starts ==============================
platform darwin -- Python 3.13.1, pytest-8.3.4, pluggy-1.5.0
rootdir: /Users/walter/test-demo
collected 3 items

test_mymath.py ...                                                       [100%]

============================== 3 passed in 0.01s ===============================
```

The three green dots `...` mean all three tests passed. Done in 0.01 seconds.

Simpler than you expected, right?

Now deliberately break the `add` function – say, change it to `return a + b + 1` – and run it again:

```
test_mymath.py FF.                                                       [100%]

=================================== FAILURES ===================================
___________________________________ test_add ___________________________________

    def test_add():
>       assert add(2, 3) == 5
E       assert 6 == 5
E        +  where 6 = add(2, 3)

test_mymath.py:4: AssertionError
```

`pytest` tells you straight away: which line's assert failed, that the left side is `6` and the right side is `5`, and where the `6` came from (worked out by `add(2, 3)`). Clear at a glance. This is `pytest`'s "assert rewriting" magic – we'll look at it properly later.



## pytest vs unittest – why choose pytest?

You might ask: "Doesn't Python already come with the `unittest` standard library? Why install `pytest`?"

Good question. Let's compare the same test written both ways.

The `unittest` way:

<!-- skip-ci -->
```python
import unittest


class TestMyMath(unittest.TestCase):
    def test_add(self):
        self.assertEqual(add(2, 3), 5)

    def test_divide(self):
        self.assertEqual(divide(10, 2), 5)


if __name__ == "__main__":
    unittest.main()
```

The `pytest` way:

<!-- skip-ci -->
```python
def test_add():
    assert add(2, 3) == 5


def test_divide():
    assert divide(10, 2) == 5
```

What's the difference?

1. **No need to inherit from `TestCase`.** `pytest` uses normal functions – one less layer of class
2. **No need to remember lots of assert method names.** `unittest` has `assertEqual`, `assertNotEqual`, `assertTrue`, `assertFalse`, `assertIn`, `assertIsInstance`, `assertGreater`, `assertRaises`… dozens of methods to remember. `pytest` just uses one `assert`
3. **No need to write `__main__`.** Just run the `pytest` command

The `unittest` style was actually copied from Java's `JUnit` – the "class + methods" approach comes from OOP thinking. In a dynamic language like Python, things you can do with normal functions don't need to be that heavy. So after 2010, the Python world gradually moved completely over to `pytest`.

Can you still use `unittest`? Yes. `pytest` is **backwards-compatible** with `unittest` – it can run your `unittest` test cases directly. So moving an old project from `unittest` is smooth – don't change a single line of code, just switch the command from `python -m unittest` to `pytest`. For new projects, I suggest using the `pytest` style throughout.

Remember this: **if anyone in the Python world still recommends `unittest` for a new project today, their information is either ten years old or they haven't kept up.** Just use `pytest`.



## Assert rewriting – the most magical part of pytest

We just saw that `pytest`'s failure messages are really detailed:

```
>       assert add(2, 3) == 5
E       assert 6 == 5
E        +  where 6 = add(2, 3)
```

Normally, `assert` is quite "weak" – when it fails, it just raises `AssertionError` with no hints at all. Python's built-in `assert` looks like this when it fails:

<!-- skip-ci -->
```python
>>> x = 6
>>> assert x == 5
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
AssertionError
```

It only tells you "the assert failed". What was on the left and the right? No idea.

So how does `pytest` get all that information?

The answer is **assertion rewriting**. Before `pytest` loads a test file, it **rewrites** the `assert` statements in the code – turning a simple `assert a == b` into "first work out `a` and `b` and save them, and if the assert fails, print them". You don't need to write any extra code – it works out of the box.

More complicated asserts give detailed information too:

```python
def test_list_equal():
    a = [1, 2, 3, 4, 5]
    b = [1, 2, 3, 4, 6]
    assert a == b
```

Run it, and `pytest` outputs:

```
>       assert a == b
E       assert [1, 2, 3, 4, 5] == [1, 2, 3, 4, 6]
E         At index 4 diff: 5 != 6
```

It even tells you "at position 4, 5 is different from 6". Dictionaries, strings and sets all get a similar "smart diff".

Don't you think this is even friendlier than `unittest.TestCase.assertEqual`? Exactly – years ago, `unittest`-style tools liked methods like `assertEqual` precisely because "a bare `assert` gives too little information". `pytest` solved this problem completely using metaprogramming.

So the `pytest` world's recommendation is just one sentence: **use `assert` for every check – never `assertXXX`.**

Let's look at some common asserts:

<!-- skip-ci -->
```python
# Equal
assert x == 5
assert name == "Two Drops"

# Not equal
assert x != 0

# Contains
assert "Python" in "I love Python"
assert 3 in [1, 2, 3]

# True/False
assert is_valid is True
assert result is None

# Size of numbers
assert age >= 18
assert 0 < score < 100

# Type
assert isinstance(x, int)
```

The key is "write ordinary Python expressions". Use `==` where you can use `==`, use `in` where you can use `in` – no special assert functions to remember. This is the nicest thing about writing `pytest` tests.



## Test discovery – how pytest finds your tests

Did you notice something just now? When we ran the `pytest` command, we **didn't say which file to run**, but it found `test_mymath.py` automatically. How?

`pytest` has default **test discovery** rules. Starting from the current folder, it scans all folders recursively, looking for things that match these rules:

1. **Test files**: `test_*.py` or `*_test.py`
2. **Test classes**: classes starting with `Test` (that have no `__init__` method)
3. **Test functions**: functions or methods starting with `test_`

Some examples:

```
my-project/
├── src/
│   └── mymath.py
└── tests/
    ├── test_mymath.py        # Found automatically ✓
    ├── test_helper.py        # Found automatically ✓
    ├── helper_test.py        # Found automatically ✓
    └── notes.py              # Not recognised ✗
```

Inside a test file:

```python
def test_add():           # Found automatically ✓
    pass


def helper():             # Not recognised ✗
    pass


class TestUser:           # Found automatically ✓
    def test_create(self):    # Found automatically ✓
        pass

    def helper(self):     # Not recognised ✗
        pass


class UserTest:           # Not recognised ✗ (doesn't start with Test)
    pass
```

When writing tests, the usual folder structure is:

```
my-project/
├── pyproject.toml
├── src/
│   └── mypackage/
│       ├── __init__.py
│       ├── core.py
│       └── utils.py
└── tests/
    ├── test_core.py
    └── test_utils.py
```

Source code goes in `src/`, tests go in `tests/`, and **each test file matches the file it tests**. `core.py` goes with `test_core.py`, `utils.py` goes with `test_utils.py`. That way, when a newcomer sees `core.py` and wants to find its tests, they find them at a glance.

How do you use the `pytest` command? Some common ways:

```bash
# Run all tests
pytest

# Run only one file
pytest tests/test_core.py

# Run only one test function
pytest tests/test_core.py::test_add

# Run only one method of one class
pytest tests/test_core.py::TestUser::test_create

# Filter by keyword (function name contains a word)
pytest -k "add"
pytest -k "add or divide"
pytest -k "not slow"

# Show more detailed output
pytest -v

# Stop at the first failure
pytest -x

# Show print output (pytest captures it by default)
pytest -s
```

`-v` lists the name of every test, with PASSED for the ones that pass:

```
test_mymath.py::test_add PASSED
test_mymath.py::test_add_negative PASSED
test_mymath.py::test_divide PASSED
```

`-x` is really useful when debugging – if a pile of tests are all failing, rather than running them all and then looking, stop at the first failure and look at that.

`-s` lets `print` output go straight to the terminal, handy for temporarily printing variable values.



## fixture – dependency injection for tests

Once you've written lots of tests, you'll notice a problem: **many tests need some "preparation work"**.

For example:

- To test database features, every test first needs a temporary database connection
- To test an API, every test first needs to start an HTTP client
- To test file operations, every test first needs a temporary folder

If you write it the "simplest" way:

```python
def test_user_create():
    db = create_test_db()
    db.connect()
    try:
        user = User(name="walter")
        db.save(user)
        assert db.get_user("walter").name == "walter"
    finally:
        db.close()


def test_user_delete():
    db = create_test_db()
    db.connect()
    try:
        user = User(name="walter")
        db.save(user)
        db.delete_user("walter")
        assert db.get_user("walter") is None
    finally:
        db.close()
```

Every test repeats "create the database → connect → close it in finally". Ugly.

`pytest`'s solution is called a **fixture**. It pulls the "preparation work" out into a function with the `@pytest.fixture` decorator:

<!-- skip-ci -->
```python
import pytest


@pytest.fixture
def db():
    """Provide a clean test database connection."""
    conn = create_test_db()
    conn.connect()
    yield conn         # Hand conn to the test function
    conn.close()       # Clean up after the test finishes


def test_user_create(db):
    user = User(name="walter")
    db.save(user)
    assert db.get_user("walter").name == "walter"


def test_user_delete(db):
    user = User(name="walter")
    db.save(user)
    db.delete_user("walter")
    assert db.get_user("walter") is None
```

Do you see the trick?

1. Write a `db` fixture that `yield`s a connection object
2. The test function **lists `db` as a parameter**, and `pytest` automatically passes in the value the fixture worked out
3. After the test finishes, the clean-up code after `yield` runs automatically

A bit like "dependency injection" in Spring/Django, isn't it? Whatever you need, write it as a parameter name, and `pytest` prepares it for you. **The test function only cares about "what am I testing", not "how do I prepare the data"** – the concerns are completely separated.

How else can you write fixtures? The most common ways:

**Prepare only, no clean-up**: just `return` – no need for `yield`.

<!-- skip-ci -->
```python
@pytest.fixture
def sample_user():
    return User(name="walter", age=28)


def test_greet(sample_user):
    assert greet(sample_user) == "Hello, walter!"
```

**Fixtures can depend on each other.** For example, `db` depends on `config`:

<!-- skip-ci -->
```python
@pytest.fixture
def config():
    return {"host": "localhost", "port": 5432}


@pytest.fixture
def db(config):                         # Note: a parameter here too
    conn = connect(config["host"], config["port"])
    yield conn
    conn.close()


def test_query(db):
    assert db.ping() is True
```

`pytest` works out the whole chain of dependencies by itself: it runs `config` first, uses `config`'s result to call `db`, and finally feeds `db` to the test.



## fixture scope – when to create, when to destroy

Here's a real problem –

"I have a fixture that creates a database connection, and creating it takes 1 second. I have 100 tests that use it. If every test creates it again, that's 100 seconds just creating connections. Can I create it once and share it between all the tests?"

`pytest`'s answer is the fixture's `scope` parameter. It has four levels:

- `function` (the default): created before each test function, destroyed after it
- `class`: created before each test class, destroyed after it
- `module`: created before each test file (module), destroyed after it
- `session`: created just once for the whole `pytest` run, from start to finish

For example, make the database connection `session`-level:

<!-- skip-ci -->
```python
@pytest.fixture(scope="session")
def db():
    conn = create_test_db()
    conn.connect()
    yield conn
    conn.close()
```

Now however many tests you run, `conn` is created once and closed once.

So which scope should you use when? Here's a rule of thumb –

- **If tests must be independent of each other** (each test starts from a clean state): use `function`
- **If creating it is very costly** (connecting to a database, starting a container, loading a big model): use `module` or `session` – but remember to **clean up state by hand** after each test

Here's a mixed example:

<!-- skip-ci -->
```python
@pytest.fixture(scope="session")
def db_connection():
    """The whole session shares one connection – creating it once is enough."""
    conn = connect_to_db()
    yield conn
    conn.close()


@pytest.fixture(scope="function")
def db(db_connection):
    """Each test gets a clean transaction, rolled back afterwards."""
    txn = db_connection.begin_transaction()
    yield txn
    txn.rollback()


def test_create_user(db):
    db.execute("INSERT INTO users ...")
    # After the test, the transaction is rolled back automatically, so the next test still sees a clean database
```

"Shared connection, separate transactions" is a very common pattern in database testing. The `session`-level connection keeps it fast, and the `function`-level transaction keeps tests separate.



## Built-in fixtures – some life-savers that come with pytest

Before writing your own fixtures, know that `pytest` already comes with dozens of common ones. Here are the most useful.

### tmp_path – a temporary folder

Tests often need to work with files – reading, writing, deleting. If you just create files anywhere on your disk, you'll have rubbish everywhere after testing. If you manage it yourself with `tempfile`, you need lots of `setup/teardown` code.

`pytest`'s `tmp_path` fixture just gives you a temporary folder, cleaned up automatically after the test.

```python
def test_write_and_read(tmp_path):
    file = tmp_path / "hello.txt"
    file.write_text("Two Drops", encoding="utf-8")

    assert file.exists()
    assert file.read_text(encoding="utf-8") == "Two Drops"
```

`tmp_path` is a `pathlib.Path` object, so you can join paths with `/`. Remember `pathlib` from python18? Here it all comes together perfectly.

Each test gets a **different** `tmp_path` folder, so they don't interfere with each other. By default, `pytest` keeps the temporary folders from the last 3 test runs under `/tmp/pytest-of-<user>/`. If a test fails, you can look in there to see what the files look like – handy for debugging.

### monkeypatch – temporarily changing the environment

Tests often need to "change some global state" – change environment variables, replace a function, change an object's attribute. And after the test, you must change it back, or it affects the next test.

The `monkeypatch` fixture does exactly this. It changes things temporarily and restores them automatically after the test.

```python
def test_with_env(monkeypatch):
    monkeypatch.setenv("API_KEY", "test-key-123")
    assert get_api_key() == "test-key-123"
    # After the test, API_KEY is restored automatically


def test_replace_function(monkeypatch):
    def fake_get_time():
        return 1700000000
    monkeypatch.setattr("mymodule.time.time", fake_get_time)
    # After the test, time.time is restored automatically


def test_chdir(monkeypatch, tmp_path):
    monkeypatch.chdir(tmp_path)
    # The current folder temporarily changes to tmp_path, and changes back after the test
```

Common methods:

- `monkeypatch.setenv(name, value)`: set an environment variable
- `monkeypatch.delenv(name)`: delete an environment variable
- `monkeypatch.setattr(target, value)`: replace an object's attribute
- `monkeypatch.delattr(target)`: delete an attribute
- `monkeypatch.chdir(path)`: change the current folder

When testing code with outside dependencies, `monkeypatch` is your first choice – no need to really connect to a database or really send HTTP requests. Just fake a return value.

### capsys – capturing stdout/stderr

How do you test that some code `print`s the right thing? That's what `capsys` is for.

```python
def greet(name):
    print(f"Hello, {name}!")


def test_greet(capsys):
    greet("walter")
    captured = capsys.readouterr()
    assert captured.out == "Hello, walter!\n"
    assert captured.err == ""
```

`capsys.readouterr()` returns an object where `.out` is stdout and `.err` is stderr. After reading, the buffer is emptied, so calling it again gives only new output.

Similar fixtures:

- `capfd`: captures output at the file descriptor level (including output from C extensions and child processes)
- `caplog`: captures output from the `logging` module

`capsys` is the easiest way to test "does this function print correctly?".



## Parametrising – running the same test with several sets of data

Do you often write tests like this?

```python
def test_add_positive():
    assert add(2, 3) == 5


def test_add_negative():
    assert add(-1, -2) == -3


def test_add_zero():
    assert add(0, 0) == 0


def test_add_mixed():
    assert add(-5, 10) == 5
```

Testing one addition function with four functions whose bodies are almost identical – only the data differs. Repetition, repetition.

`pytest`'s **parametrisation** (`@pytest.mark.parametrize`) squeezes them into one:

<!-- skip-ci -->
```python
import pytest


@pytest.mark.parametrize("a, b, expected", [
    (2, 3, 5),
    (-1, -2, -3),
    (0, 0, 0),
    (-5, 10, 5),
])
def test_add(a, b, expected):
    assert add(a, b) == expected
```

When it runs, `pytest` treats it as 4 separate tests:

```
test_mymath.py::test_add[2-3-5] PASSED
test_mymath.py::test_add[-1--2--3] PASSED
test_mymath.py::test_add[0-0-0] PASSED
test_mymath.py::test_add[-5-10-5] PASSED
```

You can see at a glance which sets passed and which failed.

Two key points about the parametrise syntax:

1. The first argument is a string listing **the parameter names the test function takes**, separated by commas
2. The second argument is a list. Each item is one set of test data (in the same order as the names in the first string)

You can also give each set a name, to make the output easier to read:

<!-- skip-ci -->
```python
@pytest.mark.parametrize("a, b, expected", [
    pytest.param(2, 3, 5, id="add-positives"),
    pytest.param(-1, -2, -3, id="add-negatives"),
    pytest.param(0, 0, 0, id="add-zeros"),
])
def test_add(a, b, expected):
    assert add(a, b) == expected
```

Run it:

```
test_mymath.py::test_add[add-positives] PASSED
test_mymath.py::test_add[add-negatives] PASSED
test_mymath.py::test_add[add-zeros] PASSED
```

Naming your cases makes the output much easier to understand.

You can also stack parametrisations – several `@pytest.mark.parametrize` decorators on top of each other automatically produce every combination:

<!-- skip-ci -->
```python
@pytest.mark.parametrize("x", [1, 2, 3])
@pytest.mark.parametrize("y", [10, 20])
def test_combo(x, y):
    print(x, y)
```

This runs `3 × 2 = 6` cases in total: `(1,10) (1,20) (2,10) (2,20) (3,10) (3,20)`.

Parametrisation is one of `pytest`'s killer features. **Use it whenever you can – don't copy and paste lots of similar tests.**



## Asserting exceptions – testing "does it raise an error?"

When writing code, we often want a function to raise an exception for bad input – dividing by 0, an empty string, a negative age.

So how do you test "this function **should** raise a `ValueError`"? Just writing `try/except` isn't enough – if the function doesn't raise anything, the test still passes, but logically, **not** raising is exactly the bug.

`pytest` provides the `pytest.raises` context manager:

<!-- skip-ci -->
```python
import pytest


def test_divide_by_zero():
    with pytest.raises(ValueError):
        divide(10, 0)
```

The code inside `with pytest.raises(ValueError):` **must raise `ValueError`**. If it raises nothing, or a different exception, the test fails.

If you also want to check the content of the exception (like the error message):

```python
def test_divide_by_zero_message():
    with pytest.raises(ValueError, match="Cannot divide by 0"):
        divide(10, 0)
```

The `match` argument is a regular expression that's matched against the exception's string.

Or get the exception object itself for more detailed checks:

```python
def test_divide_by_zero_detail():
    with pytest.raises(ValueError) as exc_info:
        divide(10, 0)
    assert "divide" in str(exc_info.value)
    assert exc_info.type is ValueError
```

`exc_info.value` is the exception object that was raised – you can access its attributes like any normal object.

When writing tests, cover both the **normal path** and the **exception path**. Testing a function with only normal input isn't enough – edge cases, bad input and empty values ("does it raise exceptions gracefully?") matter too.



## Skipping and marking – choosing which tests to run

When writing tests, you'll often meet situations like these:

- This test only works on Linux, not on Windows
- This test only applies to Python 3.11+
- This test is slow (a dozen seconds or more) – you don't want to run it normally, only in CI
- This test is still being written – mark it as "to do" for now

`pytest`'s solution is its **mark** system.

### skip – just skip it

<!-- skip-ci -->
```python
import pytest


@pytest.mark.skip(reason="Not finished yet")
def test_new_feature():
    assert do_something() == "expected"
```

When it runs, `pytest` shows an `s`:

```
test_demo.py s                                                           [100%]
================== 1 skipped in 0.01s ==================
```

The test doesn't run, and doesn't count as a failure.

### skipif – skip on a condition

<!-- skip-ci -->
```python
import sys


@pytest.mark.skipif(sys.platform == "win32", reason="Not supported on Windows")
def test_unix_specific():
    assert "/usr/bin" in PATH


@pytest.mark.skipif(sys.version_info < (3, 11), reason="Needs Python 3.11+")
def test_exception_group():
    pass
```

The first argument is an expression – if it's `True`, the test is skipped.

### xfail – expected to fail

Some tests can't pass right now, but you don't want to skip them completely. For example, a bug hasn't been fixed yet, and you want the test to stay there as a reminder.

<!-- skip-ci -->
```python
@pytest.mark.xfail(reason="Bug #42 not fixed yet")
def test_buggy_feature():
    assert buggy_function() == "expected"
```

The logic of `xfail` is "I expect this to fail":

- If it fails: it's reported as XFAIL – as expected, and not counted as a failure
- If it unexpectedly passes: it's reported as XPASS (a reminder that the bug might have been fixed)

### Custom markers – sorting tests into groups

Sometimes you want to sort tests into groups – "slow tests", "tests that need a database", "network tests".

<!-- skip-ci -->
```python
@pytest.mark.slow
def test_big_data():
    process_one_million_rows()


@pytest.mark.db
def test_query_user():
    pass


@pytest.mark.network
def test_fetch_api():
    pass
```

Then choose which to run with `-m` on the command line:

```bash
# Run only slow tests
pytest -m slow

# Run everything except slow tests
pytest -m "not slow"

# Run slow tests or network tests
pytest -m "slow or network"
```

Before using custom markers, register them in your settings, or `pytest` will warn you. In `pyproject.toml`:

```toml
[tool.pytest.ini_options]
markers = [
    "slow: slow tests (take > 1 second)",
    "db: tests that need a database",
    "network: tests that need the network",
]
```

This has two benefits – it removes the warning, and newcomers reading `pyproject.toml` can see what kinds of tests the project has.



## Coverage – which code hasn't been tested yet?

You've written a pile of tests for your project, and they all pass. Great. But have you really "tested everything"?

**Coverage** answers exactly this question – **how much of your code actually ran during the tests?** If you have 100 lines of code and the tests only ran 60, coverage is 60%. The other 40 lines might be hiding bugs.

The Python tool for measuring coverage is `coverage`. With `pytest`, people usually install the `pytest-cov` plugin, which is simpler.

```bash
uv add --dev pytest-cov
```

Run:

```bash
# Run the tests + print a coverage report
pytest --cov=src

# You can also give a package name
pytest --cov=mypackage

# Show more detail – "which lines weren't tested"
pytest --cov=src --cov-report=term-missing
```

The output looks roughly like this:

```
---------- coverage: platform darwin, python 3.13.1 -----------
Name              Stmts   Miss  Cover   Missing
-----------------------------------------------
src/mymath.py        12      2    83%   15-16
src/utils.py          8      0   100%
-----------------------------------------------
TOTAL                20      2    90%
```

Look at the `Missing` column – lines 15 and 16 of `mymath.py` weren't tested. Go and look – it's probably an edge case that wasn't covered.

For a more visual view, create an HTML report:

```bash
pytest --cov=src --cov-report=html
```

This creates a web page report in the `htmlcov/` folder. Open `htmlcov/index.html`, click into any file, and you can see **which lines were tested (green) and which weren't (red)** – very clear.

You can also put default `pytest-cov` options in `pyproject.toml`:

```toml
[tool.pytest.ini_options]
addopts = "--cov=src --cov-report=term-missing"
```

Now every time you run `pytest`, you get a coverage report automatically.

So what coverage is "good enough"? The community's "common sense" numbers are:

- **80% or more**: basically a pass
- **90% or more**: fairly high-quality project
- **100%**: ideal, but usually very costly (you have to test all sorts of "impossible" branches)

Brother Shui's advice: **don't chase 100% at all costs.** Forcing coverage up leads to lots of "tests written just to make up the numbers", which actually drag the project down. Focus on fully testing key business paths, complicated logic and edge cases. Coverage tools are for **finding gaps**, not for **giving scores**.

Don't set a hard 90% target for an old project straight away. Start from 50%, and make sure each pull request "doesn't make it go down". Over time, the project will get stronger and stronger.



## conftest.py – sharing fixtures

As you write more and more tests, you'll notice a problem – **several test files need the same fixture**.

For example, `test_user.py`, `test_order.py` and `test_product.py` all need a `db` fixture. Do you have to write it in every file?

No. `pytest` has a special file called `conftest.py`. **Fixtures in `conftest.py` are automatically available to all tests in the same folder and its sub-folders** – no import needed.

For example:

```
tests/
├── conftest.py            # Shared fixtures go here
├── test_user.py
├── test_order.py
└── api/
    ├── conftest.py        # A sub-folder can have its own too
    └── test_endpoints.py
```

`tests/conftest.py`:

<!-- skip-ci -->
```python
import pytest


@pytest.fixture
def db():
    conn = create_test_db()
    yield conn
    conn.close()


@pytest.fixture
def sample_user(db):
    user = User(name="walter", age=28)
    db.save(user)
    return user
```

`tests/test_user.py`:

```python
def test_get_user(db, sample_user):
    # Use them directly – no import needed
    assert db.get_user(sample_user.id).name == "walter"
```

`tests/test_order.py`:

```python
def test_create_order(db, sample_user):
    # Can be used directly here too
    order = Order(user=sample_user, amount=100)
    db.save(order)
    assert order.id is not None
```

`tests/api/conftest.py` can add more fixtures that only apply to the `api/` sub-folder:

<!-- skip-ci -->
```python
import pytest


@pytest.fixture
def http_client():
    from httpx import Client
    with Client(base_url="http://localhost:8000") as c:
        yield c
```

`pytest` starts from the test file's folder and looks **upwards** for every `conftest.py`, collecting all their fixtures. So **inner folders can use outer fixtures, but not the other way round**.

Once you understand this rule, your test code becomes very tidy – shared logic all lives in `conftest.py`, and each test file only focuses on its own job.



## Configuring pytest in pyproject.toml

`pytest` works with zero configuration by default, but as a project grows, writing a few common settings into `pyproject.toml` saves a lot of effort.

```toml
[tool.pytest.ini_options]
# Where to look for test files
testpaths = ["tests"]

# Default options (added automatically every time you run pytest)
addopts = [
    "-v",                          # Detailed output
    "--strict-markers",            # Error if an unregistered marker is used
    "--cov=src",                   # Run coverage
    "--cov-report=term-missing",   # Show lines not covered
]

# Register custom markers
markers = [
    "slow: slow tests",
    "db: tests that need a database",
    "network: tests that need the network",
]

# Minimum pytest version
minversion = "8.0"
```

If an old project uses `setup.cfg` or `pytest.ini`, moving to `pyproject.toml` is easy – just change the `[pytest]` section to `[tool.pytest.ini_options]`. Since `pytest 8.x`, `pyproject.toml` support is very mature, so new projects should use it directly.



## A complete mini project – writing tests for a Wallet class

Remember the `Wallet` class we wrote in python17 when learning type hints? This time, let's finish it properly and write a decent set of tests for it.

First, `wallet.py` (an upgraded version, with a few more methods and simple saving to a file):

```python
from __future__ import annotations
import json
from pathlib import Path


class InsufficientFundsError(Exception):
    """Raised when there isn't enough money."""


class Wallet:
    """A simple wallet."""

    def __init__(self, initial: float = 0) -> None:
        if initial < 0:
            raise ValueError("The starting balance cannot be negative")
        self.balance: float = initial

    def deposit(self, amount: float) -> float:
        if amount <= 0:
            raise ValueError("The amount to deposit must be greater than 0")
        self.balance += amount
        return self.balance

    def withdraw(self, amount: float) -> float:
        if amount <= 0:
            raise ValueError("The amount to withdraw must be greater than 0")
        if amount > self.balance:
            raise InsufficientFundsError(
                f"Not enough money: balance is {self.balance}, tried to withdraw {amount}"
            )
        self.balance -= amount
        return self.balance

    def can_afford(self, price: float) -> bool:
        return self.balance >= price

    def save(self, path: Path) -> None:
        path.write_text(
            json.dumps({"balance": self.balance}),
            encoding="utf-8",
        )

    @classmethod
    def load(cls, path: Path) -> Wallet:
        data = json.loads(path.read_text(encoding="utf-8"))
        return cls(initial=data["balance"])
```

Looking at this class, there are several things to test:

1. Creating it: a negative starting balance should raise `ValueError`
2. `deposit`: an amount ≤ 0 should raise `ValueError`; a normal deposit adds to the balance
3. `withdraw`: an amount ≤ 0 raises `ValueError`; too much raises `InsufficientFundsError`; a normal withdrawal takes from the balance
4. `can_afford`: three cases – below, equal to and above the balance
5. `save` / `load`: write to a file and read it back, and the balance should match

Next, write the tests in `test_wallet.py`:

    (0.5, 1000.5),
    (1, 1001),
])

    assert rich_wallet.deposit(amount) == expected
    assert rich_wallet.balance == expected

    assert rich_wallet.balance == 700

        rich_wallet.withdraw(2000)

    assert file.exists()
    data = json.loads(file.read_text(encoding="utf-8"))
    assert data == {"balance": 1000}

    loaded = Wallet.load(file)
    assert loaded.balance == 1000

    rich_wallet.save(file)
    rich_wallet.deposit(500)
    rich_wallet.save(file)

## A few common traps

### Trap 1: tests affecting each other

```python
counter = 0


def test_a():
    global counter
    counter += 1
    assert counter == 1


def test_b():
    global counter
    counter += 1
    assert counter == 1     # Fails here – counter is already 2
```

The tests share global state. `test_a` runs first and changes `counter`, so `test_b` doesn't see a clean state.

**Fix**: either use fixtures to prepare state, or make sure the functions being tested have no side effects. **Don't use global variables to pass things between tests.**

### Trap 2: tests take too long

As you write more tests, a full run takes minutes. Developers get too lazy to run them, and in the end the tests are useless.

**Fix**:

- Mark slow tests with `@pytest.mark.slow`; don't run them locally, only in CI
- Raise fixture scopes (e.g. a session-level database connection)
- Use the `pytest-xdist` plugin to run tests in parallel: `pytest -n auto`

### Trap 3: comparing floats

```python
def test_divide():
    assert divide(1, 3) == 0.3333333333333333    # Floating-point precision problem
```

Floats have built-in precision errors, so comparing them directly with `==` often fails.

**Fix**: use `pytest.approx`:

```python
def test_divide():
    assert divide(1, 3) == pytest.approx(0.3333, rel=1e-3)
```

`approx` means "approximately equal", and you can set a relative or absolute tolerance.

### Trap 4: fixtures that depend on each other in a circle

<!-- skip-ci -->
```python
@pytest.fixture
def a(b):
    return b + 1


@pytest.fixture
def b(a):       # A circular dependency
    return a - 1
```

`pytest` gives an error straight away saying the fixture dependency is recursive.

**Fix**: check the fixture dependency graph and break the circle. It usually means one fixture should be split into two separate ones.

### Trap 5: you can't see your `print` debugging

While debugging, you add a quick `print`, run `pytest`, and see nothing.

**Reason**: by default, `pytest` captures all stdout, and only shows it when a test fails.

**Fix**: add the `-s` option:

```bash
pytest -s
```

Or use `pytest --capture=no`, which does the same.



## FAQ

**Q1: Where should tests go? Together with the source code?**

The usual way is to keep them apart – source in `src/`, tests in `tests/`. That way the test code isn't included when you package and publish.

Some projects put tests right next to the source, like `mypackage/test_foo.py` next to `mypackage/foo.py`. Both have their advantages. For new projects, Brother Shui recommends keeping them apart.

**Q2: Do I need to test every feature?**

No. **Key paths must be tested, edge cases should be tested first, and exception paths must be tested.** Trivial code like plain getters/setters can go untested. Private functions are mostly covered indirectly by testing the public interface.

**Q3: Are mocks and fixtures the same thing?**

No, but they're often used together.

- A **fixture** "prepares things the test needs" (connections, users, temporary folders)
- A **mock** "pretends to be an object/function" (doesn't really send a request – pretends it returned some value)

`pytest` comes with `monkeypatch` (a lightweight mock). For more powerful mocks, use the standard library's `unittest.mock`, or the third-party `pytest-mock` plugin.

**Q4: What if my test code has repetition?**

Same as normal code – pull out functions, pull out fixtures, use parametrisation. But **for tests, readability matters more than "Don't Repeat Yourself"**. If avoiding repetition makes a test hard to understand, let it repeat a bit. People reading a test want to see at a glance "what is this testing?", not dig through lots of helper functions.

**Q5: How fast should tests run?**

Unit tests (no database, no network) should run in **seconds** – a project with hundreds of unit tests should aim to finish in a few to a dozen seconds. Integration tests can be slower, but it's best to give them their own marker (like `@pytest.mark.integration`) and run them separately from unit tests.
