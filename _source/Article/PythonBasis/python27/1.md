# Publishing to PyPI + typer: let the whole world use your tool with one pip install

Have you ever had a moment like this?

Brother Shui writes a little tool on his own computer – say, "rename lots of screenshot files at once", "analyse exported chat history" or "automatically add a watermark to images". The script is a hundred or two lines, works nicely, and he uses it every day. Then one day a friend sees it and says: "That's handy – can I have a copy?"

So Brother Shui sends `tool.py` over in a chat message. The first thing the friend says is: "How do I use this?"

"Install `pillow` and `httpx`."

"OK, done."

"Now install `pyyaml`."

"Done."

"Run `python tool.py`."

"Error – it says it can't find `requests`."

"Oh right, you need `requests` too."

Five minutes of back and forth, and the friend gives up.

This is the "last mile" problem of Python tools – the code runs for you, but it's a struggle for anyone else to use. In the Node world it's one line, `npm install -g xxx`. In Rust, `cargo install xxx`. In Go, `go install xxx`. Does Python really have to be "install this, then install that"?

Of course not. Python has its own "global app store" called **PyPI** (the Python Package Index). Package your tool properly and upload it, and anyone can install it with one line, `pip install my-tool`. No more teaching people step by step.

In this chapter, we'll go through the whole process from scratch. After it, you should be able to:

1. Know what PyPI is, and how it relates to `pip`
2. Turn your own project into a standard "publishable" structure
3. Use one `uv build` command to package your project as a `wheel` and an `sdist`
4. Practise on TestPyPI first, then publish to the real PyPI
5. Use `[project.scripts]` to turn a Python function into a system command
6. Use `typer` to write command-line tools 10 times more elegant than `argparse`
7. Connect the whole publishing process to GitHub Actions, so adding a tag publishes a release automatically

In the second half, we'll use `typer` to write a small command-line tool, `todo-cli`, and publish it to PyPI so anyone in the world can `pip install todo-cli`. This little project ties both halves together – run through it once and it'll all make sense.

Let's go.



## What is PyPI?

When you type `pip install requests`, where is the package downloaded from? The answer is PyPI.

**PyPI (the Python Package Index) is the global public package repository maintained officially for Python**, at `https://pypi.org`. As of 2026, it holds over 600,000 Python packages, downloaded tens of billions of times a month. All the well-known Python packages – `requests`, `numpy`, `flask`, `django`, `pandas`, `fastapi` – live on PyPI.

What `pip install xxx` really means is: "download the package called `xxx` from PyPI and install it into the current Python environment".

How does PyPI relate to GitHub? They each do their own job:

- **GitHub** is where **source code** lives, for developers to read
- **PyPI** is where **packaged releases** live, for users to install with `pip`

A project usually has both – source code hosted on GitHub, releases uploaded to PyPI. Packages you use, like `requests` and `flask`, have their source on GitHub and their packages on PyPI, with matching version numbers.

PyPI also has a "sister site" called **TestPyPI**, at `https://test.pypi.org`. It's a practice ground – before publishing a release, upload it to TestPyPI first to try it out, and only publish to the real PyPI once you're sure it's fine. The two sites are completely separate – accounts, passwords and tokens don't work across them.

"Why have TestPyPI?" Because on PyPI, **a released version can never be changed or deleted**. If your hand slips when publishing – you upload `0.1.0` and then find the version number was wrong, or files were missing from the package – you can't take it back. You can only publish `0.1.1`, and the broken version stays on PyPI forever as part of history. So practising on TestPyPI before the real PyPI is a good habit.

Next, let's build a project that can be published to PyPI, step by step.



## First, get the project structure right

The most common folder layout for Python projects looks like this:

```
my-tool/
├── my_tool.py
└── README.md
```

Or, a bit more carefully:

```
my-tool/
├── my_tool/
│   ├── __init__.py
│   └── main.py
└── README.md
```

These work fine locally, but once you package and publish, a hidden trap appears – **Python automatically adds the current folder to `sys.path`**. So when you run tests, you're importing "the source code in the project's root folder" rather than "the package installed in the environment", and problems get hidden.

The community now recommends a layout called **src layout**, which looks like this:

```
my-tool/
├── pyproject.toml
├── README.md
├── LICENSE
├── src/
│   └── my_tool/
│       ├── __init__.py
│       └── main.py
└── tests/
    └── test_main.py
```

Notice the extra `src/` folder in the middle. It's not decoration. Its job is to **force the source code out of the project's root folder**. That way you **must** install the package into the environment before you can import it, which avoids the trap above.

"Is that a hassle?" Not at all. With `uv` and `pyproject.toml`, the tools recognise the `src/` layout automatically – nothing to configure.

Let's start a new project with `uv` and look at the default structure:

```bash
uv init --package my-tool
cd my-tool
ls -R
```

The output is roughly:

```
.
├── README.md
├── pyproject.toml
└── src
    └── my_tool
        └── __init__.py
```

This one `uv init --package` line builds the `src layout` skeleton for you. Note the `--package` option – without it, `uv init` builds an "app" structure by default (not for packaging). With it, you get a "library/tool" structure (for packaging and publishing).

Open `pyproject.toml` and look at what `uv` created:

```toml
[project]
name = "my-tool"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.10"
dependencies = []

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project.scripts]
my-tool = "my_tool:main"
```

The skeleton is all there – the `[project]` section for metadata, the `[build-system]` section for the packaging back end, and the `[project.scripts]` section for command-line entry points. Next, let's fill in each field properly.



## The required fields in pyproject.toml

To publish to PyPI, a few fields in the `[project]` section are unavoidable – name, version, description, Python version requirement and dependencies. Let's go through them one by one.

### name: the package's globally unique name

`name` is the `xxx` people type in `pip install xxx` after you publish to PyPI. **It's unique across the whole of PyPI**, like a domain name – first come, first served. Before choosing a name, check `https://pypi.org/project/xxx/` to see whether it's taken.

Naming rules: only letters, digits, `-`, `_` and `.` are allowed; it's not case-sensitive; and it can't start with a digit. The community usually uses lowercase with hyphens, like `my-tool`, `todo-cli` or `http-prompt`.

Note one detail: **the package name (`name`) and the import name (the `xxx` in `import xxx`) aren't always the same**. For example, you `pip install scikit-learn` but `import sklearn`. You `pip install Pillow` but `import PIL`. That's because:

- `name` is the project name on PyPI, and can contain hyphens
- The import name is a Python module name, which must be a valid Python identifier – no hyphens

Brother Shui's advice: to avoid confusing users, **keep the two names as similar as possible**. For example, if the package name is `my-tool`, call the import name `my_tool` (hyphens become underscores – the usual Python habit).

### version: the version number

`version` is the version number of this release, written as a string, like `"0.1.0"`, `"1.2.3"` or `"2.0.0a1"`.

The community strongly recommends **Semantic Versioning (SemVer)** – three numbers, `MAJOR.MINOR.PATCH`:

- **Major version**: big changes that aren't backwards-compatible (removing functions, changing signatures)
- **Minor version**: new features that are backwards-compatible
- **Patch version**: bug fixes that are backwards-compatible

New projects start at `0.1.0`. Before 1.0, everything is "unstable", and the API can change freely. After 1.0, be careful about changing the API.

PyPI also has an iron rule – **each version number can only be uploaded once**. If you publish `0.1.0` and want to take it back and publish again – sorry, you can't. You must change it to `0.1.1` or `0.1.0.post1` and publish again.

### description: a one-sentence description

`description` is a one-sentence summary. It's shown at the top of the PyPI page and in search results. Write something decent – don't publish with the default `"Add your description here"`, or it'll look embarrassing once it's live.

```toml
description = "A small tool by Two Drops that adds watermarks to lots of images at once"
```

### readme: the long description

`readme` is the project's long description, shown as the main text on its PyPI page. Just point it to a Markdown file:

```toml
readme = "README.md"
```

`uv init` already created an empty `README.md` for you – fill it in. It should at least have a short introduction, the install command and a minimal usage example.

### authors / maintainers: the authors

`authors` is a list of authors. Each author is an object with at least a name; email is optional:

```toml
authors = [
    { name = "Two Drops", email = "liangdianshui@example.com" },
]
```

### requires-python: the Python version requirement

`requires-python` limits which Python versions this package supports:

```toml
requires-python = ">=3.10"
```

Don't write `>=3.0` – then ancient Python versions will try to install it too, causing lots of compatibility problems. A sensible choice in 2026 is `>=3.10` or `>=3.11`; 3.9 is at the edge of end-of-life.

### dependencies: the dependency list

`dependencies` lists the other packages this package needs to run:

```toml
dependencies = [
    "httpx>=0.27",
    "typer>=0.12",
]
```

Each one follows PEP 508 syntax – `package name` + version rule. Common version rules:

- `>=0.27`: 0.27 or higher – the most common
- `~=0.27`: a compatible version, `>=0.27, <0.28`
- `==0.27.1`: an exact version – hardly ever used
- `>=0.27, <1.0`: a range

"Should I write version numbers?" **I strongly recommend writing a minimum version**, like `httpx>=0.27`. That way, when someone installs it, at least `httpx` won't be so old that functions are missing. Don't casually write an upper limit – fixing it tightly makes dependency conflicts more likely for your users.

A complete minimal publishable `pyproject.toml` looks roughly like this:

```toml
[project]
name = "my-tool"
version = "0.1.0"
description = "A small tool by Two Drops"
readme = "README.md"
requires-python = ">=3.10"
authors = [
    { name = "Two Drops", email = "liangdianshui@example.com" },
]
dependencies = [
    "httpx>=0.27",
]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

The next section explains what `[build-system]` is.



## build-backend: who does the packaging?

At the end of that `pyproject.toml` is this section:

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

What are these two lines doing? To explain, we first need to understand the roles in Python packaging.

Python packaging has two roles – the **front end** and the **back end**:

- The **front end** is the command the user types, like `pip`, `uv` or `build`
- The **back end** is the library that does the real work – turning source code into a `wheel` and an `sdist`

The PEP 517 standard separated the two: the front end only calls the back end, and the back end can be swapped freely. The `[build-system]` section tells the front end "which back end I use".

The community's three main back ends today:

- **`hatchling`**: from the `Hatch` project – simple to configure, very extensible, **the first choice for new projects**
- **`setuptools`**: the ancient, well-established back end – used by almost every old project
- **`poetry-core`**: the back end that comes with the Poetry project, used with the Poetry tool

You might also see `flit-core`, `pdm-backend` and `maturin` (for extensions written in Rust) in the wild – different choices for the same job.

Why recommend `hatchling`? Three reasons –

1. **Simple to configure.** `uv init --package` uses it by default, so you don't need to change anything
2. **Modern.** It natively supports `src layout` and PEP 621 metadata, with no historical baggage
3. **Officially backed.** `hatch` is a project of the PyPA (Python Packaging Authority)

"Isn't `setuptools` more widespread?" It is, but its configuration is complicated and messy, and new projects don't need that trouble. Unless you need C extensions or compatibility with ten-year-old code, just pick `hatchling`.

Keep this section as the default in your `pyproject.toml`:

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

`requires` lists "packages needed to **build** this project". These are different from `[project].dependencies` – those are "packages needed to **run** this project", while these are "packages needed to **package** this project".

In the next section, let's try packaging the project.



## Building locally: one `uv build` command

Once you've written your code, how do you package it in a publishable format? One command –

```bash
uv build
```

Run it, and the output is roughly:

```
Building source distribution...
Building wheel from source distribution...
Successfully built dist/my_tool-0.1.0.tar.gz
Successfully built dist/my_tool-0.1.0-py3-none-any.whl
```

Open the `dist/` folder:

```
dist/
├── my_tool-0.1.0-py3-none-any.whl
└── my_tool-0.1.0.tar.gz
```

What are these two files?

- **The `.whl` file (wheel)**: a ready-built package. When users `pip install`, this is chosen first, because it needs no building – it installs instantly
- **The `.tar.gz` file (sdist, source distribution)**: a source package. It contains the whole project's source, for users with unusual environments who need to build from source

There's a rule in the file name – `package-version-PythonVersion-ABI-platform`:

- `py3`: works with any Python 3
- `none`: doesn't depend on a specific ABI
- `any`: works on any platform

If your package contains C extensions, the `whl` name becomes something like `my_tool-0.1.0-cp311-cp311-linux_x86_64.whl`, which only works on CPython 3.11 on Linux x86_64. You'd need to build a separate `whl` for every platform.

A pure Python project has just one `py3-none-any.whl` that works everywhere – the easiest.

"What if I don't have `uv`?" You can use the official `build` tool instead:

```bash
pip install build
python -m build
```

Same result. Use whichever you prefer – the rest of this chapter uses `uv`.

After building successfully, **always install it locally first and try it**:

```bash
uv pip install dist/my_tool-0.1.0-py3-none-any.whl
```

Or:

```bash
pip install dist/my_tool-0.1.0-py3-none-any.whl
```

After installing, run your tool and check that it works. This is the last line of defence before publishing. If you find a problem now, you can still fix it; once it's on PyPI, it's too late.



## Registering a TestPyPI account

The package is built. Next – upload it. First practise on TestPyPI, then publish to the real PyPI.

How to register on TestPyPI –

1. Open `https://test.pypi.org/account/register/`
2. Register an account with your email and verify the email
3. After logging in, go to `Account settings`
4. Turn on **two-factor authentication (2FA)** – TestPyPI now requires it. You can use a TOTP app like Authy, Google Authenticator or 1Password
5. Go to the `API tokens` page and create a token, choosing the scope `Entire account` (for your first upload, you can't limit it to a specific project, because the project doesn't exist yet)
6. Copy the token – **you can only see it once; close the page and it's gone**

A TestPyPI token looks like this:

```
pypi-AgEIcHlwaS5vcmcCJ...(a long base64 string)
```

Save this token in a password manager.

Registering on the real PyPI is the same – `https://pypi.org/account/register/`, turn on 2FA, create a token, save it. Remember, PyPI and TestPyPI are two separate websites, with separate accounts and tokens.

"How do I use the token?" You'll use it in the next section.



## Practising by uploading to TestPyPI

The command to publish to TestPyPI –

```bash
uv publish --publish-url https://test.pypi.org/legacy/ \
    --token pypi-AgEIcHlwaS5vcmcCJ...
```

Or, more safely, use an environment variable:

```bash
export UV_PUBLISH_TOKEN=pypi-AgEIcHlwaS5vcmcCJ...
uv publish --publish-url https://test.pypi.org/legacy/
```

If it succeeds, the output is roughly:

```
Uploading my_tool-0.1.0-py3-none-any.whl
Uploading my_tool-0.1.0.tar.gz
Published https://test.pypi.org/project/my-tool/0.1.0/
```

Open the link, and your little tool is sitting on TestPyPI, with its title, description, version, README and dependency list.

Next – **install it from TestPyPI and check it works**:

```bash
pip install --index-url https://test.pypi.org/simple/ \
    --extra-index-url https://pypi.org/simple/ \
    my-tool
```

Notice the two index options here –

- `--index-url https://test.pypi.org/simple/`: look for the package you just uploaded on TestPyPI
- `--extra-index-url https://pypi.org/simple/`: look for dependencies on the real PyPI (because your dependencies, like `httpx`, are published on the real PyPI)

Without the second option, the dependencies won't install properly from TestPyPI (TestPyPI only has what you just uploaded, not `httpx`). This is the most common beginner trap – remember it.

After installing, run your tool. If it works – congratulations, you've mastered the publishing process.



## Uploading to the real PyPI

Once your TestPyPI practice succeeds, publishing to the real PyPI is one command –

```bash
export UV_PUBLISH_TOKEN=pypi-your-real-token-...
uv publish
```

By default, `uv publish` uploads to `https://upload.pypi.org/legacy/` – the real PyPI.

After publishing, open `https://pypi.org/project/my-tool/`, and your project is on PyPI. Now anyone can:

```bash
pip install my-tool
```

and install your tool into their own environment. Even Brother Shui gets a little excited writing this – it means your code is on the global public repository, and anyone can use it.

"What if I want to take a release down after publishing?" PyPI has a **yank** feature – the version number stays, but by default new installs won't find it. Note that this only "hides" it, it doesn't "delete" it – users who already installed it can keep using it. Completely deleting a version isn't allowed, so that dependency chains don't break.



## Managing version numbers: by hand vs automatically

You've published `0.1.0`, and after a while you want to publish `0.1.1`. How do you change the version number?

**By hand** – open `pyproject.toml`, change `version = "0.1.0"` to `version = "0.1.1"`, then `uv build` + `uv publish` again. Simple and direct.

But doing it by hand has a problem – `pyproject.toml` and your git tags can easily get out of step. For example, `pyproject.toml` says `0.1.1` but the git tag is `v0.2.0` – which one is right? After a few versions of drifting like this, things get messy.

**Automatically** – use `hatch-vcs` to work out the version number from git tags automatically. Change `pyproject.toml`:

```toml
[project]
name = "my-tool"
dynamic = ["version"]
description = "A small tool by Two Drops"
# ...

[build-system]
requires = ["hatchling", "hatch-vcs"]
build-backend = "hatchling.build"

[tool.hatch.version]
source = "vcs"
```

Notice three changes –

1. `version = "0.1.0"` becomes `dynamic = ["version"]`, telling `hatchling` "the version number isn't fixed – work it out"
2. `hatch-vcs` is added to `[build-system].requires`, bringing in the plugin that works out the version
3. A new `[tool.hatch.version]` section tells `hatch-vcs` "read it from git"

After that, the process becomes –

```bash
git tag v0.1.1
git push --tags
uv build
uv publish
```

When you `uv build`, `hatch-vcs` reads the latest git tag `v0.1.1`, works out the version number `0.1.1`, and the package becomes `my_tool-0.1.1-py3-none-any.whl`.

If you change the code after adding a tag, `hatch-vcs` automatically adds a `dev` suffix, so the version becomes something like `0.1.2.dev3+gabc1234` – clearly telling you "this is a version still in development".

Brother Shui's advice: **use the automatic way for new projects**. Doing it by hand is fine at first, but by the third or fourth version, with more developers involved, the automatic way saves lots of checking.



## README and LICENSE: the minimum for looking "proper"

Projects you publish to PyPI **must have a README.md and a LICENSE file**. That's basic good manners in the industry.

### README.md

`README.md` is shown as the main text on your PyPI project page – it's the first thing users see. It should include at least –

```markdown
# my-tool

A small tool by Two Drops that adds watermarks to lots of images at once.

## Install

```bash
pip install my-tool
```

## Usage

```bash
my-tool ./photos --watermark "© Two Drops"
```

## License

MIT
```

Introduction, install, usage, License – four sections are enough. More careful projects also add "Features", "Examples", "FAQ" and a "Contributing guide".

### LICENSE

A licence is a legal document. It tells users "this is how I allow you to use my code". If you write an open source project without a licence, that means "all rights reserved" – which is actually the strictest option. Other people can't use your code, because they haven't been given permission.

Pick one of the three common licences –

- **MIT**: the most relaxed – "use it however you like, don't sue me, just keep the copyright notice"
- **Apache 2.0**: similar to MIT, plus a "patent grant" clause, which is friendlier for companies
- **GPL v3**: a "copyleft" licence – "if you use my code, your code must be open source too"

The community habit: tool and library projects use MIT or Apache 2.0; for app projects, decide for yourself. Brother Shui's little tools always use MIT – it's simple.

Declare it in `pyproject.toml` too:

```toml
[project]
license = { file = "LICENSE" }
```

Or use an SPDX identifier (PEP 639, officially adopted in 2024):

```toml
[project]
license = "MIT"
```

The second form is more modern, but some older tools don't understand it yet – it depends on how much you're willing to put up with.



## Publishing automatically with CI: add a tag, publish a release

Running `uv build` + `uv publish` by hand every time gets boring after two or three releases. The ideal is – **add a git tag, and CI builds and publishes to PyPI automatically**.

One GitHub Actions workflow can do this. In your project, create a file `.github/workflows/release.yml`:

```yaml
name: Release

on:
  push:
    tags:
      - "v*"

jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      id-token: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - uses: astral-sh/setup-uv@v3

      - run: uv build

      - uses: pypa/gh-action-pypi-publish@release/v1
```

What does this configuration do –

1. **Trigger**: it runs when you `push` a tag starting with `v` (like `v0.1.1`)
2. **`permissions: id-token: write`**: asks for OpenID Connect permission for the workflow – the "trusted publishing" below needs it
3. **Build**: packages the project with `uv build`
4. **Publish**: uploads to PyPI with `pypa/gh-action-pypi-publish`

The most amazing part – **this process doesn't need a PyPI token at all**. It relies on a feature called **Trusted Publishers**, which PyPI launched in 2023 and which became the recommended approach in 2024.

How trusted publishing works – PyPI directly trusts the OIDC identity of GitHub Actions. Once you link "this workflow file in this GitHub repository" in your PyPI project settings, PyPI recognises the CI run and lets it upload without a token.

Setup steps –

1. Log in to PyPI and go to your project page → `Settings` → `Publishing`
2. Add a "Trusted Publisher", filling in `Owner` (your GitHub username/organisation), `Repository name`, `Workflow name` (`release.yml`) and `Environment` (optional)
3. Push a tag to try it

The commands to add a tag –

```bash
git tag v0.1.1
git push origin v0.1.1
```

GitHub Actions starts running, and a few minutes later your package is on PyPI.

"What's better about this than a token?" Three things –

1. **No token expiry to worry about.** Tokens can expire, and then you have to create a new one
2. **No fear of the token leaking.** The OIDC credential only exists for the moment the workflow runs – it can't be copied out
3. **The configuration lives on the PyPI side.** No need to change secrets when swapping tokens, so permissions are clearer

Brother Shui strongly recommends that new projects in 2026 use trusted publishing from day one – it's much cleaner than tokens.

That's the end of the part about publishing to PyPI. In the next section we change topic – **`typer`**, a great tool for writing CLI (command-line) tools.



## The pain of CLIs: argparse is too wordy

Have you ever written a command-line tool? Python's standard library comes with `argparse`. It works, but it's terribly wordy to write. Look at this:

<!-- skip-ci -->
```python
import argparse

parser = argparse.ArgumentParser(description="Add a watermark to an image")
parser.add_argument("input", type=str, help="Input image path")
parser.add_argument("--watermark", type=str, default="© Two Drops", help="Watermark text")
parser.add_argument("--opacity", type=float, default=0.5, help="Opacity")
parser.add_argument("--verbose", action="store_true", help="Show details")
args = parser.parse_args()

print(f"Input: {args.input}")
print(f"Watermark: {args.watermark}")
print(f"Opacity: {args.opacity}")
print(f"Verbose: {args.verbose}")
```

The setup takes 7 lines, but the useful logic is just 4 variables. Why so wordy? Because `argparse` was written in 2009, before Python had type hints. You have to `add_argument` every parameter by hand, filling in the type, default and help text each time. The function signature and the parameter declarations live in two places, so it's easy to miss something when you change it.

Even worse are subcommands – a "main command + subcommand" structure like `git commit` and `git push`. In `argparse` you nest a pile of `subparsers`, and one look gives you a headache.

In 2026, is there something better?

Yes – it's called **`typer`**. It was written by Tiangolo, the author of `FastAPI`, and follows the same idea as `FastAPI` – **use type hints directly as parameter declarations**. The same feature written with `typer` looks like this:

<!-- skip-ci -->
```python
import typer

app = typer.Typer()


@app.command()
def watermark(
    input: str,
    watermark: str = "© Two Drops",
    opacity: float = 0.5,
    verbose: bool = False,
):
    print(f"Input: {input}")
    print(f"Watermark: {watermark}")
    print(f"Opacity: {opacity}")
    print(f"Verbose: {verbose}")


if __name__ == "__main__":
    app()
```

Take a look – the parameters are written right in the function signature. The type hint is the parameter type, the default value is the command-line default, and help text can be taken from the docstring automatically. The logic is the same as `argparse`, with half the lines and ten times the readability.

## An app with several commands

Have you used `git`? `git commit`, `git push`, `git pull` – one main command with lots of subcommands. In `typer`, this structure is called a **multi-command app**:

<!-- skip-ci -->
```python
import typer

app = typer.Typer()


@app.command()
def add(item: str):
    """Add a task."""
    print(f"Added: {item}")


@app.command()
def list():
    """List all tasks."""
    print("Listing all tasks...")


@app.command()
def done(index: int):
    """Mark a task as done."""
    print(f"Finished task {index}")


if __name__ == "__main__":
    app()
```

Look – three steps –

1. `app = typer.Typer()`: create an app object
2. Decorate the function for each command with `@app.command()`
3. Start it with `app()`

Run it:

```bash

python todo.py list
python todo.py done 1
```

Output:

```

Finished task 1
```

Each function decorated with `@app.command()` becomes a subcommand, and the function name is the subcommand name. When the user types `add`, the `add` function runs; when they type `list`, the `list` function runs.

## Type hints = CLI parameters

The most magical thing about `typer` is that **the type hints on your function's parameters are the types of the CLI parameters**. Whatever type you write, the CLI converts to that type automatically – you don't write a single line of conversion code.

Supported types –

<!-- skip-ci -->
```python
import typer
from pathlib import Path
from enum import Enum


class Color(str, Enum):
    red = "red"
    green = "green"
    blue = "blue"


def cmd(
    text: str,
    count: int,
    ratio: float,
    enabled: bool,
    file: Path,
    color: Color,
):
    print(f"text={text!r}")
    print(f"count={count} (type {type(count).__name__})")
    print(f"ratio={ratio} (type {type(ratio).__name__})")
    print(f"enabled={enabled}")
    print(f"file={file} (type {type(file).__name__})")
    print(f"color={color}")
```

Run this command –

```bash
python cmd.py "hi" 10 1.5 ./README.md red
```

Output:

```
text='hi'
count=10 (type int)
ratio=1.5 (type float)
enabled=False
file=README.md (type PosixPath)
color=Color.red
```

Notice a few details –

- With the `int` type, `"10"` from the command line automatically becomes an integer
- With the `float` type, `"1.5"` automatically becomes a float
- With the `Path` type, it's automatically wrapped as a `pathlib.Path` object
- With the `Enum` type, the value can only be `red`/`green`/`blue` – anything else gives an error straight away
- A `bool` parameter with no default isn't a positional argument here – it becomes an `--enabled/--no-enabled` switch, which is why `enabled=False`

Try typing the wrong type:

```bash
python cmd.py "hi" abc 1.5 ./README.md red
```

`typer` refuses straight away:

```
Usage: cmd.py [OPTIONS] TEXT COUNT RATIO FILE COLOR
Try 'cmd.py --help' for help.

Error: Invalid value for 'COUNT': 'abc' is not a valid integer.
```

"Types are validation" – write `int`, and `typer` only accepts values that can become an `int`. Anything else never even gets into your function. Compared with `argparse`, where you still have to write your own `try except`, this is so comfortable.



## Optional parameters: the magic of default values

Back to the earlier example – is the parameter `text: str` "required" or "optional"? It's required, because it has no default value.

To make it optional, just add a default value:

```python
def hello(name: str = "World"):
    print(f"Hi {name}")
```

Now `typer` changes it from a "positional argument" to an "**option**", and the command line usage becomes:

```bash
python hello.py                   # prints Hi World
python hello.py --name TwoDrops   # prints Hi TwoDrops
```

Notice –

- **A parameter with no default = a positional argument (Argument)**: required, written right after the command
- **A parameter with a default = an option (Option)**: optional, needs the `--name` prefix

This matches Python functions' "positional vs keyword arguments" logic. Whether your Python function parameter has a default decides whether the CLI gets a positional argument or an option.

Short options are easy to add too, with `typer.Option`:

<!-- skip-ci -->
```python
import typer


def hello(
    name: str = typer.Option("World", "--name", "-n", help="Whose name"),
):
    print(f"Hi {name}")


if __name__ == "__main__":
    typer.run(hello)
```

Now –

```bash
python hello.py -n TwoDrops
python hello.py --name TwoDrops
```

The two forms are the same. The first argument to `typer.Option` is the default value, then come the command-line names, and finally `help` is the help text.



## Required vs optional parameters: the one-sentence rule

If you keep going back and forth between "positional argument" and "option", here's Brother Shui's one-sentence rule –

- **"This value must be given" → positional argument.** For example, `cp source target` – without a source or target, the command can't run
- **"This value can be left out, and there's a default behaviour" → option.** For example, `ls --all` – it runs fine without it

In a `typer` function signature –

<!-- skip-ci -->
```python
def watermark(
    input: Path,                  # positional: required
    output: Path,                 # positional: required
    text: str = "© Two Drops",    # option: optional, default watermark
    opacity: float = 0.5,         # option: optional, default 0.5
    verbose: bool = False,        # option: optional, default False
):
    ...
```

CLI usage:

```bash
my-tool input.jpg output.jpg
my-tool input.jpg output.jpg --text "Copyright Two Drops" --opacity 0.8 --verbose
```

When you write CLI tools, **use 1–3 positional arguments at most** – any more and users can't remember the order. If there are more than 3 parameters, make the rest options; it actually reads more clearly.



## Asking the user: prompt and confirm

When writing CLI tools, you often have situations like this – "the user didn't pass this value, so I want to ask them". For example, asking "Are you sure?" before deleting files, or "What's the project called?" when setting up a project.

The old way is `input()`. `typer` gives you two nicer tools – `typer.prompt` and `typer.confirm`.

First, `prompt`, which asks the user a question and gets the answer:

<!-- skip-ci -->
```python
import typer


def init():
    name = typer.prompt("Project name")
    author = typer.prompt("Author", default="Two Drops")
    print(f"Creating project {name}, author {author}")


if __name__ == "__main__":
    typer.run(init)
```

When it runs –

```
Project name: my-tool
Author [Two Drops]:
Creating project my-tool, author Two Drops
```

The `default` argument gives a default value – if the user just presses Enter, the default is used. Much nicer than `input()`.

`confirm` asks a yes/no question:

<!-- skip-ci -->
```python
import typer


def delete(path: str):
    sure = typer.confirm(f"Are you sure you want to delete {path}?")
    if not sure:
        print("Cancelled")
        raise typer.Abort()
    print(f"Deleted {path}")


if __name__ == "__main__":
    typer.run(delete)
```

When it runs –

```
$ python del.py /tmp/foo
Are you sure you want to delete /tmp/foo? [y/N]: y
Deleted /tmp/foo
```

By default `confirm` means "no" (if the user just presses Enter = no). Add `default=True` to make the default "yes".

`typer.Abort()` is another special exception – it means "the user chose to give up". The CLI exits with a standard exit code (1 by default), and the meaning is clearer than `typer.Exit()`.



## Exiting with an error: typer.Exit and typer.Abort

When you write CLI tools, sometimes the command needs to exit as a "failure" – a file doesn't exist, the network is down, the user typed a wrong value. The Linux habit is "exit code 0 = success, not 0 = failure", and shell scripts use this to decide whether to carry on.

`typer` gives you two ways to exit –

<!-- skip-ci -->
```python
import typer


def deploy(env: str):
    if env not in ("dev", "staging", "prod"):
        print(f"Unknown environment: {env}")
        raise typer.Exit(code=2)
    print(f"Starting deployment to {env}")
```

`typer.Exit(code=N)` makes the CLI exit straight away with exit code N. The usual conventions –

- `0`: success
- `1`: general failure
- `2`: the user typed a wrong argument

Don't just use `sys.exit(N)` everywhere – `typer.Exit` lets `typer` finish its own exit handling properly, so stick to `typer.Exit`.

The other one is `typer.Abort()`, meaning "the user stopped". For example, when the user answers no to the `confirm` above, you `raise typer.Abort()`. It exits with code 1 like `typer.Exit(code=1)`, and also prints `Aborted!`, so the meaning is clearer.



## Coloured output: echo and secho

Have you noticed in the output of `git status` that modified files are red, staged files are green, and hint text is yellow? Adding some colour to a command-line tool makes it easier to read straight away.

`typer` has simple coloured output built in, called `typer.echo` and `typer.secho`:

<!-- skip-ci -->
```python
import typer


def status():
    typer.echo("Normal text, just like print")
    typer.secho("Success!", fg=typer.colors.GREEN)
    typer.secho("Warning!", fg=typer.colors.YELLOW)
    typer.secho("Error!", fg=typer.colors.RED, bold=True)


if __name__ == "__main__":
    typer.run(status)
```

Run it in a terminal that supports colour – "Success!" is green, "Warning!" is yellow, and "Error!" is bold red. In places without colour support (like when the output is redirected to a file), `typer` removes the colour codes automatically, so the output stays clean.

Colours you can use – `BLACK`, `RED`, `GREEN`, `YELLOW`, `BLUE`, `MAGENTA`, `CYAN`, `WHITE`, plus styles like `bold=True` and `underline=True`.

"Why not use `print`?" `print` can't tell whether the terminal supports colour. When the output is redirected to a file, colour codes turn into messy characters like `\x1b[32m` and pollute the output. `typer.secho` handles this detail for you.

For fancier output (tables, progress bars, Markdown), `typer` works smoothly with `rich` – once `rich` is installed (recent versions of `typer` install it by default), it's used for things like nicer help and error messages.



## Nested subcommands: app.add_typer

When you write a big CLI tool with lots of commands, you'll want to group them – like `git remote add`, `git remote rm`, `git stash push`, `git stash pop`, "subcommands of subcommands".

`typer` supports nesting sub-apps:

<!-- skip-ci -->
```python
import typer

app = typer.Typer()
remote_app = typer.Typer()
stash_app = typer.Typer()

app.add_typer(remote_app, name="remote", help="Manage remote repositories")
app.add_typer(stash_app, name="stash", help="Manage the stash")


@remote_app.command("add")
def remote_add(name: str, url: str):
    print(f"Adding remote: {name} -> {url}")


@remote_app.command("rm")
def remote_rm(name: str):
    print(f"Removing remote: {name}")


@stash_app.command("push")
def stash_push():
    print("Stashing current changes")


@stash_app.command("pop")
def stash_pop():
    print("Restoring the latest stash")


if __name__ == "__main__":
    app()
```

Run it –

```bash
python git.py remote add origin git@github.com:walter/python.git
python git.py remote rm origin
python git.py stash push
python git.py stash pop
```

Each sub-app can have its own sub-apps, in theory forever. But don't really nest more than three levels – users won't remember. Two levels is enough.



## Turning it into a system command: [project.scripts]

Right now, your `typer` tool runs as `python todo.py add ...`. You have to type `python` every time, unlike `git`, which you just type directly. How do you make it a global command?

The answer is the `[project.scripts]` section in `pyproject.toml`:

```toml
[project.scripts]
todo-cli = "my_tool.cli:app"
```

The format is `command-name = "package.path:function-name"`. This line means –

- After this package is installed, the command line has a new command called `todo-cli`
- Running `todo-cli` is the same as running `app` in `my_tool/cli.py`

A `typer.Typer()` object can be called like a function, so you can use `app` directly.

Reinstall the package:

```bash
uv pip install -e .
```

Then try:

```bash
todo-cli --help
```

The help appears straight away. Try more:

```bash
todo-cli add "Learn typer"
todo-cli list
```

Exactly the same as `python todo.py add ...` before, but the command is shorter, and it immediately feels like a real tool.

"What does `uv pip install -e .` mean?" `-e` is editable mode – it installs the package as a "link" to your source code. When you change the source, the command changes straight away, with no reinstalling. Always use `-e` while developing – it saves countless reinstalls.

Now all the parts for packaging + CLI are ready. In the next section, we'll tie everything together with one complete small project.



## Hands-on: todo-cli from zero to published

Let's follow Brother Shui and write a complete `todo-cli` tool, and finally publish it to PyPI (with a practice release on TestPyPI). The tool supports three commands –

- `todo-cli add "Buy vegetables"`: add a todo
- `todo-cli list`: list all todos
- `todo-cli done 1`: mark item 1 as done

The data is stored in `~/.todo-cli.json` in the user's home folder – the simplest kind of local storage.

### Step 1: Create the project skeleton

```bash
uv init --package todo-cli
cd todo-cli
uv add typer
```

`uv` creates `src/todo_cli/__init__.py` automatically. We add one more file, `src/todo_cli/cli.py`.

### Step 2: Write the core logic

<!-- skip-ci -->
```python
import json
from pathlib import Path

import typer

app = typer.Typer(help="A small todo tool by Two Drops")

DATA_FILE = Path.home() / ".todo-cli.json"


def load_todos() -> list[dict]:
    """Read the todo list. Return an empty list if the file doesn't exist."""
    if not DATA_FILE.exists():
        return []
    return json.loads(DATA_FILE.read_text(encoding="utf-8"))


def save_todos(todos: list[dict]) -> None:
    """Write the todo list back to the file."""
    DATA_FILE.write_text(
        json.dumps(todos, ensure_ascii=False, indent=2),
        encoding="utf-8",
    )


@app.command()
def add(item: str):
    """Add a todo."""
    todos = load_todos()
    todos.append({"item": item, "done": False})
    save_todos(todos)
    print(f"Added: {item}")


@app.command(name="list")
def list_todos():
    """List all todos."""
    todos = load_todos()
    if not todos:
        print("No todos yet - add one first")
        return
    for i, t in enumerate(todos, start=1):
        mark = "[x]" if t["done"] else "[ ]"
        print(f"{i}. {mark} {t['item']}")


@app.command()
def done(index: int):
    """Mark todo number index as done."""
    todos = load_todos()
    if index < 1 or index > len(todos):
        print(f"The number must be between 1 and {len(todos)}")
        raise typer.Exit(code=1)
    todos[index - 1]["done"] = True
    save_todos(todos)
    print(f"Done: {todos[index - 1]['item']}")


if __name__ == "__main__":
    app()
```

Notice a few details –

- `list` is a Python built-in function, so it's better not to use it as a function name. The function is called `list_todos`, but `@app.command(name="list")` registers it as the `list` command
- `Path.home() / ".todo-cli.json"` uses `pathlib`, which is much more elegant than `os.path.join` (see the `python18` chapter)
- `typer.Exit(code=1)` raises a special exception that makes the CLI exit with a non-zero exit code, so scripts can tell whether it succeeded
- The file uses `encoding="utf-8"`, so non-English text works on Windows too

### Step 3: Configure pyproject.toml

## Summary

In this chapter, we've conquered two things – "packaging and publishing" and "writing CLIs". Let's review the key points –

**About PyPI**:

1. **PyPI is Python's global public package repository** – where `pip install` gets things from
2. **TestPyPI is the practice ground** – try a release there first, because PyPI versions can't be taken back
3. **Modern Python projects use `src layout` + `pyproject.toml`**, with all the metadata in one file
4. **The minimum fields in the `[project]` section**: name, version, description, readme, requires-python, dependencies
5. **The `[build-system]` section names the packaging back end** – `hatchling` is the first choice for new projects
6. **One `uv build` command packages the project**, producing a `wheel` (ready-built) and an `sdist` (source)
7. **One `uv publish` command uploads it**, using a token or trusted publishing
8. **Automate version numbers** – use `hatch-vcs` to work them out from git tags
9. **For automatic publishing in CI, use trusted publishing** – cleaner than tokens: add a tag, publish a release

**About typer**:

10. **`typer` uses type hints directly as CLI parameters** – 10 times simpler than `argparse`
11. **`typer.run(func)` suits single-command tools**; `Typer()` + `@app.command()` suits multi-command tools
12. **Types are validation** – `int` is checked automatically, `Path` is wrapped automatically, `Enum` limits the values automatically
13. **No default value = positional argument (required); a default value = option (optional)**
14. **`[project.scripts]` turns a function into a system command**, available everywhere once the package is installed
15. **Docstrings automatically become command help text** – writing code is writing documentation

Now you have a complete chain: "write a tool → package it → publish it → let the whole world use it". Next time you want to share a little tool with a friend, don't send `tool.py` in a chat message – just say "`pip install xxx`". Very cool.
