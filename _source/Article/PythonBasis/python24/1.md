# ruff: one tool to replace black + flake8 + isort + pyupgrade

Do you remember back in 2022? When you started a new Python project, just "keeping the code style consistent" meant installing a pile of things:

- `black`: formats code automatically – handles indentation, line breaks and quotes
- `flake8`: checks for syntax errors, unused variables and bad names
- `isort`: rearranges `import` statements in alphabetical order and in groups
- `pyupgrade`: upgrades old syntax to newer versions, e.g. `Dict[str, int]` to `dict[str, int]`
- `pydocstyle`: checks whether docstrings are written properly
- `bandit`: scans for security problems

Six tools, six config files, six sets of rules. Install each one separately, run each one in CI, call each one before every commit. Back then, setting up the lint pipeline for a new project, Brother Shui could spend half a day just working out how to stop these tools fighting each other.

"Can't they be combined?" Lots of people asked that back then.

They couldn't. These tools were independent, and built in different ways: `black` was written in `Python`, `flake8` was written in `Python` but built on `pycodestyle`, and `isort` was its own separate project. Combining them meant rewriting everything.

Then, at the end of 2022, Astral – the same Astral that made `uv` in the last chapter – released something called `ruff`. This company has a speciality: rewriting Python tools in `Rust`, and making them **10 to 100 times faster than the originals**.

From the start, `ruff` implemented the rules of `flake8`, `isort`, `pyupgrade`, `pydocstyle`, `bandit` and others all at once. Later it added a `format` command that swallowed up `black`'s job too. One program, one config, one set of commands.

By 2024, `ruff` had become the standard in the Python community. `Pandas`, `FastAPI`, `Pydantic`, `Hugging Face Transformers` and `Apache Airflow` all switched to it. Today in 2026, almost nobody would recommend the old `flake8 + black + isort` combination for a new project.

This chapter is about how to use `ruff`. After it, you should be able to:

1. Set up `ruff` in a new project in five minutes
2. Understand the `[tool.ruff]` settings in someone else's `pyproject.toml`
3. Connect `ruff` to `pre-commit`, `CI` and your editor
4. Smoothly move an old project over from `black + flake8 + isort`


## What was so annoying about the old way?

First, let's remember how the old way worked. A fairly "proper" project would usually have these config files in its root folder:

```
my-project/
├── pyproject.toml         # Settings for some tools
├── setup.cfg              # flake8 settings had to go here (or in a separate .flake8)
├── .flake8                # flake8 settings (optional)
├── .isort.cfg             # isort settings (optional)
├── .pre-commit-config.yaml
└── ...
```

Each tool had its own favourite place for settings:

- `black` read `[tool.black]` in `pyproject.toml`
- `flake8` absolutely refused to support `pyproject.toml` – only `.flake8` or `setup.cfg`
- `isort` could use `pyproject.toml`, `.isort.cfg` or `setup.cfg` – whichever you liked
- `pyupgrade` had no config file at all – only command-line options

That's the first trap – **settings scattered everywhere**. A newcomer taking over a project could spend ages just finding the config files.

The second trap was that **the tools fought each other**. The classic one is `black` vs `flake8`. `black`'s default line length is 88 characters; `flake8`'s default is 79 (the PEP 8 recommendation). If you didn't make them match, `black` would format the code and then `flake8` would complain `E501 line too long`. What to do? Change `flake8`, change `black`, or add `# noqa` comments everywhere.

`isort` and `black` fought too. `isort` sorted `import`s in a certain style by default, which `black` didn't always accept. You had to add `--profile black` to `isort` to make them agree.

The third trap was **slowness**. Not "feels a bit slow" – really slow. On a medium-sized project, `flake8 .` took seconds to tens of seconds; `black .` took several to a dozen seconds; `isort .` took a few seconds too. Run them one after another in CI, and tens of seconds were gone. Running lint every time you saved a file was too slow to connect to your editor.

That was the reality of Python tooling before 2022. Experienced programmers reading this will know the feeling.


## What is ruff?

`ruff` is an open-source Python code checker + formatter from Astral. Two key features:

1. **It's written in Rust.** Python tools written in Python hit a speed ceiling. Switch to Rust, and they get one or two orders of magnitude faster.
2. **One tool replaces a whole pile.** `flake8`, `black`, `isort`, `pyupgrade`, `pydocstyle`, `bandit`, some of `pylint`'s rules and `autoflake` – all built in.

Look at the speed comparison `ruff` published, run on the `CPython` project (about 250,000 lines of code):

| Tool | Time |
|---|---|
| `flake8` | About 12 seconds |
| `pylint` | Several minutes |
| `ruff check` | About 0.4 seconds |

You might be suspicious: "Is it really that fast? Are the numbers made up?" Brother Shui has tried it on his own computer, and **yes, it really is that fast**. On a project with a thousand files, `ruff check .` often finishes in under a second – you can't even see it "running".

`ruff format` is similar. On a medium-sized project, `black` takes a dozen seconds; `ruff format` takes less than one.

What's the point of that speed? Two important things:

1. **Running lint live every time you save** becomes possible. Every time you press `Ctrl+S` in your editor, `ruff` runs in the background, and you hardly notice any delay.
2. **Shorter CI times.** The lint step used to take 30 seconds; now it's done in 1.

"How many rules does it support?" some of you will want to know. As of 2026, `ruff` has implemented over 800 rules, covering mainstream `flake8` + dozens of `flake8-*` plugins + `isort` + `pyupgrade` + `pydocstyle` + part of `pylint` + part of `bandit`. In other words, `ruff` has taken in the abilities of almost every mainstream Python lint tool.


## Installing

As usual, we recommend installing with `uv`:

```bash
uv add --dev ruff
```

"What does `--dev` mean?" We covered it in the last chapter – it means "install into the development dependency group", so it isn't included when you release to production. `ruff` is a development tool, only used while developing and in CI, so `--dev` is the right place.

If your project doesn't use `uv` yet, you can install with `pip` too:

```bash
pip install ruff
```

Or install it as a global command with `pipx`:

```bash
pipx install ruff
```

After installing, check it:

```bash
ruff --version
```

Output similar to:

```
ruff 0.8.0
```

The exact version number will change – in 2026, `ruff` is probably past 0.9 or even 1.0.

"Why hasn't the version even reached 1.0?" a sharp-eyed student might ask. `ruff`'s authors keep improving it in small steps, and the rule set keeps growing, so the version number stayed at 0.x. But it's been stable enough for production for a long time – lots of community projects use it without any major problems.


## Running it for the first time

Go into your project folder and run:

```bash
ruff check .
```

This scans every `.py` file in the current folder and checks it against the default rules. The first time, you'll probably see a pile of warnings:

```
foo.py:3:1: F401 [*] `os` imported but unused
foo.py:8:5: E731 Do not assign a `lambda` expression, use a `def`
bar.py:12:80: E501 Line too long (95 > 79)
```

The format is clear: `file:line:column: rule-code description`. If the rule code has a `[*]` in front of it, that rule can be **fixed automatically**.

To let `ruff` fix things automatically, add `--fix`:

```bash
ruff check --fix .
```

After this, problems like "`os` imported but unused" are fixed – `ruff` simply deletes that `import os` line. Run `ruff check .` again, and most of the warnings are gone.

To format code, use another command:

```bash
ruff format .
```

This works basically the same as `black .` – it makes the whole project's style consistent: indentation, quotes and line breaks. If you've used `black` before, there's nothing new to learn.

Put these two commands together, and you have the standard routine before every commit:

```bash
ruff check --fix . && ruff format .
```

Lint first, then format – done.


## Settings: pyproject.toml

All of `ruff`'s settings go into `pyproject.toml` – no other files. The settings look like this:

```toml
[tool.ruff]
# Line length – same as black's default
line-length = 88

# The target Python version – affects how some rules decide
target-version = "py312"

# Which folders to skip
exclude = [
    ".git",
    ".venv",
    "build",
    "dist",
    "__pycache__",
    "migrations",
]

[tool.ruff.lint]
# Which rule sets to turn on
select = ["E", "F", "I", "UP", "B", "SIM"]

# Which specific rules to ignore
ignore = ["E501"]

[tool.ruff.format]
# Quote style: prefer double quotes (black style)
quote-style = "double"
# Indentation style: spaces
indent-style = "space"
```

That might look confusing, so let's take it apart piece by piece.

### line-length

The line length. Default 88, same as `black`. If you prefer 100:

```toml
line-length = 100
```

### target-version

The target Python version. This affects how some rules decide. For example, with `target-version = "py312"`, `ruff` knows you can use syntax like `dict[str, int]`, and will suggest changing old code's `Dict[str, int]`. If you write `target-version = "py38"`, `ruff` won't suggest that (because 3.8 doesn't support it).

Valid values: `py38`, `py39`, `py310`, `py311`, `py312`, `py313`, `py314`.

### exclude

Which folders not to scan. `ruff` skips `.git`, `.venv`, `build`, `dist` and so on by default, but folders like `migrations` (migration files generated automatically by Django) you need to add yourself.

### select

The most important field – **which rule sets to turn on**. `ruff` groups rules by **letter prefixes**:

- `E`: `pycodestyle` errors (PEP 8 style rules)
- `W`: `pycodestyle` warnings
- `F`: `pyflakes` (unused variables, undefined names, etc.)
- `I`: `isort` (import sorting)
- `UP`: `pyupgrade` (suggestions to upgrade syntax)
- `B`: `flake8-bugbear` (common bug patterns)
- `SIM`: `flake8-simplify` (suggestions to simplify code)
- `N`: `pep8-naming` (naming rules)
- `D`: `pydocstyle` (docstring rules)
- `S`: `flake8-bandit` (security checks)
- `ANN`: `flake8-annotations` (type hints)
- `C4`: `flake8-comprehensions` (improving comprehensions)
- `RET`: `flake8-return` (return statement rules)
- `ARG`: `flake8-unused-arguments` (unused arguments)

Under each prefix are specific rules. For example, `E501` is "line too long", and `F401` is "imported but not used".

For a new project's first setup, we recommend this set:

```toml
select = ["E", "F", "I", "UP", "B", "SIM"]
```

`E + F` are the basics (PEP 8 + pyflakes), `I` sorts imports, `UP` upgrades old syntax, `B` catches common bugs, and `SIM` gives some simplifying suggestions. These six groups cover 80% of what you need without too much noise.

If your project needs high code quality, add `N` (naming), `C4` (comprehensions), `RET` (returns) and `ARG` (unused arguments).

If you also want docstring checks (`D`), be mentally prepared – `pydocstyle`'s rules are very strict, and an old project will get hundreds of warnings straight away. Try `select = ["D"]` + `ignore = ["D100", "D101", "D102", ...]` one rule at a time – don't switch them all on at once.

### ignore

Ignore some specific rules. For example, some projects find 88 characters too short, so they add `E501` (line too long) to `ignore`:

```toml
ignore = ["E501"]
```

Or ignore a whole group:

```toml
ignore = ["D"]
```

### per-file-ignores

Ignore rules for particular files. `__init__.py` often has imports that look unused (they're really there to re-export things). To stop those warnings:

```toml
[tool.ruff.lint.per-file-ignores]
"__init__.py" = ["F401"]
"tests/*" = ["S101", "ANN"]
```

In `tests/*`, `assert` is allowed (`S101`), and test functions don't need type hints (`ANN`).

### isort sub-settings

The `I` rule set (the isort replacement) has its own sub-settings, under `[tool.ruff.lint.isort]`:

```toml
[tool.ruff.lint.isort]
# Treat these as "first-party" packages, sorted separately from third-party ones
known-first-party = ["my_project"]

# The order of groups in an import block
section-order = [
    "future",
    "standard-library",
    "third-party",
    "first-party",
    "local-folder",
]
```

`known-first-party` is used a lot – it tells `ruff` "`my_project` is my own package", so `ruff` puts its `import`s in a separate group, not mixed in with third-party packages.


## A complete settings example

Here's a production-ready `pyproject.toml` setup you can copy and adapt:

```toml
[tool.ruff]
line-length = 88
target-version = "py312"
exclude = [
    ".git",
    ".venv",
    "build",
    "dist",
    "__pycache__",
    "migrations",
    "*.ipynb",
]

[tool.ruff.lint]
select = [
    "E",   # pycodestyle errors
    "W",   # pycodestyle warnings
    "F",   # pyflakes
    "I",   # isort
    "UP",  # pyupgrade
    "B",   # flake8-bugbear
    "SIM", # flake8-simplify
    "C4",  # flake8-comprehensions
    "N",   # pep8-naming
    "RET", # flake8-return
]
ignore = [
    "E501",  # Line too long – let the formatter handle it
    "B008",  # Calling a function in a default argument – FastAPI's Depends uses this
]

[tool.ruff.lint.per-file-ignores]
"__init__.py" = ["F401"]
"tests/*" = ["S101"]

[tool.ruff.lint.isort]
known-first-party = ["my_project"]

[tool.ruff.format]
quote-style = "double"
indent-style = "space"
line-ending = "auto"
```

Copy this, change `target-version` and `known-first-party`, and it should basically work.


## Common rule sets at a glance

Here are the rule sets above in one table, for easy reference:

| Prefix | Original tool | What it checks |
|---|---|---|
| `E` | `pycodestyle` | PEP 8 style errors (indentation, spaces) |
| `W` | `pycodestyle` | PEP 8 style warnings |
| `F` | `pyflakes` | Unused variables, undefined names, import mistakes |
| `I` | `isort` | Import sorting and grouping |
| `UP` | `pyupgrade` | Upgrading old syntax to newer versions |
| `B` | `flake8-bugbear` | Common bug patterns |
| `SIM` | `flake8-simplify` | Suggestions to simplify code |
| `N` | `pep8-naming` | Naming rules (CamelCase, underscores) |
| `D` | `pydocstyle` | Docstring rules |
| `S` | `flake8-bandit` | Security checks |
| `ANN` | `flake8-annotations` | Type hint checks |
| `C4` | `flake8-comprehensions` | Improving comprehensions |
| `RET` | `flake8-return` | Return statement style |
| `ARG` | `flake8-unused-arguments` | Unused arguments |
| `PT` | `flake8-pytest-style` | pytest style |
| `PL` | `pylint` | Some pylint rules |
| `RUF` | `ruff` | ruff's own original rules |

The full list is in the official docs, on the "Rules" page, which clearly lists each rule code, its description, and whether it can be fixed automatically. If you don't understand a rule, just search for its code.


## Automatic fixes in practice

What can `ruff check --fix .` fix? Let's look at some common ones.

### F401: unused import

```python
import os
import sys

print(sys.version)
```

After `ruff check --fix`:

```python
import sys

print(sys.version)
```

`os` wasn't used, so it's deleted.

### E711: compare with None using `is`

<!-- skip-ci -->
```python
if x == None:
    print("x is None")
```

After fixing:

<!-- skip-ci -->
```python
if x is None:
    print("x is None")
```

Why change it? Because `==` calls the `__eq__` method, and some classes implement `__eq__` in strange ways (like `numpy` arrays), so comparing with `None` can give surprising results. `is None` compares **identity** – it only asks "is this the very same object?" – so it's always safe.

### C408: unnecessary list/dict/tuple calls

```python
empty = list()
d = dict()
t = tuple()
```

After fixing:

```python
empty = []
d = {}
t = ()
```

`list()` and `[]` mean the same, but `list()` has to look up the name `list` in the global namespace and then call it, which is a little slower. Writing the literal directly is faster and shorter.

### UP006: use the new type hint style

```python
from typing import List, Dict

def foo(x: List[int]) -> Dict[str, int]:
    pass
```

After fixing (with `target-version = "py39"` or higher):

```python
def foo(x: list[int]) -> dict[str, int]:
    pass
```

Python 3.9+ supports `list[int]` directly in type hints, so you don't need to import from `typing` any more. `ruff` upgrades it for you automatically.

### UP008: use super() without arguments

<!-- skip-ci -->
```python
class Foo(Bar):
    def __init__(self):
        super(Foo, self).__init__()
```

After fixing:

<!-- skip-ci -->
```python
class Foo(Bar):
    def __init__(self):
        super().__init__()
```

In Python 3, `super()` with no arguments is enough. The old Python 2 style `super(Foo, self)` is just historical baggage.

### SIM108: use a conditional expression instead of if-else

<!-- skip-ci -->
```python
if x > 0:
    y = "positive"
else:
    y = "non-positive"
```

`ruff` will suggest (this one isn't fixed automatically, because it affects readability and needs a human to decide):

<!-- skip-ci -->
```python
y = "positive" if x > 0 else "non-positive"
```

### I001: import sorting

<!-- skip-ci -->
```python
import sys
from my_project import utils
import os
import requests
```

After fixing:

<!-- skip-ci -->
```python
import os
import sys

import requests

from my_project import utils
```

`ruff` sorts imports into three groups – "standard library → third-party → first-party" – with a blank line between groups, and alphabetical order inside each group. This is the same as running `isort`.

### Unsafe fixes

Some fixes `ruff` won't do by default, because they might change behaviour. For example, changing `dict()` to `{}` – in 99% of cases they're the same, but if the name `dict` has been overwritten in your code, the behaviour changes. These are called **unsafe fixes**, and you need `--unsafe-fixes` to apply them:

```bash
ruff check --fix --unsafe-fixes .
```

If you're not sure, run the safe fixes first with `ruff check --fix .`, then run `--unsafe-fixes` separately and review the changes.


## ruff format: the black replacement

`ruff format .` does almost exactly what `black .` does:

- Line length 88 by default
- Double quotes for strings by default
- 4-space indentation
- Automatically breaks function arguments that are too long onto new lines
- Lays out dict, list and `set` literals in a consistent style

Before formatting:

```python
def foo(a,b,c, d ):
    return  {  'name':a,'age':b,'list':[1,2,3]  }
```

After `ruff format .`:

```python
def foo(a, b, c, d):
    return {"name": a, "age": b, "list": [1, 2, 3]}
```

Almost exactly the same as `black`'s output. Astral's docs clearly say "`ruff format` is 99.9% compatible with `black`", so moving from `black` won't suddenly change your code style.

There are a few small differences, mainly in edge cases (extremely long lines, special magic comments and so on). Run `ruff format` and check `git diff` to see them.

`ruff format` also has a `--check` mode that checks without changing anything:

```bash
ruff format --check .
```

If any files need formatting, the command returns a non-zero exit code. You can use this in CI to block pull requests that "forgot to format before committing".


## Connecting to pre-commit

`pre-commit` is a git hook framework that runs checks automatically when you `git commit`. Install it:

```bash
uv add --dev pre-commit
pre-commit install
```

Then create `.pre-commit-config.yaml` in the project's root folder:

```yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.8.0
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
```

This config does two things:

1. The `ruff` hook: runs `ruff check --fix`, fixing whatever can be fixed automatically
2. The `ruff-format` hook: runs `ruff format`

Every time you `git commit`, `pre-commit` runs these two hooks automatically, and only lets the commit through if they pass.

"What do I put for `rev: v0.8.0`?" `pre-commit` has a command that fills in the newest version automatically:

```bash
pre-commit autoupdate
```

Run it, and the version number in `.pre-commit-config.yaml` is updated to the newest. I suggest running this every few months.

After installing `pre-commit` for the first time, you can run it by hand once:

```bash
pre-commit run --all-files
```

This goes through every file in the project and clears out all the old problems in one go.

"Why not just use `ruff`'s own hook?" some of you will ask. `ruff` doesn't have its own git hook system – it relies on a general framework like `pre-commit`. `pre-commit` is the standard solution in the Python world, and besides `ruff` it can run other hooks too (like `mypy` and `prettier`), all managed in one place.


## Connecting to GitHub Actions CI

Using `ruff` in CI is very simple. Create `.github/workflows/lint.yml`:

```yaml
name: Lint

on:
  push:
    branches: [main]
  pull_request:

jobs:
  ruff:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install uv
        uses: astral-sh/setup-uv@v3

      - name: Install ruff
        run: uv tool install ruff

      - name: Run ruff check
        run: ruff check --output-format=github .

      - name: Run ruff format check
        run: ruff format --check .
```

The `--output-format=github` option is important – it outputs warnings in a format GitHub Actions understands, so the pull request page shows a little marker right on the problem line. Hover over it to see the rule and explanation. Much better than a plain text log.

There's also an official action that's even easier:

```yaml
- name: Run ruff
  uses: astral-sh/ruff-action@v3
```

This action installs `ruff` and runs `ruff check` automatically – one line. If you're interested, search GitHub for `astral-sh/ruff-action` to read its docs.

As for CI time, the `ruff` part usually finishes within 5 seconds (including setting up the environment) – much faster than the old `flake8 + black + isort` set.

"Can it fix things automatically on a pull request and commit them back?" It can, but you have to handle permissions and forked pull requests carefully. The usual approach is: CI only checks, doesn't fix; developers fix things locally and push again. Automatic fix pull requests need a special bot account + a GitHub App, which is beyond this chapter.


## Connecting to your editor

The last mile for code style tools is your editor. Once it's set up, every time you save a file, your editor runs `ruff` automatically, and problems show up right on the lines they're in. This experience can't be replaced by CI or `pre-commit`: CI is the safety net, the editor is for every day.

### VS Code

Install this extension: [Ruff (charliermarsh.ruff)](https://marketplace.visualstudio.com/items?itemName=charliermarsh.ruff)

Then add a few lines to `settings.json`:

```json
{
    "[python]": {
        "editor.defaultFormatter": "charliermarsh.ruff",
        "editor.formatOnSave": true,
        "editor.codeActionsOnSave": {
            "source.fixAll.ruff": "explicit",
            "source.organizeImports.ruff": "explicit"
        }
    }
}
```

The effect:

- Runs `ruff format` automatically when you save a file
- Applies every lint fix that can be done automatically
- Tidies up imports automatically

While you write code, every `Ctrl+S` runs `ruff` in the background, and your code tidies itself up.

### PyCharm

PyCharm has an officially supported `Ruff` plugin. Go to `Settings → Plugins`, search for "Ruff" and install it.

After installing:

- `Settings → Tools → Ruff`: tick "Use ruff format" and "Run ruff on save"
- `Settings → Editor → Code Style → Python`: change the line length to 88, to match `ruff`

The nice thing about PyCharm is that checks show live while you edit, without waiting for a save. Problem code gets a yellow wavy line – hover over it to see the rule.

### Neovim / Vim

Install `ruff`'s LSP server through `nvim-lspconfig` + `mason.nvim`:

```lua
require("lspconfig").ruff.setup({})
```

Or use the `ruff` integration in `null-ls` / `none-ls`. Which one depends on your Neovim config framework.


## Moving over from black + flake8 + isort

How do you switch an old project? Here are the steps:

### Step 1: install ruff

```bash
uv add --dev ruff
```

### Step 2: write the ruff settings

Using the "complete settings example" above, write a `[tool.ruff]` section into `pyproject.toml`. Match key settings like `line-length` and `target-version` to your old `black` settings.

### Step 3: run it and look at the differences

```bash
ruff check .
ruff format --check .
```

`ruff check .` shows lint warnings, and `ruff format --check .` shows formatting differences.

`ruff format` is 99.9% compatible with `black`, but a few files will still change. Run `ruff format .` first, look at `git diff`, and commit once you're happy with the changes.

### Step 4: remove the old tools

```bash
uv remove --dev black flake8 isort pyupgrade
```

If the project still uses `pip` + `requirements-dev.txt`, remove them from there.

### Step 5: remove the old settings

Delete `.flake8`, delete the `[flake8]` section in `setup.cfg`, and delete the `[tool.black]` and `[tool.isort]` sections in `pyproject.toml`.

### Step 6: update pre-commit and CI

In `.pre-commit-config.yaml`, remove the `black`, `flake8` and `isort` hooks and replace them with `ruff`'s. Same for CI.

### Step 7: tell the team

Send the team a message: "From [date], this project uses ruff. Please pull the latest code and run `pre-commit install` to reinstall the hooks." This step usually goes smoothly, because `ruff format` is compatible with `black`, so code already formatted by `black` won't change much.


## ruff vs black + flake8 + isort – comparison table

Finally, a comparison table so you've got the full picture:

| Aspect | The old combo | ruff |
|---|---|---|
| Number of tools | At least 3 (black + flake8 + isort), more with pyupgrade and pydocstyle | 1 |
| Where settings live | Scattered across `pyproject.toml`, `.flake8`, `setup.cfg`, etc. | All in `pyproject.toml` |
| Speed | Seconds to tens of seconds | Usually under 1 second |
| Number of rules | About 500 between them | 800+ |
| Automatic fixes | Partly (black, isort, pyupgrade fix automatically; flake8 doesn't) | Most rules |
| Written in | Python | Rust |
| Installation | Python packages | A single program (can also be pip-installed) |
| Live lint in the editor | Slow, poor experience | Fast, smooth experience |
| pyproject.toml support | Partial (flake8 doesn't support it) | Full |


## ruff's own rules: the RUF series

Besides copying other tools' rules, `ruff` has invented some rules of its own, with the prefix `RUF`. Let's look at a few common ones.

### RUF001/RUF002/RUF003: confusable characters

If your code has characters that "look like English letters but are actually Greek letters or full-width characters", it triggers `RUF001`. For example:

<!-- skip-ci -->
```python
result = data["nаme"]  # The а here is the Cyrillic letter а, not the English a
```

You can hardly see the difference, but when the program runs it can't find the key and raises a `KeyError`. `ruff` spots characters like this and warns you, saving you from debugging until you doubt everything.

### RUF005: use unpacking instead of joining lists

<!-- skip-ci -->
```python
new_list = [1, 2, 3] + list(other)
```

`ruff` suggests changing it to:

<!-- skip-ci -->
```python
new_list = [1, 2, 3, *other]
```

Unpacking is faster and shorter, and it can join any iterable directly, without turning it into a list first.

### RUF013: implicit Optional types

<!-- skip-ci -->
```python
def greet(name: str = None):
    print(f"Hello, {name}")
```

This is very common, but there's a problem – `name` defaults to `None`, but its type hint says `str`. They don't match. `ruff` suggests:

<!-- skip-ci -->
```python
def greet(name: str | None = None):
    print(f"Hello, {name}")
```

The old Python way was `Optional[str]`; in newer Python (3.10+), `str | None` is cleaner.

### RUF100: unused noqa

```python
x = 1  # noqa: F401
```

If this line actually has no lint warnings, that `# noqa` is just rubbish. `ruff` specifically marks these "out-of-date noqa" comments, reminding you to delete them.

This rule is really useful – after moving an old project to `ruff`, most of the `# noqa` comments you added for `flake8` will be out of date, and `RUF100` finds them all.


## A common trap: how it relates to mypy

Lots of people ask: "Can `ruff` replace `mypy`?"

**No.**

`ruff` is a linter + formatter. It checks "code style and common error patterns". `mypy` is a **type checker**. It works out types across the whole program, like "is the type of this variable right for that function?". They're tools for different jobs, and you use them together.

The right approach:

- Use `ruff` for style, imports, obvious bugs and syntax upgrades
- Use `mypy` or `pyright` for types

Run both in CI:

```yaml
- run: ruff check .
- run: ruff format --check .
- run: mypy .
```

`ruff` does have some rules (prefix `ANN`) that do basic type hint checks, like "this function has no return type". But it **doesn't** really work out whether types are consistent. For complicated type problems, you still need `mypy`.


## An advanced trick: different rules for different folders

Big projects often want "strict rules for the core code, relaxed rules for the scripts folder". Since 0.5, `ruff` supports **overriding settings for sub-folders**, using `[tool.ruff.lint.per-file-ignores]` with glob patterns. We saw a simple use earlier; here's a more complicated one:

```toml
[tool.ruff.lint.per-file-ignores]
# Test files may use assert, and can be a bit longer
"tests/**/*.py" = ["S101", "ANN", "D"]

# One-off scripts – the loosest rules
"scripts/*.py" = ["ALL"]

# Documentation example code – print is allowed
"docs/examples/*.py" = ["T20"]

# Leave migration files alone
"**/migrations/*.py" = ["E", "F", "I", "UP", "B"]
```

`"ALL"` is a special value meaning "ignore every rule". So the `scripts/*.py` line means `ruff` doesn't check anything in the scripts folder – write it however you like.

### Nested settings

If your project is a **monorepo** with several sub-projects, and each one wants its own `ruff` settings, put a separate `pyproject.toml` or `ruff.toml` in the sub-folder:

```
mono/
├── pyproject.toml          # Root settings
├── service-a/
│   ├── pyproject.toml      # service-a's own settings (optional)
│   └── ...
└── service-b/
    ├── ruff.toml           # service-b's own settings
    └── ...
```

When `ruff` checks each file, it looks upwards for the nearest settings file. The sub-projects don't interfere with each other.


## An advanced trick: noqa comments

Sometimes you really do want `ruff` to be quiet. For example, a line uses `eval()` for a very good reason, but `S307` (`flake8-bandit`) warns about it. Then you can add a `# noqa` comment:

<!-- skip-ci -->
```python
result = eval(user_input)  # noqa: S307
```

`# noqa: S307` means "ignore rule S307 on this line". Separate several rules with commas:

<!-- skip-ci -->
```python
result = eval(user_input)  # noqa: S307, S102
```

A bare `# noqa` (without a rule code) works too, but isn't recommended – it ignores **every** rule on that line, like switching off all the lights. Naming the rule is the most precise.

Before writing `# noqa`, think: is the rule unreasonable, or should the code itself be changed? Most of the time, it's the second one.


## A few easy traps

Finally, here are some traps that even experienced programmers fall into after moving to `ruff`. Knowing them in advance will save you time.

### Trap 1: the wrong prefix in select, so rules don't turn on

How specific the prefix is decides how many rules you get. Prefixes match like the start of a word:

- `"E"`: turns on every rule starting with E (E1xx, E2xx, E5xx…)
- `"E1"`: turns on every rule starting with E1 (E1xx)
- `"E101"`: turns on only rule E101

If a prefix doesn't match the rules you expected, nothing you wanted gets turned on – and you won't get an error about it. If you can't remember, start with broad groups like `["E", "F", "I"]` – as long as it works.

### Trap 2: writing both select and ignore

```toml
select = ["E"]
ignore = ["E501"]
```

This means "turn on the whole E group, except E501". It's completely valid – **ignore wins**. You'll often see this "turn on a group + leave out one or two" pattern. It's standard.

### Trap 3: ruff format doesn't read [tool.ruff.lint] settings

`[tool.ruff.lint]` controls lint, and `[tool.ruff.format]` controls formatting – **they're completely separate**. The most common trap: you set `quote-style = "double"` in `[tool.ruff.lint]`, but `ruff format` still uses the default style, because `quote-style` belongs in `[tool.ruff.format]`.

```toml
# Wrong place
[tool.ruff.lint]
quote-style = "double"  # Writing it here does nothing

# Right place
[tool.ruff.format]
quote-style = "double"
```

### Trap 4: preview rules

`ruff` also has a set of **preview** rules still being developed, which are off by default. To turn them on:

```toml
[tool.ruff.lint]
preview = true
```

Or use `ruff check --preview` on the command line. The good thing about preview rules is getting new features early. The bad thing is that rule codes and behaviour might change between versions. For production projects, play it safe – **don't turn on preview by default**.

### Trap 5: forgetting to update the pre-commit hook version

The `rev: v0.8.0` in your `.pre-commit-config.yaml` is fixed – when `ruff` releases a new version, it doesn't sync automatically. Six months later, the old `ruff` can't run the new rules, and different team members having different `ruff` versions causes problems too.

Suggestion: run `pre-commit autoupdate` every month or every quarter to bring all the hook versions up to date. Update CI at the same time.

## Deal with one check result you understand at a time

When a code checker outputs a long list of rule codes, first pick **one** problem you can explain. Don't rush to turn on every rule. Do a read-only check in the final exercise's folder:

```bash
ruff check .
ruff format --check .
```

The first command checks the rules that are turned on; the second checks whether the formatting needs adjusting. The actual output depends on the version, settings and what's in your files – it doesn't need to match some old screenshot exactly.

If you find an unused import, first find it, make sure it really isn't used, and then fix it in your own practice file. Write down the rule code, the reason and the change, then run the check again. When you meet a rule you don't know, look it up in the [Ruff rules list](https://docs.astral.sh/ruff/rules/) to see what it checks and whether there are situations where it doesn't apply.

Next, deliberately break the addition in the totals function, and check again. You'll see that a style checker doesn't decide "what the total study time should be". Running tests is still necessary. And the other way round: passing tests doesn't mean the code is clear and easy to read. Both kinds of checks are useful in their own way.

Work in your own practice folder first. Before letting a tool change things automatically, read the reason it reports. After changing, run the tests again to confirm the program's results haven't changed.
