Have you ever written code like this?

```python
import os

base_dir = os.path.dirname(os.path.abspath(__file__))
data_path = os.path.join(base_dir, 'data', 'sub', 'foo.txt')

if os.path.exists(data_path) and os.path.isfile(data_path):
    with open(data_path, 'r', encoding='utf-8') as f:
        content = f.read()
    print(content)
```

Does it make your head hurt? An `os.path.dirname` wrapped around an `os.path.abspath`, plus an `os.path.join` – the path gets built layer by layer. To open it, you need `with open(...) as f:`. To check it, you need `os.path.exists` plus `os.path.isfile`. The functions are spread across two modules, `os` and `os.path`, plus the built-in `open` function. Just counting the function names makes Brother Shui dizzy.

Even worse, in this style a path is just a normal **string**. A string is just a string – it doesn't know whether it's a file or a folder, and it certainly can't check "do I exist?" or "what's my extension?" by itself. For every operation, you have to feed the string into a function, the function spits out a string, and that string goes to the next function… The whole thing is like a factory line passing bricks along.

Is there a way to make paths "come alive"? So that something like `Path('data/foo.txt')` itself knows whether it's a file, whether it can be read, and what its extension is?

Yes – that's `pathlib`, today's topic. It's a standard library module added in Python 3.4, made specifically to clean up messy path code like the above. Since Python 3.6, most standard library functions that accept path strings can also take `Path` objects directly, so switching over is almost painless.

Python is up to 3.13 now. If you're still using `os.path.join` for everything, you're really missing out. In this article, follow Brother Shui as we go through the modern `pathlib` API from start to finish.



## 1. Your first Path

First, let's meet the star of the show:

```python
from pathlib import Path

p = Path('data/foo.txt')
print(p)
print(type(p))
```

The output might look like this (on macOS / Linux):

```
data/foo.txt
<class 'pathlib.PosixPath'>
```

Notice something odd? We wrote `Path('data/foo.txt')`, so why is the type `PosixPath`?

Because `Path` is clever. It looks at your operating system and automatically gives you the right subclass for that platform:

- On macOS / Linux, it returns a `PosixPath`
- On Windows, it returns a `WindowsPath`

You usually don't need to care about this. Just use `Path`, and worry about cross-platform details when you need to.

Besides the basic `Path('string')`, there are two very common "shortcuts":

```python
from pathlib import Path

print(Path.home())
print(Path.cwd())
```

Output:

```
/Users/two_water
/Users/two_water/projects/demo
```

`Path.home()` is the current user's **home folder**, and `Path.cwd()` is the **current working directory**. These are the same as the old `os.path.expanduser('~')` and `os.getcwd()`, but the new way is clearly neater, isn't it?



## 2. Joining paths with `/`

Joining paths is the most common operation of all. Here's the old way:

```python
import os

base = '/tmp'
data_path = os.path.join(base, 'demo', 'sub', 'foo.txt')
print(data_path)
```

Output:

```
/tmp/demo/sub/foo.txt
```

`os.path.join` works fine, but you have to say "os path join" again and again – your fingers get tired.

Now see how `pathlib` does it:

```python
from pathlib import Path

base = Path('/tmp')
data_path = base / 'demo' / 'sub' / 'foo.txt'
print(data_path)
```

Output:

```
/tmp/demo/sub/foo.txt
```

Look: we join paths with the `/` operator. A bit magical, isn't it?

Why does this work? Because `Path` overrides `__truediv__` (the division operator), so `Path('/tmp') / 'demo'` is turned into joining paths. This design is genius, because URLs and Linux file systems already use `/` for paths – it matches exactly what we have in our heads.

Here's a comparison table – see how much cleaner it is:

| Old way | New way |
| --- | --- |
| `os.path.join(a, b, c)` | `Path(a) / b / c` |
| `os.path.join(os.path.dirname(__file__), 'data')` | `Path(__file__).parent / 'data'` |
| `os.path.expanduser('~/Documents')` | `Path.home() / 'Documents'` |

You can also mix `Path` objects and strings with `/`. The result is always a `Path`:

```python
from pathlib import Path

p1 = Path('/tmp') / 'foo'
p2 = Path('/tmp') / Path('foo')
p3 = 'foo' / Path('tmp')

print(p1)
print(p2)
print(p3)
```

Output:

```
/tmp/foo
/tmp/foo
foo/tmp
```

Whether the string is on the left or the right of `/`, as long as one side is a `Path`, the result is a `Path`.



## 3. Common attributes, all in one go

If you've written web scrapers or file-handling code, you'll know tasks like "I've got a path, I want its file name" or "I want its extension". The old way spreads these across functions like `os.path.basename` and `os.path.splitext`, which are hard to remember.

`Path` turns them all into **attributes**. Let's look at them one by one.

### 3.1 `.name`: the full file name (with extension)

```python
from pathlib import Path

p = Path('/tmp/demo/foo.txt')
print(p.name)
```

Output:

```
foo.txt
```

Same as the old `os.path.basename(...)`.

### 3.2 `.stem`: the "stem" without the extension

```python
from pathlib import Path

p = Path('/tmp/demo/foo.txt')
print(p.stem)
```

Output:

```
foo
```

This is the file name without its extension. It's perfect for making a new file with the same name but a different extension, like turning `foo.txt` into `foo.json`.

### 3.3 `.suffix`: the extension (with the dot)

```python
from pathlib import Path

p = Path('/tmp/demo/foo.txt')
print(p.suffix)
```

Output:

```
.txt
```

Note that it includes the dot. If you want it without the dot, just slice it with `[1:]`.

What about a file with several extensions, like `foo.tar.gz`?

```python
from pathlib import Path

p = Path('archive.tar.gz')
print(p.suffix)
print(p.suffixes)
```

Output:

```
.gz
['.tar', '.gz']
```

See? `.suffix` gives only the last one, and `.suffixes` gives a list.

### 3.4 `.parent`: the parent folder

```python
from pathlib import Path

p = Path('/tmp/demo/sub/foo.txt')
print(p.parent)
```

Output:

```
/tmp/demo/sub
```

Same as `os.path.dirname(...)`, but much more natural to read.

### 3.5 `.parents`: all the ancestor folders

```python
from pathlib import Path

p = Path('/tmp/demo/sub/foo.txt')
for ancestor in p.parents:
    print(ancestor)
```

Output:

```
/tmp/demo/sub
/tmp/demo
/tmp
/
```

`.parents` returns a sequence, starting with the nearest parent folder and going up through all the ancestors. You can use indexes like `p.parents[0]` and `p.parents[1]`, or loop through it with `for`.

### 3.6 `.anchor`: the anchor

The anchor is the "root" part of a path.

```python
from pathlib import Path

p = Path('/tmp/demo/foo.txt')
print(p.anchor)
```

Output:

```
/
```

On Linux / macOS it's usually `/`. On Windows it might be a drive letter like `C:\`. You won't use this often, but it's occasionally handy in cross-platform code.

### 3.7 Putting it all together

Here's an example that uses all these attributes together:

```python
from pathlib import Path

p = Path('/Users/two_water/projects/demo/main.py')

print('name    :', p.name)
print('stem    :', p.stem)
print('suffix  :', p.suffix)
print('parent  :', p.parent)
print('anchor  :', p.anchor)
print('parts   :', p.parts)
```

Output:

```
name    : main.py
stem    : main
suffix  : .py
parent  : /Users/two_water/projects/demo
anchor  : /
parts   : ('/', 'Users', 'two_water', 'projects', 'demo', 'main.py')
```

The bonus `.parts` at the end splits the whole path into a tuple, so you can handle it piece by piece. Notice how, in `pathlib`, a path isn't a string any more – it's an **object** with attributes and methods?



## 4. Checks and information

Joining paths isn't enough. We often need to check "does this file exist?" or "is it a file or a folder?".

The old way:

```python
import os

p = '/tmp'
if os.path.exists(p):
    if os.path.isdir(p):
        print('It is a folder')
    elif os.path.isfile(p):
        print('It is a file')
```

The new way:

```python
from pathlib import Path

p = Path('/tmp')
if p.exists():
    if p.is_dir():
        print('It is a folder')
    elif p.is_file():
        print('It is a file')
```

These two are about the same length, but they mean something quite different. In the new way, `p` itself knows "do I exist?" and "am I a file or a folder?" – the methods are attached to the object. In the old way, `p` is just a string, and every check has to go through the `os.path` module.

Here are the common check methods:

| Method | Meaning |
| --- | --- |
| `.exists()` | Does the path exist? |
| `.is_file()` | Is it a normal file? |
| `.is_dir()` | Is it a folder? |
| `.is_symlink()` | Is it a symbolic link (shortcut)? |
| `.is_absolute()` | Is it an absolute path? |

Note: `.is_file()` and `.is_dir()` already include "it exists", so you usually don't need to call `.exists()` first – unless you want to tell apart "doesn't exist" from "exists but isn't a file".

Here's a real example:

```python
from pathlib import Path

p = Path('/tmp')
print('exists  :', p.exists())
print('is_dir  :', p.is_dir())
print('is_file :', p.is_file())
```

On macOS / Linux, `/tmp` is always a folder that exists, so the output is:

```
exists  : True
is_dir  : True
is_file : False
```

### 4.1 Getting detailed info: `.stat()`

If you want more details, like file size or modification time, use `.stat()`:

```python
from pathlib import Path
import datetime

p = Path('/tmp')
info = p.stat()
print('size      :', info.st_size, 'bytes')
print('mtime ts  :', info.st_mtime)
print('mtime str :', datetime.datetime.fromtimestamp(info.st_mtime))
```

`.stat()` returns an `os.stat_result` object. Its common fields are:

- `.st_size`: file size (in bytes)
- `.st_mtime`: last modified time (a Unix timestamp)
- `.st_ctime`: creation time (the exact meaning depends on the system)
- `.st_mode`: permission bits

The timestamp is a float. To turn it into a readable time, use `datetime.datetime.fromtimestamp(...)`.



## 5. Looping through folders

Have you ever written code like "find all the `.py` files in some folder"? The old way usually needs `os.walk`, which is a bit of a pain. `pathlib` gives you three great tools.

### 5.1 `.iterdir()`: list only one level of the current folder

```python
from pathlib import Path

root = Path('/tmp')
for child in root.iterdir():
    print(child)
```

Everything one level down inside `/tmp` (files and folders) is listed. Note that `.iterdir()` is **not recursive** – it only looks at this one folder level.

If you only want files, add a check:

```python
from pathlib import Path

root = Path('/tmp')
files = [c for c in root.iterdir() if c.is_file()]
print(f'There are {len(files)} files')
```

### 5.2 `.glob(pattern)`: match a pattern (current folder only)

`.glob` uses shell-style **wildcards**. A star `*` means any characters (but not the path separator), and a question mark `?` means one single character.

```python
from pathlib import Path

root = Path('/tmp')
for txt in root.glob('*.txt'):
    print(txt)
```

This lists all files ending in `.txt` directly inside `/tmp`. But `.txt` files in sub-folders won't be found.

### 5.3 `.rglob(pattern)`: recursive matching

`.rglob` is short for `.glob('**/' + pattern)`, meaning "search recursively through all sub-folders".

```python
from pathlib import Path

root = Path('/tmp')
md_files = list(root.rglob('*.md'))
print(f'Found {len(md_files)} markdown files')
```

This finds every `.md` file inside `/tmp` and all its sub-folders (and their sub-folders…).

### 5.4 In practice: find all the Python files in a folder

Here's a combined example: find all `.py` files in a folder and count them:

```python
from pathlib import Path

root = Path.cwd()
py_files = list(root.rglob('*.py'))

print(f'Found {len(py_files)} .py files under {root}')
for f in py_files[:5]:
    print(' -', f.relative_to(root))
```

`Path.cwd()` is the current working directory, and `.rglob('*.py')` finds all `.py` files recursively. `.relative_to(root)` turns an absolute path into a relative one, which looks tidier.

Run it yourself – you should see a list of the `.py` files in your current project. Isn't this much, much neater than `os.walk` plus `endswith('.py')`?



## 6. Reading and writing files

This is one of my favourite things about `pathlib`.

The old way to read a file:

<!-- skip-ci -->
```python
with open('/tmp/foo.txt', 'r', encoding='utf-8') as f:
    content = f.read()
print(content)
```

The old way to write a file:

```python
with open('/tmp/foo.txt', 'w', encoding='utf-8') as f:
    f.write('hello two_water')
```

`with open(...) as f:` has become Python "muscle memory". But honestly, needing that line plus an indented line just to read a whole file is a bit… wordy, isn't it?

### 6.1 `.read_text()` – read it in one line

```python
from pathlib import Path

p = Path('/tmp/two_water_demo.txt')
p.write_text('hello two_water', encoding='utf-8')

content = p.read_text(encoding='utf-8')
print(content)
```

Output:

```
hello two_water
```

Neat, right? `.read_text()` reads the whole file into a string directly – no `with`, no `open`, no `f.read()`.

### 6.2 `.write_text()` – write it in one line

```python
from pathlib import Path

p = Path('/tmp/two_water_demo.txt')
p.write_text("Two Drops' clock-in records\n", encoding='utf-8')
print(p.read_text(encoding='utf-8'))
```

`.write_text(s)` writes the string `s` into the file. If the file already exists, it's **overwritten** (careful – overwritten, not added to). It returns the number of characters written.

### 6.3 Reading and writing binary: `.read_bytes()` and `.write_bytes()`

Besides text, there are matching methods for binary data:

```python
from pathlib import Path

p = Path('/tmp/two_water_bin.dat')
p.write_bytes(b'\x00\x01\x02two_water')

data = p.read_bytes()
print(data)
print(len(data), 'bytes')
```

Output:

```
b'\x00\x01\x02two_water'
12 bytes
```

`.read_bytes()` and `.write_bytes()` work with `bytes` objects. You don't need to (and can't) pass `encoding`.

### 6.4 When do you still need `open()`?

So now that we have `read_text` / `write_text`, is `open` useless?

Not quite. For these jobs, you still need the traditional `with open(...) as f:`:

- Reading a huge file line by line, so you don't load it all into memory at once
- Append mode (`'a'`)
- Doing complicated logic while writing (like reading, calculating and writing at the same time)

The good news is that `Path` objects have an `.open()` method you can use directly:

```python
from pathlib import Path

p = Path('/tmp/two_water_lines.txt')
p.write_text('line1\nline2\nline3\n', encoding='utf-8')

with p.open('r', encoding='utf-8') as f:
    for line in f:
        print(line.rstrip())
```

Output:

```
line1
line2
line3
```

`p.open(...)` is exactly the same as the built-in `open(p, ...)`, but it feels more natural – every file operation starts from the object `p`.



## 7. Creating and deleting

Creating folders, creating empty files, deleting files, deleting folders – you'll do these all the time. `pathlib` has them all ready.

### 7.1 `.mkdir()` – create a folder

```python
from pathlib import Path

p = Path('/tmp/two_water_demo_dir')
p.mkdir(exist_ok=True)
print(p.exists(), p.is_dir())
```

Output:

```
True True
```

The `exist_ok=True` argument is really useful: if the folder already exists, there's no error. If it's `False` (the default), you get a `FileExistsError` when the folder already exists.

What if the parent folders don't exist either? For example, you want to create `/tmp/a/b/c`, but `a` and `b` don't exist yet:

```python
from pathlib import Path

p = Path('/tmp/two_water_a/b/c')
p.mkdir(parents=True, exist_ok=True)
print(p.exists())
```

`parents=True` means "if the parent folders don't exist, create them all the way down". It's the same as `mkdir -p` in the shell.

Remember this combo – `mkdir(parents=True, exist_ok=True)`. When writing scripts, you'll use it almost with your eyes closed.

### 7.2 `.touch()` – create an empty file

```python
from pathlib import Path

p = Path('/tmp/two_water_demo.empty')
p.touch(exist_ok=True)
print(p.exists(), p.is_file(), p.stat().st_size)
```

The output is roughly:

```
True True 0
```

`.touch()` is like the `touch` command in the shell: if the file doesn't exist, it creates an empty file; if it does, it updates its modification time.

### 7.3 `.unlink()` – delete a file

```python
from pathlib import Path

p = Path('/tmp/two_water_demo.empty')
if p.exists():
    p.unlink()
print('after unlink:', p.exists())
```

Output:

```
after unlink: False
```

`.unlink()` deletes a **single file or symbolic link**. If the file doesn't exist, you get a `FileNotFoundError`. You can avoid that with `missing_ok=True` (Python 3.8+):

```python
from pathlib import Path

p = Path('/tmp/two_water_does_not_exist.x')
p.unlink(missing_ok=True)
print('done')
```

### 7.4 `.rmdir()` – delete an empty folder

```python
from pathlib import Path

p = Path('/tmp/two_water_demo_dir')
p.mkdir(exist_ok=True)
p.rmdir()
print('after rmdir:', p.exists())
```

Note: `.rmdir()` can only delete **empty** folders. If the folder still has something in it, you get an `OSError`.

So how do you delete a folder that isn't empty? `pathlib` doesn't do this itself – you need the standard library's `shutil`:

```python
import shutil
from pathlib import Path

p = Path('/tmp/two_water_demo_full')
p.mkdir(exist_ok=True)
(p / 'child.txt').write_text('hi', encoding='utf-8')

shutil.rmtree(p)
print('after rmtree:', p.exists())
```

Output:

```
after rmtree: False
```

`shutil.rmtree` deletes the folder **and everything in it** – like `rm -rf`. When you use it, check the path very carefully, so you don't accidentally `rmtree('/')` and wipe out everything!



## 8. Converting paths

In real projects, paths come in two forms – **relative** and **absolute** – and you often need to convert between them.

### 8.1 `.absolute()`: make it absolute (without following symbolic links)

```python
from pathlib import Path

p = Path('foo.txt')
print(p)
print(p.absolute())
```

The output looks something like this (depending on where you are):

```
foo.txt
/Users/two_water/projects/demo/foo.txt
```

Note: `.absolute()` doesn't need the file to really exist. It just sticks the relative path onto the current working directory to get an absolute form.

### 8.2 `.resolve()`: make it absolute (and resolve symbolic links, `..` and so on)

```python
from pathlib import Path

p = Path('foo/../bar/./baz.txt')
print(p)
print(p.resolve())
```

Output (run from `/tmp`):

```
foo/../bar/./baz.txt
/tmp/bar/baz.txt
```

See? `.resolve()` simplifies all the relative bits like `..` and `.`, giving you a clean absolute path. It also follows symbolic links to the real location.

So when do you use `.absolute()` and when `.resolve()`? Here's a rough but good-enough rule: **use `.resolve()` by default.** It's more thorough and gives a cleaner result. Only use `.absolute()` when you specifically don't want to follow symbolic links or simplify `..`.

### 8.3 `.relative_to(other)`: work out a relative path

```python
from pathlib import Path

base = Path('/tmp')
file = Path('/tmp/demo/sub/foo.txt')

print(file.relative_to(base))
```

Output:

```
demo/sub/foo.txt
```

This is perfect for logging and displaying things. For example, printing the relative paths of all files in a project looks a million times nicer than absolute paths.

Note: `.relative_to(other)` requires the current path to be **inside** `other`. Otherwise you get a `ValueError`.

### 8.4 `.expanduser()`: turn `~` into your home folder

When writing scripts, you'll often get a path from the user. For example, a config file might say `~/.config/myapp/conf.toml`. The `~` is the shell's shortcut for "home folder", but Python doesn't expand it automatically – you have to do it yourself:

```python
from pathlib import Path

p = Path('~/Documents/foo.txt')
print(p)
print(p.expanduser())
```

Output (your home folder will be different):

```
~/Documents/foo.txt
/Users/two_water/Documents/foo.txt
```

`.expanduser()` is the same as the old `os.path.expanduser(...)`. You'll almost always need it for paths typed in by users.

### 8.5 A common combo: `expanduser().resolve()`

```python
from pathlib import Path

raw = '~/Desktop/../Desktop/foo.txt'
p = Path(raw).expanduser().resolve()
print(p)
```

First expand `~`, then `resolve` to simplify it and make it absolute. You end up with a clean, tidy absolute path. This is very handy for things like reading user config.



## 9. Renaming: `with_name` / `with_stem` / `with_suffix`

Have you needed this? You've got `foo.txt` and want to make `foo.json` in the same folder, or change `report_v1.md` to `report_v2.md`.

The old way needs string slicing plus `os.path.join`, which is really ugly. `pathlib` gives you three very thoughtful methods.

### 9.1 `.with_suffix(new_suffix)` – change the extension

```python
from pathlib import Path

p = Path('/tmp/foo.txt')
print(p.with_suffix('.json'))
print(p.with_suffix(''))
```

Output:

```
/tmp/foo.json
/tmp/foo
```

Note: `new_suffix` must start with `.` (or be an empty string, which means "remove the extension"). This method is great for "same name, different format" jobs, like turning lots of `.md` files into `.html`:

```python
from pathlib import Path

src = Path('/tmp/two_water_doc.md')
src.write_text('# Title', encoding='utf-8')

dst = src.with_suffix('.html')
print('Source:', src)
print('Target:', dst)
```

Output:

```
Source: /tmp/two_water_doc.md
Target: /tmp/two_water_doc.html
```

### 9.2 `.with_name(new_name)` – change the whole file name

`.with_name(...)` replaces the whole last part (including the extension):

```python
from pathlib import Path

p = Path('/tmp/demo/foo.txt')
print(p.with_name('bar.md'))
```

Output:

```
/tmp/demo/bar.md
```

### 9.3 `.with_stem(new_stem)` – change the stem (keep the extension)

This was added in Python 3.9, specifically for "keep the extension, change only the stem":

```python
from pathlib import Path

p = Path('/tmp/demo/foo.txt')
print(p.with_stem('bar'))
```

Output:

```
/tmp/demo/bar.txt
```

The extension `.txt` stays the same, and the stem `foo` becomes `bar`.

Think about it: without `.with_stem`, you'd have to write `p.with_name(new_stem + p.suffix)` – an extra joining step. The people who designed Python's standard library thought of everything, didn't they?

### 9.4 Putting it together

Here's an example that turns `report_v1.md` into `report_v2.json`:

```python
from pathlib import Path

p = Path('/tmp/report_v1.md')
new = p.with_stem('report_v2').with_suffix('.json')
print(new)
```

Output:

```
/tmp/report_v2.json
```

Chained calls – all in one smooth line.



## 10. Cross-platform: the `PurePath` family

Have you ever had this happen? A script you wrote on macOS crashes when a teammate runs it on Windows. Very often, it's because of the path separator – macOS / Linux use `/`, and Windows uses `\`.

`pathlib` handles this quite elegantly. It has two "family lines":

- **Concrete paths**: `Path` (picked automatically), `PosixPath`, `WindowsPath` – these can really access the file system
- **Pure paths**: `PurePath`, `PurePosixPath`, `PureWindowsPath` – these only work with paths as text, and never touch the file system

99% of the time, `Path` is all you need. But occasionally – say, you're on Linux and need to read a Windows-style path string – you'll need `PureWindowsPath`:

```python
from pathlib import PureWindowsPath, PurePosixPath

p = PureWindowsPath(r'C:\Users\two_water\foo.txt')
print(p.name)
print(p.parent)

q = PurePosixPath('/home/two_water/foo.txt')
print(q.name)
print(q.parent)
```

Output:

```
foo.txt
C:\Users\two_water
foo.txt
/home/two_water
```

You can see that `PureWindowsPath` reads the path the Windows way, even when running on macOS, and `PurePosixPath` does the opposite. These can't call methods like `.exists()` or `.read_text()` that need real file system access, but they're more than enough for **reading path strings**.

That's enough on cross-platform code for now. For everyday use, `Path` is all most people need.



## 11. Old vs new cheat sheet + common traps

### 11.1 A cheat sheet to keep

To help you switch from the old APIs to `pathlib`, here's a table of the most common changes:

| Task | Old way (`os` / `os.path` / `open`) | New way (`pathlib`) |
| --- | --- | --- |
| Current working directory | `os.getcwd()` | `Path.cwd()` |
| User's home folder | `os.path.expanduser('~')` | `Path.home()` |
| Join paths | `os.path.join(a, b, c)` | `Path(a) / b / c` |
| File name | `os.path.basename(p)` | `Path(p).name` |
| Stem (no extension) | `os.path.splitext(name)[0]` | `Path(p).stem` |
| Extension | `os.path.splitext(name)[1]` | `Path(p).suffix` |
| Parent folder | `os.path.dirname(p)` | `Path(p).parent` |
| Does it exist? | `os.path.exists(p)` | `Path(p).exists()` |
| Is it a file? | `os.path.isfile(p)` | `Path(p).is_file()` |
| Is it a folder? | `os.path.isdir(p)` | `Path(p).is_dir()` |
| Absolute path | `os.path.abspath(p)` | `Path(p).resolve()` |
| Relative path | `os.path.relpath(p, base)` | `Path(p).relative_to(base)` |
| Create a folder | `os.makedirs(p, exist_ok=True)` | `Path(p).mkdir(parents=True, exist_ok=True)` |
| Delete a file | `os.remove(p)` | `Path(p).unlink()` |
| Delete an empty folder | `os.rmdir(p)` | `Path(p).rmdir()` |
| List a folder | `os.listdir(p)` | `list(Path(p).iterdir())` |
| Wildcard match | `glob.glob(pattern)` | `Path(...).glob(pattern)` |
| Recursive wildcard | `glob.glob(pattern, recursive=True)` | `Path(...).rglob(pattern)` |
| Read text | `with open(p) as f: content = f.read()` | `Path(p).read_text(encoding='utf-8')` |
| Write text | `with open(p, 'w') as f: f.write(s)` | `Path(p).write_text(s, encoding='utf-8')` |
| File size | `os.path.getsize(p)` | `Path(p).stat().st_size` |

If you forget something while coding, just come back and check.

### 11.2 Common traps

#### Trap 1: forgetting that `Path` doesn't create a file by itself

```python
from pathlib import Path

p = Path('/tmp/two_water_not_exist.txt')
print(p)
print(p.exists())
```

Output:

```
/tmp/two_water_not_exist.txt
False
```

Notice something? Just writing `Path('xxx')` doesn't actually create a file on disk. It only creates a **path object**. The file it represents might exist, or might not. To actually make the file, you need methods that "do something", like `.touch()`, `.write_text()` or `.mkdir()`.

#### Trap 2: Is `Path('foo') == Path('./foo')`?

```python
from pathlib import Path

a = Path('foo')
b = Path('./foo')
print(a == b)
print(a.resolve() == b.resolve())
```

Output:

```
True
True
```

`pathlib` tidies up a leading `./` when it builds the path, so these two are equal even before resolving. But that tidying only goes so far – `Path('foo')` and `Path('bar/../foo')` are **not** equal until you `.resolve()` them. If you want to check whether two paths "point to the same thing", it's best to `.resolve()` both first, or use the more specialised `.samefile(other)` method (which needs both to really exist).

#### Trap 3: `.suffix` returns an empty string for files with no extension

```python
from pathlib import Path

p = Path('/tmp/Makefile')
print(repr(p.suffix))
print(repr(p.stem))
```

Output:

```
''
'Makefile'
```

Be careful when writing code that filters by extension: `.suffix == ''` is true for files with no extension, like `Makefile` and `README`. Don't catch them by mistake.

#### Trap 4: `mkdir` without `exist_ok` will blow up

```python
from pathlib import Path

p = Path('/tmp/two_water_collide')
p.mkdir(exist_ok=True)
p.mkdir(exist_ok=True)
print('Neither call blew up:', p.exists())
```

Output:

```
Neither call blew up: True
```

Without `exist_ok=True`, the second `mkdir` raises a `FileExistsError`. When writing scripts, I recommend adding this argument to almost every `mkdir`.

#### Trap 5: `relative_to` can't jump across to a different branch

```python
from pathlib import Path

a = Path('/tmp/foo')
b = Path('/var/log')

try:
    print(a.relative_to(b))
except ValueError as e:
    print('Blew up:', e)
```

Output:

```
Blew up: '/tmp/foo' is not in the subpath of '/var/log' OR one path is relative and the other is absolute.
```

In this case you can't use `relative_to`. You have to use `os.path.relpath`, or the `walk_up=True` argument in Python 3.12+:

<!-- skip-ci -->
```python
from pathlib import Path

a = Path('/tmp/foo')
b = Path('/var/log')

print(a.relative_to(b, walk_up=True))
```

The output is roughly:

```
../../tmp/foo
```

`walk_up=True` was only added in 3.12. It allows the result to contain `..`.



## 12. Mini project: count the total lines in all `.py` files in a folder

We've covered a lot. Let's tie it together with a small function. Here's the task:

> Given a folder, recursively count the total number of lines in all the `.py` files inside it.

The old way might look like this:

```python
import os

def count_py_lines_old(root):
    total = 0
    for dirpath, dirnames, filenames in os.walk(root):
        for name in filenames:
            if name.endswith('.py'):
                full = os.path.join(dirpath, name)
                with open(full, 'r', encoding='utf-8') as f:
                    total += sum(1 for _ in f)
    return total
```

`os.walk` with two nested `for` loops, then `os.path.join`, then `with open` – it takes seven or eight lines just to write the core logic.

What does it look like with `pathlib`?

```python
from pathlib import Path


def count_py_lines(root: Path) -> int:
    """Recursively count the total lines in all .py files under root."""
    total = 0
    for py in root.rglob('*.py'):
        if not py.is_file():
            continue
        text = py.read_text(encoding='utf-8', errors='ignore')
        total += text.count('\n') + (0 if text.endswith('\n') or not text else 1)
    return total


if __name__ == '__main__':
    n = count_py_lines(Path.cwd())
    print(f'Total lines in .py files in the current folder: {n}')
```

Let's walk through it:

1. `root.rglob('*.py')` finds all `.py` files recursively – no more `os.walk` mess
2. `py.is_file()` is attached to the object – nice to read
3. `py.read_text(...)` reads the whole file in one line – no `with open`
4. Count lines with `text.count('\n')`, plus handle the case where the last line has no newline

The whole core loop is just 5 lines. Compared with the old way, isn't it much cleaner?

Another question: what if some `.py` files aren't UTF-8? `read_text` would raise a `UnicodeDecodeError`. Here we added `errors='ignore'`, so bytes that can't be decoded are skipped, and the count doesn't stop. Little tricks like this are really handy when writing tool scripts.

Curious readers can improve it further:

- Skip folders like `.venv` and `__pycache__`
- Count blank lines and non-blank lines separately
- Add an `--ext` option so it works with any extension

Treat these as homework, and have fun with them.



## 13. Bonus: working with the old APIs

You might be worried: what if some "inherited" code in your project uses string paths, or a third-party library needs a string instead of a `Path`?

Don't worry at all. Converting between `Path` and strings is very easy.

### 13.1 `Path` → string: just use `str()`

```python
from pathlib import Path

p = Path('/tmp/foo.txt')
s = str(p)
print(s)
print(type(s))
```

Output:

```
/tmp/foo.txt
<class 'str'>
```

`str(p)` turns a `Path` object back into a plain string. You can pass this to any old API that wants a string path.

### 13.2 String → `Path`: `Path(s)`

The other way is even easier – we've done it countless times already:

```python
from pathlib import Path

s = '/tmp/foo.txt'
p = Path(s)
print(p)
```

### 13.3 `os.PathLike`: the standard library's compatibility protocol

Since Python 3.6, the `os.PathLike` protocol lets almost every standard library function that takes a path (including `open`, `os.listdir`, `shutil.copy` and so on) accept `Path` objects directly. That means:

```python
from pathlib import Path

p = Path('/tmp/two_water_compat.txt')
p.write_text('hi', encoding='utf-8')

with open(p, 'r', encoding='utf-8') as f:
    print(f.read())
```

Output:

```
hi
```

Notice anything? We passed a `Path` object straight into `open` without `str()` first, and it still works. That's thanks to the `os.PathLike` protocol.

So you can use `pathlib` with confidence – it works smoothly with your "old friends" in the standard library.



## 14. Summary

We've covered a lot. Here are the key points about `pathlib`:

First, in `pathlib`, a path isn't a string any more – it's an **object**. It knows its own name, where it is, whether it's a file, and whether it can be read. This "the object looks after itself" design makes code read more like natural language.

Second, the `/` operator makes joining paths look just like a path. `Path('/tmp') / 'foo' / 'bar.txt'` is so much better than a long `os.path.join`.

Third, `pathlib` brings together features from several old modules (`os.path`, `os`, `open`, part of `shutil`) into one object. `p.exists()`, `p.read_text()`, `p.mkdir(parents=True, exist_ok=True)` – everything starts from `p`, with no need to import things all over the place.

From now on, when you write new code, stop using `os.path.join` for everything. Just `from pathlib import Path` – you'll love it.



## Where did the file get written?

We've covered lots of path operations. This time, let's do a small job where you can check the result. Save two lines of text in a special practice folder, then read them back:

```python
from pathlib import Path

folder = Path('study-demo-records')
folder.mkdir(exist_ok=True)
path = folder / 'lesson.txt'
path.write_text('Python:15\nReading:10\n', encoding='utf-8')
text = path.read_text(encoding='utf-8')
print(path.name)
print(len(text.splitlines()))
```

Output:

```text
lesson.txt
2
```

The relative path here starts from the program's **current working directory** – it's not automatically relative to the folder the script is in, wherever you run it from. On your own computer, first check `Path.cwd()`, then find the file that was created. Running it again updates this practice file. Use a special practice folder – don't experiment on your own notes files.

If you run the same code in the browser, it writes to the runtime's **virtual file system**, not a folder on your computer that's kept long-term. It's not guaranteed to survive a refresh or a restart of the environment. For a full project that needs to save things between runs, do it on your own computer.

Add a third line to the content yourself, then check the line count. Then create a `Path` object only, without calling any write method, and see that it doesn't magically create a file. When you need complete data, don't just ignore decoding errors to avoid an error message – first check the file's encoding and whether any data might be lost.
