    Decorators

    In the last article, we learned about closures by solving a real problem. This article does the same: we'll slowly change a task, step by step, to understand Python decorators.

    First, here's a function that prints an employee's clock-in message:

    def punch():
    print('Nickname: Two Drops  Department: Coding Dept  Clocked in for work')


punch()

    Output:

    Nickname: Two Drops  Department: Coding Dept  Clocked in for work

    Then the product team says: "That's no good – the clock-in doesn't show the date! Add the date." Should be easy, done in a minute. OK, let's just add some code to print the date:

    import time


def punch():
    print(time.strftime('%Y-%m-%d', time.localtime(time.time())))
    print('Nickname: Two Drops  Department: Coding Dept  Clocked in for work')


punch()

    Output:

    2018-01-09
Nickname: Two Drops  Department: Coding Dept  Clocked in for work

    This works, but it changes the structure of the function. The function was meant to print an employee's info and say they clocked in. Adding date-printing code could lead to lots of repeated code. For example, if somewhere else you only need the employee info and clock-in message without the date, do you write another function? Also, printing the current date is something you'll use often, so it could be a shared function that other modules call. Of course, this is thinking about the project as a whole.

    So, let's change this code using functional programming. From what we've learned, Python functions have two features: functions are objects, and functions can be nested inside functions. Let's change the code to this:

    import time


def punch():
    print('Nickname: Two Drops  Department: Coding Dept  Clocked in for work')


def add_time(func):
    print(time.strftime('%Y-%m-%d', time.localtime(time.time())))
    func()


add_time(punch)

    Output:

    2018-01-09
Nickname: Two Drops  Department: Coding Dept  Clocked in for work

    See? We didn't change the punch function at all. And any function that needs the current date printed can just be passed into add_time, like this:

    import time


def punch():
    print('Nickname: Two Drops  Department: Coding Dept  Clocked in for work')


def add_time(func):
    print(time.strftime('%Y-%m-%d', time.localtime(time.time())))
    func()


def holiday():
    print('It is too cold – day off today!')


add_time(punch)
add_time(holiday)

    Output:

    2018-01-09
Nickname: Two Drops  Department: Coding Dept  Clocked in for work
2018-01-09
It is too cold – day off today!

    Functional programming is handy, isn't it? But every time we call it, we have to pass the original function in as an argument. Is there a better way? Yes – the decorator, which this article is about. Writing a decorator is a lot like writing a closure, just without the free variable. Here's the decorator version of the code above, so you can compare it with the functional version:

    import time


def decorator(func):
    def punch():
        print(time.strftime('%Y-%m-%d', time.localtime(time.time())))
        func()

    return punch


def punch():
    print('Nickname: Two Drops  Department: Coding Dept  Clocked in for work')


f = decorator(punch)
f()

    Output:

    2018-01-09
Nickname: Two Drops  Department: Coding Dept  Clocked in for work

    From the code, a decorator function usually does three things:

    1. Takes a function as an argument
    2. Has a wrapper function inside it. The wrapper takes the same arguments as the original function, runs the original function, and also does something extra
    3. Returns the wrapper function

    But look closely – this decorator version seems even more trouble than the functional version! It looks more complicated, and even a bit pointless.

    That's because we haven't used the decorator's syntactic sugar yet. From the code above, you can see that when Python added decorators, it didn't add any new language features – it's all based on what functions can already do. This shows decorators aren't special to Python – they're a general programming idea in every language. But Python designed the @ syntactic sugar to make it simpler and easier to define a decorator, have it wrap the original function, and assign the result back to the original function's name. So you could say the heart of Python decorators is this syntactic sugar.

    How do you use it? Easy. After writing the decorator function as above, just put @ and the decorator's name above the original function, like this:

    import time


def decorator(func):
    def punch():
        print(time.strftime('%Y-%m-%d', time.localtime(time.time())))
        func()

    return punch

@decorator
def punch():
    print('Nickname: Two Drops  Department: Coding Dept  Clocked in for work')

punch()

    Output:

    2018-01-09
Nickname: Two Drops  Department: Coding Dept  Clocked in for work

    Now this is really convenient – especially when calling it. In the example, after adding the decorator, we just put the decorator's syntactic sugar above the original function. The function itself doesn't need to change at all, and the places that call it don't need to change either.

    But there's still a problem: the clock-in message is fixed. If we want to pass it in through arguments, how do we write the decorator? The function inside the decorator can use *args for variable arguments. But *args alone doesn't cover every case – it doesn't handle keyword arguments. To handle keyword arguments too, we also add **kwargs.

    So the final form of the decorator can be written like this:

    import time


def decorator(func):
    def punch(*args, **kwargs):
        print(time.strftime('%Y-%m-%d', time.localtime(time.time())))
        func(*args, **kwargs)

    return punch


@decorator
def punch(name, department):
    print(f'Nickname: {name}  Department: {department}  Clocked in for work')


@decorator
def print_args(reason, **kwargs):
    print(reason)
    print(kwargs)


punch('Two Drops', 'Coding Dept')
print_args('Two Drops', sex='Male', age=99)

    Output:

    2018-01-09
Nickname: Two Drops  Department: Coding Dept  Clocked in for work
2018-01-09
Two Drops
{'sex': 'Male', 'age': 99}

    When you add a decorator, does the function run straight away?¶

    We've gone from clocking in all the way to decorators. Now let's look clearly at the order things happen in: what happens when @decorator appears, and what happens later when we call punch()?

    Let's use a list to record the steps, so we don't mix up "creating the wrapper" with "doing the clock-in":

    events = []


def decorator(func):
    events.append('Wrapper created')

    def wrapper(*args, **kwargs):
        events.append('Original function called')
        return func(*args, **kwargs)

    return wrapper


@decorator
def punch(name):
    return f'{name} clocked in'


print(events)
print(punch('Two Drops'))
print(events)

    Output:

    ['Wrapper created']
Two Drops clocked in
['Wrapper created', 'Original function called']

    The first line shows that before we reach punch('Two Drops'), the decorator has already received the original function and returned the wrapper – but the body of the original function hasn't run yet. Only when we later call punch do we go into wrapper, which then calls the original function.

    This order comes from how this decorator is written: it returns wrapper and doesn't call the original function while creating the wrapper. A decorator can contain other logic too, so to know when things run, look at which level the call is written at.

    You can think of @decorator as a shortcut for defining the function and then running punch = decorator(punch). Decorators are built on what functions can already do, but @ is special decorator syntax. Keep the syntax and the function-wrapping that happens behind it separate in your head.

    The original function worked out a result – did the wrapper pass it on?¶

    In the clock-in example, we mostly showed the effect by printing, so the original function didn't need to return a result. But if you decorate a function that calculates something, and the wrapper only calls it without returning the result, the caller outside won't get the value it worked out.

    Let's try it with a function that records study time:

    def add_log(func):
    def wrapper(*args, **kwargs):
        print('Start counting')
        result = func(*args, **kwargs)
        print('Counting done')
        return result

    return wrapper


@add_log
def total_minutes(first, second):
    return first + second


minutes = total_minutes(5, second=10)
print(minutes)

    Output:

    Start counting
Counting done
15

    Try a small experiment: remove only the return result in wrapper, leave everything else the same, and run it again. The last line becomes None. It's not that the original function didn't work out 15 – it's that the wrapper didn't pass that result on to the caller outside.

    In this example, *args collects positional arguments and **kwargs collects keyword arguments, and then they're passed on to the original function the same way. They just forward arguments – they don't make the original function accept arguments it didn't support before. If you pass the wrong arguments, the original function will still give an error.

    Check it yourself – don't stop just because you saw the log messages¶

    Keep using add_log from above, and call total_minutes(0, 0) and total_minutes(first=12, second=3). Each time, you should first see two log lines, and then the print outside should show 0 and 15.

    Then go back to the first example and call punch('Two Drops') once more. events should have only one 'Wrapper created', and two 'Original function called'. If you can explain why the wrapper isn't created twice, you've understood the difference between when the decorator runs and when the wrapper runs.

    When you run the date examples, you'll get today's date. When checking, look at what it does and the order – the date doesn't need to match the old example.
