    pyproject.toml + uv: putting an end to "it works on my computer but not on yours"¶

    Have you ever had this nightmare? Brother Shui packs up his code and sends it to a teammate. The teammate runs it and gets a pile of ModuleNotFoundErrors. Brother Shui says: "Just pip install it." The teammate asks: "Which version?" Brother Shui searches his computer, can't find a complete requirements.txt anywhere, and finally mumbles: "Er… it works on my computer. That's weird."

    This happens all the time in the Python world. It was like this three years ago, and five years ago. Go back even further to ancient times, and people used a scattered pile of files – setup.py + requirements.txt + MANIFEST.in + setup.cfg – each handling one bit of the job. Beginners wanted to cry.

    "Why is it so complicated?" you might ask.

    The answer is history. Python's packaging tools evolved slowly, and every generation of tools left behind some files of its own. It wasn't until PEP 518 in 2018, followed by PEP 621 in 2021, that the community finally agreed: put all project metadata, dependencies and tool settings into one single file, called pyproject.toml.

    Then in 2024, a new tool called uv arrived, made by Astral (the people behind ruff). It's written in Rust, it's 10 to 100 times faster than pip, it's a single program with no dependencies, and one command installs it.

    These two weapons together are what this chapter is about. After this chapter, when you start a new project, going from nothing to "a project that runs, locks its dependencies and runs tests" takes just four or five commands. When a teammate asks "which version do I install?", just send them the project folder. They run uv sync, and the exact same environment grows on their computer. That's the experience you should have in 2026.

    What was so bad about the old way?¶

    First, let's remember what the old way looked like. A "proper" Python project usually had these files:

    my-project/
├── setup.py
├── setup.cfg
├── requirements.txt
├── requirements-dev.txt
├── MANIFEST.in
├── pytest.ini
├── .flake8
├── tox.ini
└── my_project/
    └── __init__.py

    Eight or nine config files alone, each doing something different:

    • setup.py: for packaging – tells pip the project's name, version and entry points
    • setup.cfg: part of setup.py's settings could move here, if you felt like it
    • requirements.txt: the list of production dependencies
    • requirements-dev.txt: the list of development dependencies (testing, linter, formatter)
    • MANIFEST.in: which non-code files to include when packaging
    • pytest.ini: settings for pytest
    • .flake8: settings for flake8
    • tox.ini: for testing on several Python versions

    Is your head spinning yet? And that's not even the worst part. The worst part is:

    requirements.txt doesn't lock versions.

    Have you written a requirements.txt like this?

    requests
flask
sqlalchemy

    Clean and simple – three lines. Six months later, a teammate downloads it and runs it. requests automatically installs the newest version, an old API has been removed, and the code breaks. This is the famous gap between "it runs" and "it can be reproduced".

    It's not that the old way couldn't solve this – but it needed a pile of patches: pip-tools to make requirements.lock, pipenv to maintain Pipfile.lock, poetry to maintain poetry.lock. Every tool had its own lock file format, and they didn't work with each other.

    "Didn't Pipenv solve this?" Some of you might remember it. Pipenv was popular for a while, but it was painfully slow. Installing numpy could take 30 seconds just to work out dependencies, and big projects took minutes. Engineers' lives drained away waiting for pipenv install.

    Then came poetry, much faster than pipenv, but with its own problems: it invented its own dependency syntax (using ^ and ~ for version ranges), which wasn't fully compatible with the standard PEP 508, so moving to or from it wasn't smooth.

    By 2024, the community had finally cleaned things up:

    • Metadata format: unified as pyproject.toml (PEP 621)
    • Dependency format: unified as PEP 508
    • Tool: uv is recommended (the speed king)

    Let's look step by step at how much easier the new way is.

    What is pyproject.toml?¶

    pyproject.toml is a file name, and the file format is TOML. If you've never seen TOML, don't worry – it's a config format that's friendlier than JSON and stricter than YAML. It looks like this:

    [project]
name = "my-project"
version = "0.1.0"

    The square brackets [project] mark a section, and the key = value lines below it are settings. Strings use double quotes, numbers are written directly, and lists use square brackets – much like most programming languages.

    The core idea of pyproject.toml is: put all of a project's information in one file. What can go in it? Look at this complete example:

    [project]
name = "my-project"
version = "0.1.0"
description = "A small tool by Two Drops"
requires-python = ">=3.10"
dependencies = [
    "httpx>=0.27",
    "click>=8.0",
]

[project.optional-dependencies]
dev = [
    "pytest>=8.0",
    "ruff>=0.5",
]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.ruff]
line-length = 100

[tool.pytest.ini_options]
testpaths = ["tests"]

    Count how many jobs this one file does:

    • The [project] section: project name, version, Python version requirement, dependency list – these used to be in setup.py
    • The [project.optional-dependencies] section: development dependencies and optional dependencies – used to be requirements-dev.txt
    • The [build-system] section: how to package the project – used to be setup.py + MANIFEST.in
    • The [tool.ruff] section: ruff settings – used to be .ruff.toml or setup.cfg
    • The [tool.pytest.ini_options] section: pytest settings – used to be pytest.ini

    One file does everything. When a newcomer takes over a project, they open pyproject.toml, scan it top to bottom, and have the whole project's metadata, dependencies and tool settings in their head.

    "Isn't this just package.json?" you'll ask if you've written Node.js.

    Yes – the idea was copied from package.json, but pyproject.toml is stricter. It says the [project] section must follow PEP 621, and tool settings go under [tool.*] sections, so nothing ends up in the wrong place.

    Next, let's go through the fields one by one.

    The smallest pyproject.toml, field by field¶

    Here's the minimum a project needs to run:

    [project]
name = "my-project"
version = "0.1.0"
requires-python = ">=3.10"
dependencies = [
    "httpx>=0.27",
]

    Five fields. Let's explain each one.

    name¶

    name = "my-project"

    The project's name. This is the name used when publishing to PyPI, and it's unique across the whole internet. Naming rules:

    • Only letters, digits, hyphens -, underscores _ and dots .
    • Not case-sensitive – My-Project and my_project are the same name to PyPI
    • By convention, all lowercase with hyphens

    When choosing a name, note that the project name (name) and the import name (what you import) aren't always the same. For example, the famous Pillow has the project name Pillow, but you import PIL. scikit-learn has a hyphen in its project name, but you import sklearn.

    If your project is just for fun and won't be published to PyPI, name it however you like – but it's still good to follow the conventions.

    version¶

    version = "0.1.0"

    The version number. It's best to follow Semantic Versioning, in the format MAJOR.MINOR.PATCH:

    • MAJOR: big, incompatible changes (e.g. going from 1.x to 2.x, old code might stop working)
    • MINOR: new features that are backwards-compatible (0.1.x to 0.2.x)
    • PATCH: bug fixes that are backwards-compatible (0.1.0 to 0.1.1)

    New projects start at 0.1.0, and the first stable release is 1.0.0. You can also use tools like setuptools-scm to take the version automatically from a git tag, but let's not go into that yet – get comfortable with the basics first.

    requires-python¶

    requires-python = ">=3.10"

    Says which version of Python the project needs. Brother Shui strongly recommends always writing this line, for three reasons:

    1. If someone installs your package with Python 3.7, they get an error straight away, instead of crashing halfway through
    2. pip uses this information to pick suitable sub-dependencies
    3. Tools (ruff, mypy) use it to decide which syntax is available

    The version range syntax follows PEP 440:

    • >=3.10: 3.10 or higher
    • >=3.10,<4.0: from 3.10, but below 4.0
    • ~=3.10: the 3.10.x series, not 3.11
    • ==3.10.*: any patch version of 3.10

    For a new project in 2026, Brother Shui suggests: just write >=3.10 or >=3.11. 3.9 is close to retirement, and modern features (match statements, better type hints) only start in 3.10.

    dependencies¶

    dependencies = [
    "httpx>=0.27",
    "click>=8.0",
]

    The list of dependencies the project needs to run. Each item is a string following PEP 508 syntax. Common forms:

    dependencies = [
    "httpx",                   # Any version
    "httpx>=0.27",             # From 0.27 up
    "httpx>=0.27,<1.0",        # A range
    "httpx==0.27.2",           # Pinned exactly
    "httpx[http2]",            # With extras
    "httpx ; python_version >= '3.10'",  # A conditional dependency
]

    The most common form is a lower limit like >=X.Y. That's the community convention: write a lower limit, not an upper limit, unless you really know an upper version will cause problems. Why? If you write httpx<1.0 today, and httpx 1.0 comes out tomorrow, every project that depends on yours gets stuck and is forced to deal with it. This is called "upper-bound pollution", and it's poison.

    The exact versions of dependencies are recorded in a lock file (uv.lock), which we'll see below.

    A complete minimal example¶

    Put the five fields together, and a working minimal pyproject.toml looks like this:

    [project]
name = "my-project"
version = "0.1.0"
requires-python = ">=3.10"
dependencies = [
    "httpx>=0.27",
]

    That's it. Five lines – much shorter than setup.py, and much shorter than setup.cfg + requirements.txt together. A newcomer understands it at a glance.

    For projects that "won't be published to PyPI – just an internal script", this is enough. To publish to PyPI, you also need a [build-system] section to tell the packaging tool how to build it – uv init below creates it for you.

    What is uv, and how do you install it?¶

    That's the file format. Now for the tool.

    uv is a Python package manager and project manager from Astral. You might know this company – their ruff is now the standard Python linter and formatter. uv is their next product, and its goal is to replace a whole set of old tools: pip, pip-tools, pipenv, poetry, virtualenv and pyenv.

    Sounds bold, right? But uv really does it. Its selling points:

    • Fast: written in Rust, it works out dependencies 10–100 times faster than pip. Installing numpy takes half a second, not ages like pipenv
    • A single program: uv itself doesn't need Python. It's one executable file you can put anywhere and use
    • All in one: project management (creating projects, adding dependencies, running scripts), Python version management (installing Python interpreters) and virtual environment management (venv) – all in one tool
    • Compatible: uv pip install is used just like pip install. pyproject.toml uses the PEP 621 standard, so there are no walls to moving in or out

    Since its release in early 2024, uv has been quickly adopted by big companies and open-source projects. Now in 2026, uv is the first choice for new projects – almost no question.

    Installing uv¶

    The easiest way for macOS users:

    brew install uv

    A general way that works on any platform:

    curl -LsSf https://astral.sh/uv/install.sh | sh

    Windows users can use PowerShell:

    powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

    If you already have pip, you can also do this:

    pip install uv

    But Brother Shui recommends installing it on its own – uv was designed to get away from pip, so there's no need to tie it to pip.

    After installing, check the version:

    uv --version

    The output is something like:

    uv 0.5.20

    Your version number may be different – as long as it prints something, you're good.

    By the way: installing Python itself¶

    Many people don't have a suitable version of Python on their computer, or only have the system's Python 3.9. uv can install Python for you too:

    uv python install 3.12

    After this, Python 3.12 is installed in a folder that uv manages. It's like a lightweight pyenv.

    See which Pythons are installed:

    uv python list

    The output is roughly:

    cpython-3.12.7-macos-aarch64-none           /Users/foo/.local/share/uv/python/...
cpython-3.11.10-macos-aarch64-none          /Users/foo/.local/share/uv/python/...
cpython-3.10.15-macos-aarch64-none          /Users/foo/.local/share/uv/python/...

    From now on, when you start a new project, just pick the version you want – no worrying about what's installed on your computer.

    uv init: creating a project¶

    Enough theory – let's get going.

    uv init my-project

    This one command does a lot. Look at the folder it creates:

    cd my-project
ls -la

    Roughly:

    .git/
.gitignore
.python-version
README.md
main.py
pyproject.toml

    Let's look at each file.

    .python-version¶

    3.12

    This one file pins the Python version the project uses. On any computer with uv installed, go into this folder, and uv automatically uses 3.12 – installing it if needed. That's where uv python install above comes in handy.

    pyproject.toml¶

    [project]
name = "my-project"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.12"
dependencies = []

    Very like the minimal example we wrote by hand, with just description and readme added. uv init assumes you'll write a README.md, so it creates an empty one for you.

    dependencies = [] is empty, because we haven't added any dependencies yet.

    main.py¶

    def main():
    print("Hello from my-project!")


if __name__ == "__main__":
    main()

    A "Hello World" entry point you can run straight away.

    .gitignore¶

    uv also creates a general .gitignore for Python projects, which ignores __pycache__/, .venv/, *.pyc and so on. No more copying .gitignore templates from the internet.

    Let's run it¶

    uv run main.py

    Output:

    Hello from my-project!

    uv run is one of uv's main commands. It does these things:

    1. Checks whether the project's Python version is suitable, and installs it if not
    2. Checks whether the .venv/ virtual environment exists, and creates it if not
    3. Checks whether all dependencies are installed, and installs them if not
    4. Runs the command using the project's virtual environment

    So you can see: from uv init to running code takes two commands – uv init my-project and uv run main.py. No "create a virtual environment, activate it, install dependencies" steps in between. That's the uv experience.

    uv add: adding dependencies¶

    The new project runs. Now let's add something. How do you usually install httpx?

    The old way:

    pip install httpx
# Then open requirements.txt by hand and add a line
echo "httpx" >> requirements.txt

    Two steps – and it's easy to forget the second one. It works fine after installing, but you commit your code without updating requirements.txt, and your teammate's copy doesn't run.

    The uv way:

    uv add httpx

    One command. What does it do behind the scenes?

    1. Works out the newest version of httpx (that fits the project's requires-python)
    2. Installs it in the project's .venv/
    3. Writes httpx>=0.28 into the dependencies in pyproject.toml
    4. Updates uv.lock, pinning the exact versions of httpx and all its own dependencies

    Open pyproject.toml and look:

    [project]
name = "my-project"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "httpx>=0.28",
]

    dependencies has a new line, added automatically. You don't need to look after this list by hand.

    Adding several dependencies¶

    uv add httpx click rich

    Add three at once. They're worked out together, much faster than pip install-ing them one by one.

    Adding development dependencies¶

    pytest for testing and ruff as a linter aren't needed when the project runs – only while developing – so they should go in development dependencies. uv uses the --dev flag:

    uv add --dev pytest ruff

    This time pyproject.toml gets a new section:

    [dependency-groups]
dev = [
    "pytest>=8.3",
    "ruff>=0.8",
]

    Note it's [dependency-groups], not [project.optional-dependencies] – this is the new PEP 735 format, which uv uses by default. Both work, but dependency-groups is the new standard from 2024, made specially for dependencies that "aren't published, only used for local development".

    Removing dependencies¶

    uv remove rich

    It's not only removed from pyproject.toml – it's also uninstalled from .venv/, and uv.lock is updated. Cleanly removed.

    Upgrading dependencies¶

    uv add httpx --upgrade

    Or:

    uv lock --upgrade-package httpx

    Upgrades to the newest version that fits the rules.

    Giving a version range¶

    If you have special requirements for the version:

    uv add "httpx>=0.27,<0.30"

    This writes httpx>=0.27,<0.30 into pyproject.toml. uv picks the newest version within that range.

    uv run: running commands¶

    uv run can run more than main.py – it can run any command.

    Run a bit of Python:

    uv run python -c "import httpx; print(httpx.__version__)"

    The output is roughly:

    0.28.1

    Run pytest:

    uv run pytest

    Run your own script:

    uv run python scripts/build.py

    The good thing about uv run is that it makes sure the project's virtual environment is used. You don't need source .venv/bin/activate, or to activate it again every time you open a new terminal. Just go into the project folder and uv run.

    "What if I want to activate it and run lots of commands?" You can do that too:

    source .venv/bin/activate
python -c "import httpx; print(httpx.__version__)"
pytest

    After activating, it's the same as the traditional way. But Brother Shui hardly ever activates any more – putting uv run in front of each command is enough.

    Running command-line tools¶

    Many packages install a command-line tool. For example, after installing ruff you get a ruff command. In a uv project, run it like this:

    uv run ruff check .

    uv finds ruff in .venv/bin/ and runs it.

    Running a one-off command¶

    Sometimes you want to use a tool without adding it to your project's dependencies. For example, to quickly see how httpie sends a request:

    uvx httpie https://httpbin.org/get

    uvx is short for uv tool run. It installs httpie in a temporary environment, runs it, and throws it away – without messing up your project. It's like pipx run, but much faster.

    Similarly, run cowsay just once:

    uvx cowsay "Hello Two Drops"

    You can use this for lots of "install once, use once" situations.

    uv sync: syncing dependencies¶

    Now for the key question: how does a teammate run it after downloading it?

    The old way:

    git clone <repo>
cd <repo>
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
pip install -r requirements-dev.txt

    Five commands. And they differ across platforms – the command to activate a virtual environment is different on Windows.

    The uv way:

    git clone <repo>
cd <repo>
uv sync

    Done. uv sync will:

    1. Check the Python version set in .python-version, and install it if needed
    2. Create .venv/ (if it doesn't exist)
    3. Install every dependency (including development dependencies) at the exact versions pinned in uv.lock

    "Exact versions" is the key. uv.lock doesn't record httpx>=0.28 – it records httpx==0.28.1, and pins all of httpx's own dependencies to exact versions too. So the environment uv sync creates is identical, byte for byte, to the one on Brother Shui's computer.

    In the past, every time you ran pip install -r requirements.txt, the dependency resolution might pick different versions (unless you'd pinned every indirect dependency by hand in requirements.txt, which is torture). uv sync automates all of this.

    What does uv.lock look like?¶

    head -30 uv.lock

    Roughly:

    version = 1
revision = 1
requires-python = ">=3.12"

[[package]]
name = "anyio"
version = "4.6.2.post1"
source = { registry = "https://pypi.org/simple" }
dependencies = [
    { name = "idna" },
    { name = "sniffio" },
]
sdist = { url = "https://files.pythonhosted.org/packages/.../anyio-4.6.2.post1.tar.gz", hash = "sha256:..." }

    Each package records:

    • Its name and version
    • Where it comes from (PyPI, git, a local path…)
    • Which other packages it depends on
    • The download address and hash of its source package (sdist)
    • The download address and hash of its binary package (wheel)

    The hash is key – uv sync checks it when installing, making sure the downloaded package is exactly the same as when it was locked. This protects against supply-chain attacks like "someone tampered with a package on PyPI".

    A few common sync options¶

    Install only production dependencies, not development ones (common when deploying):

    uv sync --no-dev

    Force everything to be reinstalled (e.g. after changing pyproject.toml):

    uv sync --reinstall

    Install only one dependency-group:

    uv sync --only-group dev

    90% of the time, plain uv sync with no options is all you need.

    Automatic virtual environment management¶

    You all know the old virtual environment routine:

    python -m venv .venv
source .venv/bin/activate    # macOS/Linux
.venv\Scripts\activate       # Windows
pip install ...

    It has a few pain points:

    1. It's easy to forget to activate – every new terminal needs activating again
    2. It's different on different platforms – Windows and macOS use different commands
    3. Switching projects means deactivate first, then activate the new one – annoying
    4. Using the wrong virtual environment is a common bug – "I installed httpx, so why does import fail? Oh, I'm in the wrong environment"

    uv's approach: you don't need to activate at all. Run every command with uv run, and uv automatically finds the .venv/ in the current folder and uses its Python. You don't even have to remember "which environment is active right now".

    To see which Python is being used:

    uv run which python

    Output:

    /Users/walter/projects/my-project/.venv/bin/python

    Go into the project folder, and the project's .venv is used automatically.

    You can still activate by hand if you want¶

    To work with the traditional way, uv lets you activate too:

    source .venv/bin/activate
python main.py

    After activating, use the python command directly – no uv run needed. Brother Shui does this occasionally, when "running lots of commands in a row and wanting to keep the environment active".

    Moving over from requirements.txt¶

    If you have an old project that already uses requirements.txt, how do you move it over?

    Situation 1: lock straight from requirements.txt¶

    If your requirements.txt is already "input rules" (ranges like httpx>=0.27), you can do this:

    uv pip compile requirements.in > requirements.txt

    By convention, requirements.in is the input (with version ranges), and requirements.txt is the output (pinned exact versions). This is the pip-tools convention, and uv pip compile is fully compatible with it.

    If you don't have a requirements.in, only a requirements.txt that already has exact versions, you can just use it as your lock file and skip this step.

    Situation 2: turn requirements.txt into pyproject.toml¶

    This is a more complete move. Say your current requirements.txt is:

    httpx>=0.27
click>=8.0
sqlalchemy>=2.0

    Step 1: in the project's root folder, run:

    uv init --no-package

    --no-package tells uv this is just an app, not something to publish to PyPI. It creates pyproject.toml and .python-version, but no [build-system] section.

    Step 2: uv add the dependencies from requirements.txt:

    uv add httpx click sqlalchemy

    Or all at once:

    uv add -r requirements.txt

    -r makes uv read requirements.txt and add all its dependencies to pyproject.toml.

    Step 3: delete the old requirements.txt (or, to stay compatible, export one from pyproject.toml):

    uv export --no-dev > requirements.txt

    Now requirements.txt becomes "exact versions exported from the lock file", and old tools (like Docker image build scripts) can keep using it.

    Situation 3: moving over from poetry¶

    poetry projects use pyproject.toml too, but the format isn't exactly PEP 621 – dependencies go in a [tool.poetry.dependencies] section.

    The quickest way to move:

    uvx pdm import pyproject.toml

    Or rewrite the [tool.poetry.dependencies] section by hand into a dependencies list under [project]. Change poetry's ^1.0 to >=1.0,<2.0, and ~1.0 to >=1.0,<1.1 – just translate by the rules.

    After moving, delete poetry.lock and run uv lock to create a new uv.lock:

    uv lock

    Situation 4: moving over from pipenv¶

    pipenv uses Pipfile and Pipfile.lock. Convert by hand: the [packages] section in Pipfile maps to dependencies, and [dev-packages] maps to [dependency-groups].dev. Then uv lock to create the new lock file.

    uv vs pip vs poetry vs pipenv – side by side¶

    You often hear people say one tool is good and another is bad. Here's Brother Shui's unemotional comparison:

    Tool Speed Lock file Project management Python management Recommendation in 2026
    pip Slow None (needs pip-tools) No No For maintaining old projects
    pipenv Very slow Pipfile.lock Yes No Not recommended
    poetry Medium poetry.lock Yes No Still usable
    uv Super fast uv.lock Yes Yes First choice

    Now you know. For a new project in 2026, just choose uv. For an old project still on pip + requirements.txt, it's worth moving over soon. If an old project uses poetry, don't panic – if it works, let it run, and think about it at the next big rewrite.

    In practice: from nothing to "runs, locked, tested"¶

    After all that, let's do a complete mini project. The task: write a little tool that "fetches a URL and prints the response status code". Requirements:

    1. Use httpx to send the request
    2. Write a test with pytest
    3. Lock the dependencies, so a teammate can run it straight away

    The full set of commands:

    # 1. Create the project
uv init url-checker
cd url-checker

# 2. Add a production dependency
uv add httpx

# 3. Add a development dependency
uv add --dev pytest

# 4. Write the code (shown below)

# 5. Run the tests
uv run pytest

# 6. Commit to git
git add .
git commit -m "init project"

    Now the code. First, the main logic file url_checker.py:

    import httpx


def check_url(url: str) -> int:
    """Return the response status code of the URL"""
    response = httpx.get(url, timeout=5.0)
    return response.status_code


def main():
    url = "https://httpbin.org/status/200"
    code = check_url(url)
    print(f"{url} -> {code}")


if __name__ == "__main__":
    main()

    Then the test file tests/test_url_checker.py:

    from url_checker import check_url


def test_check_url_returns_int():
    """Just an illustration – a real test should mock httpx"""
    # In real tests you would use respx or httpx.MockTransport to mock it
    pass


def test_status_code_type():
    """Assuming 200 is 200, the type should be int"""
    assert isinstance(200, int)

    Run the tests:

    uv run pytest

    Roughly:

    ========================= test session starts =========================
collected 2 items

tests/test_url_checker.py ..                                    [100%]
========================= 2 passed in 0.05s =========================

    Run the main program:

    uv run url_checker.py

    Output:

    https://httpbin.org/status/200 -> 200

    Send it to a teammate:

    git push origin main

    The teammate downloads it:

    git clone <repo>
cd url-checker
uv sync
uv run url_checker.py

    Three commands, an identical environment, and it runs. That's the 2026 workflow.

    The project's final folder structure¶

    url-checker/
├── .git/
├── .gitignore
├── .python-version
├── .venv/              # Created by uv automatically – not committed to git
├── README.md
├── pyproject.toml
├── tests/
│   └── test_url_checker.py
├── url_checker.py
└── uv.lock

    What goes into git:

    • .gitignore
    • .python-version
    • README.md
    • pyproject.toml
    • uv.lock (very important – don't forget to commit it)
    • tests/
    • url_checker.py

    What doesn't go into git:

    • .venv/ (uv init adds it to .gitignore automatically)
    • __pycache__/, *.pyc

    A common mistake: forgetting to commit uv.lock. Without the lock file, uv sync can't guarantee the versions match – it will work out the dependencies on the spot, and the result might be different each time. So remember: uv.lock is part of the project and must go into git.

    Some common traps and tips¶

    Trap 1: committing .venv to git¶

    Beginners easily forget to add .venv/ to .gitignore. uv init handles this for you, but if you moved an old project over by hand, remember to check .gitignore.

    Trap 2: forgetting uv.lock¶

    We just said it, but here it is again: uv.lock must go into git.

    Trap 3: installing packages globally¶

    Sometimes you'll habitually type pip install something, and it gets installed into the system Python, nothing to do with your project. In a uv project:

    • To add a project dependency, use uv add
    • To install a command-line tool globally, use uv tool install (e.g. uv tool install ruff)
    • To run something just once, use uvx

    Don't pip install directly in a uv project unless you really know what you're doing.

    Tip 1: a shared global cache¶

    uv has a global cache, so all projects share the packages they've downloaded. You can see where it is like this:

    uv cache dir

    Output:

    /Users/walter/.cache/uv

    The first uv sync in a new project installs in seconds if the packages are already cached – no downloading again. That's another reason uv is so fast.

    Clear the cache:

    uv cache clean

    You don't usually need to – only when you're short of disk space.

    Tip 2: use pyproject.toml as your settings centre¶

    As we said, pyproject.toml isn't just for project metadata – it can hold tool settings too. A fuller example:

    [project]
name = "my-project"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "httpx>=0.28",
]

[dependency-groups]
dev = [
    "pytest>=8.3",
    "ruff>=0.8",
    "mypy>=1.13",
]

[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-v"

[tool.mypy]
python_version = "3.12"
strict = true

    The settings for ruff, pytest and mypy are all together, so a newcomer can open one file and see everything. Settings that used to be scattered across .flake8, .pylintrc, pytest.ini, mypy.ini and so on can all be brought back into one place.

    Tip 3: install command-line tools with uv tool install¶

    Want to install ruff globally so it works in any folder?

    uv tool install ruff

    Same as pipx install ruff, but much faster. After installing, ruff is on your PATH.

    Upgrade:

    uv tool upgrade ruff

    Uninstall:

    uv tool uninstall ruff

    You can use uv tool instead of pipx, and instead of brew install for some Python command-line tools.

    Tip 4: run one-off commands with uvx¶

    We mentioned uvx earlier, but it's worth saying again. When you want to try a tool without installing it globally:

    uvx ruff check .
uvx pycowsay "Hello"
uvx httpie GET https://httpbin.org/get

    uvx installs it in a temporary environment, runs it, and throws it away. Dozens of times faster than pipx run.

    You can use uv for single-file scripts too¶

    An advanced trick: sometimes you write a one-off script – maybe just 50 lines of Python – but it needs httpx. Do you really need a whole new project for 50 lines?

    uv supports inline dependencies (PEP 723). Write some metadata at the top of the script:

    # /// script
# requires-python = ">=3.12"
# dependencies = [
#     "httpx",
# ]
# ///

import httpx

response = httpx.get("https://httpbin.org/get")
print(response.status_code)

    Run it:

    uv run script.py

    uv reads the metadata at the top of the script, creates a temporary environment, installs httpx, runs it, and throws the environment away. A single .py file is a complete project – send one file to a teammate and it runs.

    Writing "one-off little tools" will never be the same again.

    About publishing to PyPI¶

    This chapter is mainly about managing projects. Publishing to PyPI isn't the focus, but let's mention it briefly so you know.

    Plain uv init with no options creates a pyproject.toml without a [build-system] section, meaning it's an app, not a library. If you want to publish to PyPI, start it like this:

    uv init --package my-library

    --package creates a pyproject.toml with a [build-system] section, and a standard package structure like src/my_library/__init__.py.

    To package it, run:

    uv build

    This creates a .tar.gz (source package) and a .whl (wheel) in the dist/ folder.

    To publish to PyPI:

    uv publish

    The first time, you need to register a PyPI account and set up an API token. That's beyond this chapter – read the official uv publish docs when you want to publish.

    For most people, uv's core value is managing dependencies for apps – not for publishing packages, but so that "if it runs on my computer, it runs on yours". uv sync does that in one go.

    Summary¶

    This chapter has a lot of information. Here it is boiled down to a few things you can remember:

    First, pyproject.toml replaces everything.

    setup.py, setup.cfg, requirements.txt, requirements-dev.txt, pytest.ini, .flake8, tox.ini – in 2026, that whole scattered pile can go into one pyproject.toml file. Start new projects this way.

    Second, uv is the package manager of choice in 2026.

    Made by Astral, written in Rust, 10–100x faster, a single program, and it manages Python versions, virtual environments and dependencies all together.

    Third, remember these five core commands.

    uv init my-project       # Create a project
uv add httpx             # Add a production dependency
uv add --dev pytest      # Add a development dependency
uv sync                  # Sync the environment (what a teammate runs after downloading)
uv run python main.py    # Run a command

    Fourth, uv.lock must go into git.

    It's what guarantees the environment is identical, byte for byte.

    Fifth, old projects can use uv pip compile to make requirements.txt; new projects use uv add + uv sync.

    Next time you start a new project, free yourself from the tedious routine of "install a Python interpreter, create a virtual environment, install dependencies, write setup.py". One uv init, one uv add, and in seconds you go from nothing to running. A teammate downloads it, runs uv sync, and gets exactly the same environment.

    From 2026 on, "it works on my computer but not on yours" can go in the bin of history.

    uv init study-tracker-practice

Once you add real dependencies, practise with the lock file and the sync command. The point of this check is getting the same result from one clear folder and one set of commands – not memorising tool names.
