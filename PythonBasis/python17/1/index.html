    Type hints

    After the earlier chapters, I'm sure you can now write pretty decent Python code. Functions, classes, closures, decorators – no problem. But here's the thing about writing code: enjoying writing it yourself is one thing. Having someone else read it, or coming back to it yourself six months later, is something else.

    Come on, let's look at some code that "Brother Shui" handed over to a teammate last week:

    def calc(x, y, op):
    if op == 'add':
        return x + y
    elif op == 'sub':
        return x - y

    The teammate stares at calc, totally confused: are x and y numbers or strings? What else can op be? What type does it return? They have to dig through the code that calls it, or just shout: "Brother Shui, how do I use this function?!"

    Sound familiar? Python is a dynamic language. Variables don't need to declare their type, which makes writing code feel great. But once a project gets big and lots of people work on it, things go wrong very easily.

    Think about what problems this "unclear type" code causes:

    • Someone passes the wrong type and doesn't notice while coding. It only crashes after it's released, when a user clicks some button.
    • The IDE can't give you accurate code completion – it doesn't even know what your variable is, so how can it suggest which methods you can use?
    • Refactoring is scary – if you change this function's parameters, what else will break? You can only search the whole project, then check each line by eye.
    • Teammates keep interrupting each other – every time you want to use a function you don't know, you have to ask its author "what does this parameter mean?"

    To solve this, Python 3.5 introduced type hints. They kept improving through 3.9, 3.10 and 3.12, and they're really easy to use now. Sadly, lots of older tutorials barely mention them, so many people have written Python for years and still write def f(x, y) with nothing else.

    Imagine this: "Brother Shui" suddenly takes the weekend off and hands his project over to a teammate. The code has dozens of functions, and every one looks like def process(data, config, cb). The teammate opens one file and is lost – is data a dict or a list? Is config an object or a path? Is cb a function or a string? They have to ask about every single one, or trace through the whole call stack. That's their whole weekend gone.

    But if the function signature had been def process(data: dict[str, int], config: Path, cb: Callable[[str], None]) from the start, the teammate would understand at a glance, without asking anyone. That's the most direct value of type hints.

    So today, let's talk all about type hints, so the code you write is clearer and more professional.

    The simplest type hints¶

    Let's fix the calc function above. Say it adds or subtracts two integers:

    def calc(x: int, y: int, op: str) -> int:
    if op == 'add':
        return x + y
    elif op == 'sub':
        return x - y
    return 0


print(calc(3, 5, 'add'))
print(calc(10, 4, 'sub'))

    Output:

    8
6

    See? Now the function is clear at a glance: x and y are int, op is str, and the return value is int too. Even without any comments, the signature tells you enough.

    The syntax is simple. Remember two things:

    • After a parameter, add : type
    • For the return value, add -> type

    Remember it like this: "parameters get a colon, the return gets an arrow". It's 100% compatible with the old way of writing. Old code without hints can run together with new code that has hints, without changing a single character.

    Some of you might ask: "Can I hint only the parameters and not the return value? Or only the return value and not the parameters?"

    Absolutely. You can add hints wherever you want – you don't have to hint everything. For example:

    def double(x: int):
    return x * 2


def greet(name) -> str:
    return f'Hello, {name}'


print(double(3))
print(greet('Two Drops'))

    Output:

    6
Hello, Two Drops

    But to keep the "contract" clear, I suggest you either hint everything, or hint nothing. Half-and-half looks messy, and readers will wonder: "Did they forget to hint that one, or was it on purpose?"

    Here's a really important point you must remember: the Python interpreter does NOT check these types. They're just "notes" – for people, and for tools (IDEs, static checkers).

    Don't believe me? Let's pass the wrong type on purpose:

    def calc(x: int, y: int) -> int:
    return x + y


print(calc('Two Drops', ' Coding Dept'))

    Output:

    Two Drops Coding Dept

    See? We hinted int, but passing strings still runs, because strings support + too. Python didn't stop anything. So type hints aren't "type enforcement" – they're more like a "contract" written for your teammates.

    Then someone will ask: "If it's not enforced, why bother?"

    Good question. Here's why:

    • IDEs (PyCharm, VS Code) can use hints to give you accurate code completion and error warnings
    • Static checking tools (like mypy and pyright) can catch type errors before the code runs
    • Teammates (including your future self) save lots of guessing time when reading code

    These three reasons alone are enough to take type hints seriously.

    Another thing many people find confusing: "How do I hint a parameter that has a default value?" Easy – the hint goes first, then the equals sign and default value:

    def punch(name: str, dept: str = 'Coding Dept') -> None:
    print(f'{name} ({dept}) clocked in')


punch('Two Drops')
punch('Three Drops', 'Design Dept')

    Output:

    Two Drops (Coding Dept) clocked in
Three Drops (Design Dept) clocked in

    The format is name: type = default. Just put the three parts in that order.

    What about variable arguments like *args and **kwargs? You can hint them too. You write the type of each single item, not the type of the whole tuple/dict:

    def sum_all(*nums: int) -> int:
    return sum(nums)


def make_user(**fields: str) -> dict[str, str]:
    return fields


print(sum_all(1, 2, 3, 4, 5))
print(make_user(name='Two Drops', dept='Coding Dept'))

    Output:

    15
{'name': 'Two Drops', 'dept': 'Coding Dept'}

    *nums: int means "each item in the tuple nums is an int", not "nums itself is an int". **fields: str is the same – each value is a str. Beginners often get this wrong, so remember it.

    Common basic types¶

    The types you can write in hints are mostly Python's built-in ones:

    Type Meaning
    int Integer
    float Floating-point number
    str String
    bool Boolean
    list List
    dict Dictionary
    tuple Tuple
    set Set
    bytes Bytes
    None Nothing (used as a return type)

    Here's an example that uses several of them – a function that makes an employee profile for the "Coding Dept":

    def make_profile(name: str, age: int, salary: float, is_active: bool) -> str:
    return f'{name} ({age} years old, salary {salary}, active: {is_active})'


print(make_profile('Two Drops', 28, 12000.5, True))

    Output:

    Two Drops (28 years old, salary 12000.5, active: True)

    Try pasting this code into PyCharm or VS Code. When you type make_profile(, the IDE immediately pops up parameter hints: "the first parameter name is a str, the second parameter age is an int…". Without hints, the IDE can only dully tell you "four parameters go here", and you have to remember all the types yourself.

    See how adding hints instantly makes coding nicer?

    And this one table covers most situations. Basic types aren't fancy – the key is to use them accurately. If it's an int, write int; if it's a str, write str. Don't be lazy and write object or Any, which swallows everything.

    A few more words about bool. In Python, bool is actually a subclass of int (True == 1, False == 0). So if a parameter is hinted int and you pass True, the type checker won't complain. But the other way round – a parameter hinted bool and you pass 1 – the checker will stop you. Just be aware of this; when writing hints, follow your real intention: use bool for on/off switches, and int for numbers.

    One more small trap with int: Python's int has unlimited precision. There's no int32 or int64, so there's only one int in hints. People used to C or Java sometimes look for "where's int32?" – it doesn't exist. Just use int with confidence.

    Here's a mixed signature you'd often see when writing an "employee profile":

    def make_employee(
    name: str,
    age: int,
    height: float,
    is_intern: bool,
    skills: list,
    address: dict,
) -> str:
    return f'{name} / {age} years old / {height}m / intern: {is_intern} / skills: {skills} / address: {address}'


print(make_employee(
    'Two Drops', 28, 1.75, False,
    ['Python', 'Django'],
    {'city': 'Shenzhen', 'street': 'Science Park'},
))

    Output:

    Two Drops / 28 years old / 1.75m / intern: False / skills: ['Python', 'Django'] / address: {'city': 'Shenzhen', 'street': 'Science Park'}

    This signature is much clearer now. But look closely: skills: list and address: dict aren't good enough yet. What's inside the list? What types are the dictionary's keys and values? We don't know. That's what container types in the next section are for.

    If a function returns nothing (that is, it returns None), write None as the return type:

    def greet(name: str) -> None:
    print(f'Hello, {name}')


greet('Two Drops')

    Output:

    Hello, Two Drops

    Note: -> None here doesn't mean "I didn't write a return type". It means "I'm clearly telling you this function has no meaningful return value". These two feel very different to a reader.

    Now picture this. The "Coding Dept" clock-in function (the one from the decorators chapter), with hints added, looks like this:

    import time


def punch(name: str, dept: str) -> None:
    today = time.strftime('%Y-%m-%d', time.localtime(time.time()))
    print(f'{today}: Nickname: {name}  Department: {dept}  Clocked in for work')


punch('Two Drops', 'Coding Dept')

    Output (the date changes with the current time):

    2026-04-28: Nickname: Two Drops  Department: Coding Dept  Clocked in for work

    Look – just adding name: str, dept: str and -> None to the signature completely explains how to use the function: pass in strings, get nothing back, and it prints something. From a reader's point of view, isn't that much easier?

    What if a function might return None?¶

    Let's imagine a real situation. The "Coding Dept" employee list is a dictionary, and we write a function that looks up an employee ID by nickname:

    employees = {'Two Drops': '001', 'Three Drops': '002'}


def find_id(name: str) -> str:
    return employees.get(name)


print(find_id('Two Drops'))
print(find_id('Four Drops'))

    Output:

    001
None

    See the problem? We said the return type is str, but when the employee doesn't exist, dict.get() returns None, not a str. The hint and the real behaviour don't match.

    "Either return X, or return None" is very common. The old way to write it was with Optional from the typing module:

    from typing import Optional


employees = {'Two Drops': '001', 'Three Drops': '002'}


def find_id(name: str) -> Optional[str]:
    return employees.get(name)


print(find_id('Two Drops'))
print(find_id('Four Drops'))

    Optional[str] means "this value is either a str or None".

    But importing Optional from typing every time gets really annoying. In Python 3.10, a simpler way was introduced (PEP 604): join the types with a vertical bar |:

    employees = {'Two Drops': '001', 'Three Drops': '002'}


def find_id(name: str) -> str | None:
    return employees.get(name)


print(find_id('Two Drops'))
print(find_id('Four Drops'))

    Output:

    001
None

    Doesn't str | None read more naturally? "A string or nothing" – just like "or" in English.

    I really want to stress this: a return type of str | None does not mean the caller can just use it as a str. You must check which one it is before using it. Look at this:

    def find_id(name: str) -> str | None:
    db = {'Two Drops': '001'}
    return db.get(name)


emp_id = find_id('Four Drops')
print(emp_id.upper())

    The IDE will immediately underline emp_id.upper() in red, because emp_id might be None, and None has no upper method. The correct way is to check first:

    def find_id(name: str) -> str | None:
    db = {'Two Drops': '001'}
    return db.get(name)


emp_id = find_id('Two Drops')
if emp_id is not None:
    print(emp_id.upper())
else:
    print('Employee not found')

    Output:

    001

    Inside this if branch, the type checker automatically narrows the type – it knows that inside if emp_id is not None:, emp_id must be a str, so .upper() is fine. This clever trick is called type narrowing, and it's one of the most useful abilities of modern type checkers.

    And | isn't just for None – you can join as many types as you like:

    def to_int(value: int | str | float) -> int:
    return int(value)


print(to_int(3))
print(to_int('5'))
print(to_int(7.8))

    Output: 

    3
5
7

    int | str | float means "this parameter can be an int, a str or a float". The technical name for this is a union type.

    The X | Y syntax only works in Python 3.10+. If your project still uses 3.9 or older, you have to use from typing import Union; Union[X, Y]. But honestly, it's 2026 – upgrade if you can.

    To sum up:

    • Old way: Optional[str], Union[int, str] – needs from typing import ...
    • New way: str | None, int | str – no import needed, just write it

    For new code, always use the new way.

    One more small detail. Once a function has a return type of X | None, the caller is "reminded" to handle the None case. For example:

    employees = {'Two Drops': '001', 'Three Drops': '002'}


def find_id(name: str) -> str | None:
    return employees.get(name)


emp_id = find_id('Four Drops')
if emp_id is None:
    print('Employee not found')
else:
    print(f'Employee ID: {emp_id}')

    Output:

    Employee not found

    Without | None, the caller can easily forget to check for empty values, and go straight on to join strings or query a database with the return value – then crash halfway through. Hints + a static checker can remind you the moment you forget to check.

    How to hint container types¶

    Just saying list isn't enough. Look at this function:

    def total_salary(salaries: list) -> float:
    return sum(salaries)


print(total_salary([10000, 12000, 8000]))

    Output:

    30000

    It says list, but it doesn't say what's in the list. ints? floats? strs? The reader still has to guess.

    Here comes the old way again: import capitalised List, Dict, Tuple and so on from typing:

    from typing import List


def total_salary(salaries: List[float]) -> float:
    return sum(salaries)


print(total_salary([10000, 12000, 8000]))

    List[float] means "a list that holds floats". The type in the square brackets is the type of the elements.

    In Python 3.9 (PEP 585), the Python team said: "Everyone uses these every day – having to import them is so annoying. Why not just let list itself take square brackets?" And so the new way arrived:

    def total_salary(salaries: list[float]) -> float:
    return sum(salaries)


print(total_salary([10000, 12000, 8000]))

    Output:

    30000

    Look – we just use lowercase list[float] directly, with no import. Other containers work the same way:

    def group_by_dept(staff: dict[str, list[str]]) -> int:
    return len(staff)


data = {
    'Coding Dept': ['Two Drops', 'Three Drops'],
    'Design Dept': ['Four Drops'],
}
print(group_by_dept(data))

    Output:

    2

    dict[str, list[str]] means "a dictionary whose keys are str and whose values are lists of str". Even nested types like this are easy to read.

    While we're here, a word about choosing between list and Sequence. list[int] feels natural to write, but sometimes your function doesn't really need a list – it just needs something you can loop through and index. In that case, Sequence is more flexible:

    from collections.abc import Sequence


def first_and_last(items: Sequence[int]) -> tuple[int, int]:
    return items[0], items[-1]


print(first_and_last([1, 2, 3]))
print(first_and_last((10, 20, 30)))

    Output:

    (1, 3)
(10, 30)

    Sequence[int] accepts lists, tuples, strings… anything that's an ordered container. Similar ones are Iterable[X] (anything you can loop through, even a generator) and Mapping[K, V] (anything you can look up values in like a dict). These abstract types are especially useful when writing libraries, because they let a function accept a wider range of inputs. For everyday code, don't worry too much – plain list[int] is totally fine.

    tuple is a bit special. For a fixed-length tuple, write the type of each position:

    def parse_point(p: tuple[int, int]) -> int:
    x, y = p
    return x + y


print(parse_point((3, 5)))

    Output:

    8

    For a tuple of any length where every element is the same type (less common), use ...:

    def join_names(names: tuple[str, ...]) -> str:
    return ', '.join(names)


print(join_names(('Two Drops', 'Three Drops', 'Four Drops')))

    Output:

    Two Drops, Three Drops, Four Drops

    set is like list:

    def unique_count(tags: set[str]) -> int:
    return len(tags)


print(unique_count({'Python', 'Java', 'Python'}))

    Output:

    2

    Remember this: from 3.9 on, all built-in containers can be used directly as types – no need to import the capitalised versions from typing.

    Let's look at a few more complicated nested containers. Say we have a data structure that records how many times each employee clocked in each day:

    punches: dict[str, dict[str, int]] = {
    'Two Drops': {'2026-04-26': 2, '2026-04-27': 1},
    'Three Drops': {'2026-04-26': 1, '2026-04-27': 2},
}


def total_punches(data: dict[str, dict[str, int]], name: str) -> int:
    return sum(data.get(name, {}).values())


print(total_punches(punches, 'Two Drops'))
print(total_punches(punches, 'Three Drops'))
print(total_punches(punches, 'Four Drops'))

    Output:

    3
3
0

    Nested types like dict[str, dict[str, int]] can be tiring to read at first. But break it down – "the outer keys are str (employee nicknames), and the values are dict[str, int] (date → count)" – and the logic is clear. Later we'll see that if a nested type like this appears many times, you can simplify it with a type alias.

    Let's do a bigger example to practise. The "Coding Dept" wants a staff statistics function. The input is a list of employee records, and the output is the number of people in each department:

    def count_by_dept(records: list[dict[str, str]]) -> dict[str, int]:
    result: dict[str, int] = {}
    for r in records:
        dept = r['dept']
        result[dept] = result.get(dept, 0) + 1
    return result


data = [
    {'name': 'Two Drops', 'dept': 'Coding Dept'},
    {'name': 'Three Drops', 'dept': 'Coding Dept'},
    {'name': 'Four Drops', 'dept': 'Design Dept'},
]
print(count_by_dept(data))

    Output:

    {'Coding Dept': 2, 'Design Dept': 1}

    The whole function's input and output are clear just from the signature list[dict[str, str]] -> dict[str, int]: "pass in a list of field-name-to-value dictionaries, and get back a department-to-headcount dictionary". Nice, right?

    There's a small detail hidden here: result: dict[str, int] = {} inside the function also has a hint. It tells the IDE "result will hold str → int". Otherwise, when the IDE sees result = {}, it can only guess "an empty dict, anything can go in", and won't warn you if you make a mistake.

    Variables can have hints too¶

    It's not just function parameters and return values – normal variables can have hints too. The syntax is the same as for parameters:

    name: str = 'Two Drops'
age: int = 28
salary: float = 12000.5
tags: list[str] = ['Python', 'Backend']

print(name, age, salary, tags)

    Output:

    Two Drops 28 12000.5 ['Python', 'Backend']

    Then someone asks: "When I assign a variable, isn't the type obvious? Why not just write name = 'Brother Shui'? Why add a hint?"

    There are two situations where it's really needed:

    First: when the starting value doesn't show the final type. For example, you create an empty list and want to tell others "this list will hold strings":

    employees: list[str] = []
employees.append('Two Drops')
employees.append('Three Drops')
print(employees)

    Output:

    ['Two Drops', 'Three Drops']

    Without a hint, when the IDE sees employees = [], it can only guess "a list, element type unknown", and won't complain whatever you append. With list[str], if you accidentally write employees.append(123), the IDE underlines it in red straight away.

    Here's a very realistic little scenario. We're writing the setup code for a login points system – "Brother Shui" earns some points every day he logs in, but he starts with none:

    points: int = 0
visited_pages: list[str] = []
last_login: str | None = None


points += 5
visited_pages.append('Home')
last_login = '2026-04-28'

print(points, visited_pages, last_login)

    Output:

    5 ['Home'] 2026-04-28

    Look at the line last_login: str | None = None. It starts as None, but its type is str | None. Saying "this can be empty, and gets a real value later" is very common in long processes. Without the hint, the IDE might decide last_login is just None. It might not complain when you later assign a string, but the meaning isn't as clear.

    The same goes for empty dicts and empty sets:

    scores: dict[str, int] = {}
scores['Two Drops'] = 95
scores['Three Drops'] = 88
print(scores)


unique_tags: set[str] = set()
unique_tags.add('Python')
unique_tags.add('Backend')
unique_tags.add('Python')
print(unique_tags)

    Output:

    {'Two Drops': 95, 'Three Drops': 88}
{'Python', 'Backend'}

    Second: declaring without assigning. For example, class attributes:

    class Employee:
    name: str
    age: int

    def __init__(self, name: str, age: int):
        self.name = name
        self.age = age


emp = Employee('Two Drops', 28)
print(emp.name, emp.age)

    Output:

    Two Drops 28

    Writing name: str directly in the class body declares an attribute of type str, without even giving a default value. You'll see this much more with dataclasses, which come later.

    You can also give default values directly in the class body, much like declaring variables:

    class Counter:
    count: int = 0
    name: str = 'Default counter'

    def incr(self) -> None:
        self.count += 1


c = Counter()
c.incr()
c.incr()
print(c.name, c.count)

    Output:

    Default counter 2

    Careful: giving default values in the class body really creates class attributes (shared by all instances). If the default is immutable (int, str, tuple…), it works almost the same as an instance default. But if the default is a mutable object like a list or dict, it's a trap – all instances share the same list! So for list and dict fields, we usually set them up in __init__, or use a dataclass with field(default_factory=list). More on that later.

    Callable and Any – two special roles¶

    After hinting a few functions, sooner or later you'll ask: "My function's parameter is another function – how do I hint that?"

    If you've learned decorators, you'll remember that functions are objects too, and can be passed around. The type for "something you can call" is Callable, from collections.abc:

    from collections.abc import Callable


def apply(func: Callable[[int, int], int], x: int, y: int) -> int:
    return func(x, y)


print(apply(lambda a, b: a + b, 3, 5))
print(apply(lambda a, b: a * b, 3, 5))

    Output:

    8
15

    How do you read Callable[[int, int], int]? Inside the square brackets, the first list is the parameter types, and the second item is the return type. So it means: "a function that takes two ints and returns an int".

    Before Python 3.9, Callable was also imported from typing. From 3.9 on, it's recommended to import it from collections.abc.

    If you've learned decorators, you'll realise a decorator is really "something that takes a function and returns a function". So decorators can be hinted with Callable too:

    from collections.abc import Callable


def with_log(func: Callable[[int, int], int]) -> Callable[[int, int], int]:
    def wrapper(x: int, y: int) -> int:
        print(f'Calling {func.__name__}({x}, {y})')
        return func(x, y)
    return wrapper


@with_log
def add(x: int, y: int) -> int:
    return x + y


print(add(3, 5))

    Output:

    Calling add(3, 5)
8

    The signature of with_log is clear at a glance: "I take in a function that takes two ints and returns an int, and give back a function of exactly the same shape". Of course, to write a general decorator that can wrap any function, Callable alone isn't enough – you need more advanced tools like ParamSpec and TypeVar. That's a different topic, so we won't go into it here.

    There's another role called Any, which means "any type is fine, don't check". Use it when you really don't care about the type:

    from typing import Any


def log(value: Any) -> None:
    print(f'Log: {value}')


log('Two Drops')
log(123)
log([1, 2, 3])

    Output:

    Log: Two Drops
Log: 123
Log: [1, 2, 3]

    Any sounds handy, but be careful with it. Once you hint Any, the type checker ignores that value completely – you throw away all the benefits of hints. If you can write a specific type, never use Any.

    You might ask: "So when should I use Any?" Usually in two situations:

    • You're writing a truly general tool function and really don't know what type will come in (like print)
    • You're working with an old library without hints, where even its author can't say what the types are, and forcing a hint would make things messier

    Otherwise, first choose a specific type, then a union type, then a loose abstract type like object or Sequence, and only as a last resort, Any. That's the priority order for writing hints – remember it.

    For example, say we want a function that turns any input into a string. Your first idea might be:

    from typing import Any


def to_str(x: Any) -> str:
    return str(x)


print(to_str(123))
print(to_str([1, 2, 3]))
print(to_str({'name': 'Two Drops'}))

    Output:

    123
[1, 2, 3]
{'name': 'Two Drops'}

    But think about it: is x really "anything at all"? No. str(x) really just calls x.__str__(), so a more accurate description is "any object that str() can handle". Every object in Python has __str__ (inherited from object), so object is actually more accurate here than Any:

    def to_str(x: object) -> str:
    return str(x)


print(to_str(123))
print(to_str([1, 2, 3]))
print(to_str({'name': 'Two Drops'}))

    Output:

    123
[1, 2, 3]
{'name': 'Two Drops'}

    Same result, but the hint works much better as built-in documentation. When readers see x: Any, they wonder "can I pass functions, classes, generators?" When they see x: object, they immediately understand "any object works". Paying attention to details like this makes your code read very professionally.

    While we're here, object is often confused with Any. object is the parent of all types. Hinting object means "pass anything, but once you have it, you can only use methods every object has (like str())". It looks like Any, but it behaves very differently:

    def show(x: object) -> None:
    print(str(x))


show('Two Drops')
show(123)
show([1, 2, 3])

    Output:

    Two Drops
123
[1, 2, 3]

    If you hint x as object and then write x.upper() in the function, the type checker complains – because "object has no upper method". With Any, it wouldn't complain. So if you want "the function accepts any type, but you must check/convert it before using it", object is safer than Any.

    Is your type too long? Give it a nickname (alias)¶

    Let's look at a slightly more complicated situation. The "Coding Dept" wants an archive of all employees. Each employee's profile is "name + list of tags", and the whole archive is a mapping of "department name → list of employee profiles". The hint looks like this:

    def add_employee(
    db: dict[str, list[tuple[str, list[str]]]],
    dept: str,
    profile: tuple[str, list[str]],
) -> None:
    db.setdefault(dept, []).append(profile)


db: dict[str, list[tuple[str, list[str]]]] = {}
add_employee(db, 'Coding Dept', ('Two Drops', ['Python', 'Backend']))
add_employee(db, 'Coding Dept', ('Three Drops', ['Frontend']))
print(db)

    Output:

    {'Coding Dept': [('Two Drops', ['Python', 'Backend']), ('Three Drops', ['Frontend'])]}

    Isn't dict[str, list[tuple[str, list[str]]]] really tiring to read? And every time you need this type you have to copy it again. Miss one square bracket somewhere, and you've planted a bug.

    This is when type aliases come in. From Python 3.12, there's a brand-new type keyword (PEP 695). You can write:

    type Profile = tuple[str, list[str]]
type EmployeeDB = dict[str, list[Profile]]


def add_employee(db: EmployeeDB, dept: str, profile: Profile) -> None:
    db.setdefault(dept, []).append(profile)


db: EmployeeDB = {}
add_employee(db, 'Coding Dept', ('Two Drops', ['Python', 'Backend']))
add_employee(db, 'Coding Dept', ('Three Drops', ['Frontend']))
print(db)

    The type Alias = ... syntax only works in Python 3.12+.

    Now the names Profile and EmployeeDB explain their meaning at a glance. And because the type is defined in one place, it's easy to change.

    Let's actually run it (on 3.12+):

    Profile = tuple[str, list[str]]
EmployeeDB = dict[str, list[Profile]]


def add_employee(db: EmployeeDB, dept: str, profile: Profile) -> None:
    db.setdefault(dept, []).append(profile)


db: EmployeeDB = {}
add_employee(db, 'Coding Dept', ('Two Drops', ['Python', 'Backend']))
add_employee(db, 'Coding Dept', ('Three Drops', ['Frontend']))
print(db)

    Output:

    {'Coding Dept': [('Two Drops', ['Python', 'Backend']), ('Three Drops', ['Frontend'])]}

    Note: the code above actually uses plain assignment – it assigns the type to a normal variable. This works in every version that supports type hints, and at runtime it just defines an ordinary variable. But strictly speaking, type checkers won't necessarily treat it as a "type alias".

    If your project runs on 3.10 or 3.11, and you want to clearly tell the checker "this is an alias", use TypeAlias:

    from typing import TypeAlias


Profile: TypeAlias = tuple[str, list[str]]
EmployeeDB: TypeAlias = dict[str, list[Profile]]


def add_employee(db: EmployeeDB, dept: str, profile: Profile) -> None:
    db.setdefault(dept, []).append(profile)


db: EmployeeDB = {}
add_employee(db, 'Coding Dept', ('Two Drops', ['Python']))
print(db)

    Output:

    {'Coding Dept': [('Two Drops', ['Python'])]}

    A quick summary:

    • Python 3.12+: just write type Alias = ... – the cleanest
    • Python 3.10/3.11: use Alias: TypeAlias = ...
    • Plain assignment Alias = ...: works, but the meaning isn't as clear as the other two

    Type aliases have another very useful job: giving names to business ideas. Like this:

    UserId = int
ProductId = int


def get_user(uid: UserId) -> str:
    return f'User {uid}'


def get_product(pid: ProductId) -> str:
    return f'Product {pid}'


print(get_user(1001))
print(get_product(2002))

    Output:

    User 1001
Product 2002

    UserId and ProductId are both int underneath, but they have different names. Reading def get_user(uid: UserId) tells you much more than def get_user(uid: int) – you can see at a glance "this int isn't just any number, it's a user ID".

    Here's an example of what not to do. The "Coding Dept"'s original code looked like this:

    def transfer(from_id: int, to_id: int, product_id: int, amount: int) -> bool:
    print(f'Transfer {amount} of product {product_id} from user {from_id} to user {to_id}')
    return True


transfer(1001, 2002, 3003, 5)

    Output:

    Transfer 5 of product 3003 from user 1001 to user 2002

    All four parameters are int. Get the order wrong when calling it, and you're in trouble – a product ID might be used as a user ID, or an amount as a product ID, and there won't even be an error, because the types match. With named aliases, the syntax still doesn't force anything, but the IDE hint becomes from_id: UserId, to_id: UserId, product_id: ProductId, amount: int, so you're much less likely to make a mistake.

    To go further and really prevent bugs like "passing a product ID as a user ID", you can use NewType:

    from typing import NewType


UserId = NewType('UserId', int)
ProductId = NewType('ProductId', int)


def get_user(uid: UserId) -> str:
    return f'User {uid}'


print(get_user(UserId(1001)))

    Output:

    User 1001

    At runtime, NewType is just a function that passes the value straight through. But to the type checker, UserId and int are two different types – passing a plain int will be flagged. This truly turns a "business idea" into a "type". It's especially useful in big projects, but for small projects, type Alias is enough.

    How to hint class attributes¶

    We wrote an Employee class earlier. Let's go a bit deeper into hinting class attributes.

    The plainest way looks like this:

    class Employee:
    def __init__(self, name, age, salary):
        self.name = name
        self.age = age
        self.salary = salary


emp = Employee('Two Drops', 28, 12000.5)
print(emp.name)

    Output:

    Two Drops

    Reading this Employee class, just from __init__ we can't tell what type each attribute is. Let's improve it:

    class Employee:
    def __init__(self, name: str, age: int, salary: float) -> None:
        self.name = name
        self.age = age
        self.salary = salary


emp = Employee('Two Drops', 28, 12000.5)
print(emp.name, emp.age, emp.salary)

    Output:

    Two Drops 28 12000.5

    Once the parameters have hints, the IDE can usually work out that self.name is a str. If you want to be even clearer, declare the attributes separately in the class body too:

    class Employee:
    name: str
    age: int
    salary: float

    def __init__(self, name: str, age: int, salary: float) -> None:
        self.name = name
        self.age = age
        self.salary = salary


emp = Employee('Two Drops', 28, 12000.5)
print(emp.name, emp.age, emp.salary)

    Output:

    Two Drops 28 12000.5

    The three lines at the top of the class body are class-level hints, for type checkers and tools. Together with self.xxx = xxx in __init__, they make the class's "attribute blueprint" clear at a glance.

    Do "name: str in the class body" and "self.name = name in __init__" have to go together? Strictly no, but pairing them is safest. If you only declare in the class body without assigning in __init__, accessing it gives an AttributeError. If you only assign in __init__ without declaring in the class body, the type checker has a less clear picture of the class's attributes.

    Instance methods follow the same rules. You don't hint self; hint the other parameters and the return value as normal:

    class Wallet:
    balance: float

    def __init__(self, initial: float = 0) -> None:
        self.balance = initial

    def deposit(self, amount: float) -> float:
        self.balance += amount
        return self.balance

    def can_afford(self, price: float) -> bool:
        return self.balance >= price


w = Wallet(100.0)
print(w.deposit(50.5))
print(w.can_afford(120))
print(w.can_afford(160))

    Output:

    150.5
True
False

    The signatures read smoothly, right? deposit "takes a float, returns a float"; can_afford "takes a float, returns a bool". The intention is clear at a glance.

    Now think: after writing a few classes like this – "a bunch of attributes + an __init__ that's all assignments" – doesn't it get annoying? You write every attribute twice (once in the class body, once in __init__).

    Yes – that's exactly the problem dataclass solves. It lets you write only the type declarations in the class body, and creates __init__ for you automatically. We'll cover this in python20. Let's keep you in suspense for now.

    Protocol – duck typing for type hints¶

    If you've used Python for a while, you've heard the saying: "If it walks like a duck and quacks like a duck, it's a duck." This is duck typing. One of Python's core ideas is: "I don't care whether you're an instance of the Duck class – as long as you can quack(), I'll treat you as a duck."

    But here's the problem: how do you say that with type hints? You can't write def feed(d: Duck) and force everyone to inherit from Duck – that goes against the whole idea of duck typing.

    Python 3.8 introduced Protocol (PEP 544) to solve exactly this. It means: as long as an object has the methods and attributes I need, it fits this protocol – even if it doesn't inherit from it.

    Let's look at an example. The "Coding Dept" keeps lots of different animals, and we want a general function that "makes them make a sound":

    from typing import Protocol


class Quacker(Protocol):
    def quack(self) -> str:
        ...


class Duck:
    def quack(self) -> str:
        return 'Quack quack quack'


class Dog:
    def quack(self) -> str:
        return 'Woof woof woof (actually I am not a duck)'


def let_it_quack(animal: Quacker) -> None:
    print(animal.quack())


let_it_quack(Duck())
let_it_quack(Dog())

    Output:

    Quack quack quack
Woof woof woof (actually I am not a duck)

    Look – neither Duck nor Dog inherits from Quacker, but they both have a quack method, so passing them to let_it_quack is fine. This is called structural subtyping. If you pass in an object without a quack method, the type checker complains straight away.

    The good thing about Protocol is that you don't need to plan the inheritance in advance – as long as the "shape" matches, it works. It's a really handy tool for writing libraries and frameworks.

    Here's a more realistic example. Say we want a tool function that prints the size of anything. Thinking in duck typing: "if you can call len() on it, it has a size":

    from typing import Protocol


class Sized(Protocol):
    def __len__(self) -> int:
        ...


def show_size(obj: Sized) -> None:
    print(f'The size is {len(obj)}')


show_size('Two')
show_size([1, 2, 3, 4])
show_size({'a': 1, 'b': 2})

    Output:

    The size is 3
The size is 4
The size is 2

    str, list and dict don't inherit from our Sized, but they all have __len__, so they all fit the protocol. This "by shape, not by inheritance" polymorphism is both flexible and type-safe.

    Protocol can describe attributes as well as methods. For example, "I need an object with a name attribute":

    from typing import Protocol


class HasName(Protocol):
    name: str


class Employee:
    def __init__(self, name: str, dept: str) -> None:
        self.name = name
        self.dept = dept


class Pet:
    def __init__(self, name: str, kind: str) -> None:
        self.name = name
        self.kind = kind


def shout_name(obj: HasName) -> None:
    print(f'Hello, {obj.name}!')


shout_name(Employee('Two Drops', 'Coding Dept'))
shout_name(Pet('Goldie', 'duck'))

    Output:

    Hello, Two Drops!
Hello, Goldie!

    Employee and Pet have nothing to do with each other, but both have a name attribute, so both can be passed to shout_name.

    This is really useful when writing libraries or middle layers – you don't force callers to inherit from your base class. Their existing types can plug straight in as long as the "shape" fits. It's extremely extensible.

    This is just a taste. Protocol has deeper features like runtime_checkable and attribute protocols – I'll leave those for curious readers to explore.

    Once you've written hints, how do you actually check the types?¶

    By now you're probably asking: "I've written all these hints, but the Python interpreter doesn't enforce them. So how do I actually find type errors?"

    Answer: use a static type checker. The two common ones are:

    • mypy: the veteran, with the most mature community
    • pyright: made by Microsoft, fast – it's the core of Pylance in VS Code

    Pick either one. To install:

    pip install mypy

    Say we've written a file bad.py:

    def add(x: int, y: int) -> int:
    return x + y


print(add('Two Drops', 3))

    python bad.py doesn't notice anything is wrong until that line actually runs (and then it crashes with a TypeError). But run mypy bad.py:

    bad.py:5: error: Argument 1 to "add" has incompatible type "str"; expected "int"  [arg-type]
Found 1 error in 1 file (checked 1 source file)

    Now try another typical mistake – forgetting to handle None:

    def find_id(name: str) -> str | None:
    db = {'Two Drops': '001'}
    return db.get(name)


emp_id = find_id('Four Drops')
print(emp_id.upper())

    Running it with python gives AttributeError: 'NoneType' object has no attribute 'upper' – that would be a crash in the live app. But mypy warns you as soon as you've written the code:

    bad.py:7: error: Item "None" of "str | None" has no attribute "upper"  [union-attr]

    See? For mistakes like "forgot to check for None", mypy is a lifesaver – edge cases you didn't think of, it finds by scanning the code.

    Errors that would slip through at runtime, mypy catches after you write the code but before you run it. That's the biggest point of type hints.

    In real projects, people usually add mypy or pyright to CI (automatic checks), running together with unit tests, to stop lots of silly mistakes before code is merged.

    You might ask again: "My IDE (PyCharm, VS Code) already underlines errors using the hints. Do I still need to run mypy separately?"

    Answer: yes, it's best to. Here's why:

    • IDE underlines only show when you open that file. Old files nobody opens can hide type errors for years
    • IDE settings can be different on different people's computers – some see the warnings, some don't
    • Running mypy in CI is "objective and enforced" – if it fails, the code is blocked, and nobody can pretend they didn't see it

    So the recommended approach: rely on the IDE for instant feedback while coding, and let mypy/pyright guard the gate before code is submitted. With both lines of defence, type errors can really be controlled.

    One last common question: "If an old project has lots of code without hints, will mypy fill the screen with errors?" Yes. So for old projects, people usually add it gradually:

    • First, loosen the checks in mypy.ini or pyproject.toml (--ignore-missing-imports, don't require return type hints, and so on)
    • All new code gets hints; old code gets hints when you touch it
    • After a few rounds, coverage slowly rises, and you gradually tighten the rules

    Never switch on --strict from day one – that basically means "I'm going to rewrite the whole project", and nobody can handle that. Step by step is the safe way.

    Some common questions¶

    To finish, let's answer some questions people keep asking:

    Q1: Do hints make Python slower?

    Hardly at all. To the interpreter, hints are just "read them and store them in __annotations__". No checking happens at runtime. Unless a function is called extremely often and has extremely complicated hints, you won't be able to measure any difference. Write them without worrying.

    Q2: Do hints clash with docstrings?

    No – they work together. Hints cover types; docstrings cover business meaning, rules about behaviour, and examples. Using both gives the full picture:

    def punch(name: str, dept: str = 'Coding Dept') -> None:
    """Record an employee clocking in for work.

    Args:
        name: the employee's nickname, e.g. 'Two Drops'
        dept: the department name, 'Coding Dept' by default

    Clock-ins are only recorded in memory, not written to a database.
    """
    print(f'{name} ({dept}) clocked in')


punch('Two Drops')

    Output:

    Two Drops (Coding Dept) clocked in

    Q3: Do I have to add hints to every line?

    No. From most to least important:

    1. Public functions/classes (ones other people will call): try to hint them all – this is the interface contract
    2. Complicated business functions (many parameters, deep nesting): hint them, to make later maintenance easier
    3. Simple one-off scripts: up to you; it's fine without

    In a loop like for i in range(10): print(i), i is obviously an int – no need to force in i: int. The value of hints is removing confusion. Adding them where there's no confusion just makes code wordy.

    Q4: What if a third-party library has no hints?

    Lots of older libraries may not have hints. Then you can:

    • Check whether the library has a py.typed marker (which means the author promises type support)
    • If not, use the stub packages maintained by the typeshed community (package names are usually types-xxx)
    • If there really is nothing, add a variable hint where you call it to "patch" it: result: list[str] = some_legacy_lib.get_data()

    Popular modern libraries (FastAPI, httpx, Pydantic, SQLAlchemy 2.x and so on) have fully embraced type hints. When choosing a new library, it's worth checking this.

    Summary¶

    At first, type hints look like extra work for Python. Once you get used to them, you'll love them. Three final points:

    • Hints are only for people and tools – the Python interpreter doesn't enforce them. To really check types, run mypy or pyright
    • Use the new syntax: X | None instead of Optional[X], list[int] instead of List[int] – one less import, a lot cleaner
    • Start with signatures: function parameters and return values give you the most value for your effort. Add variable and class attribute hints as needed. When a type gets ridiculously long, give it a name with a type alias

    Build the habit of writing hints, and your code will get more professional every day.

    Finally, a little puzzle for curious readers: in this article we've seen int | None, list[int], Callable[[int, int], int], Protocol, type aliases… So how would you write a function that "takes any type T and returns a list of that same type T" (for example, "wrap any item in a one-item list")?

    Hint: you need generics. The keyword is TypeVar, or the new generic syntax in Python 3.12+ (def wrap[T](x: T) -> list[T]: ...). It's a bit advanced, but once you've written a few tool functions and small frameworks, you'll naturally want to look it up. Good work takes time – let's take it slowly.

    Here are some more directions to explore after this chapter:

    • Literal['get', 'post']: limit a string to a few allowed values – great for writing API clients
    • TypedDict: give each key in a dictionary its own type – much better than dict[str, Any]
    • Final: say "this variable must not be changed after it's assigned"
    • @override (Python 3.12+): clearly mark "I am overriding a parent class's method"
    • The Self type (Python 3.11+): a neater way to write "returns myself" in a class
    • Generic classes, generic functions, ParamSpec: standard tools for writing libraries

    These are all members of the type hint family. You don't need to learn them all at once – learning each one when you need it is the most efficient way.

    The most important thing about type hints isn't "learning them all" – it's using them. Starting today, add a signature every time you write a new function. Look back in a month, and you'll find your coding "muscle memory" has completely changed. That's enough.

    Once hints are written, is the input guaranteed to be correct?¶

    We've explained what type hints are for. Now check for yourself how they differ from checks at runtime:

    def add_minutes(first: int, second: int) -> int:
    return first + second


print(add_minutes(5, 10))
print(add_minutes('5', '10'))

    Output:

    15
510

    The second time, we passed strings, and the interpreter still joined them together as strings. Hints help people and static checkers understand what you meant, but they don't automatically turn text into integers for us, or reject input that breaks our rules.

    Add a docstring to this function yourself, saying the unit is minutes, and decide whether negative numbers are allowed. "The type is an integer" only answers part of the question. Is it non-negative? Is there a maximum? What happens with an empty record? You still need to write down these rules clearly and test them.

    When reading, look at names and function interfaces first, then look up advanced hints as you need them. You don't have to master every type tool before writing a small function.
