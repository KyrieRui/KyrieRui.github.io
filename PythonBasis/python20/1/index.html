    dataclass and Pydantic

    When writing code, it's easy to get stuck in the swamp of boilerplate code. Don't argue yet – let's do a small experiment. Write an Employee class with these requirements: it stores an employee's name, department, employee ID, start date and monthly salary; it should print nicely (not something horrible like <__main__.Employee object at 0x...>); you should be able to check whether two employee objects are equal; and ideally it can be used as a dictionary key.

    Doesn't sound hard, right? If you like to think things through, you've probably already written it in your head. It looks something like this:

    class Employee:
    def __init__(self, name, dept, emp_id, hire_date, salary):
        self.name = name
        self.dept = dept
        self.emp_id = emp_id
        self.hire_date = hire_date
        self.salary = salary

    def __repr__(self):
        return (
            f'Employee(name={self.name!r}, dept={self.dept!r}, '
            f'emp_id={self.emp_id!r}, hire_date={self.hire_date!r}, '
            f'salary={self.salary!r})'
        )

    def __eq__(self, other):
        if not isinstance(other, Employee):
            return NotImplemented
        return (
            self.name == other.name
            and self.dept == other.dept
            and self.emp_id == other.emp_id
            and self.hire_date == other.hire_date
            and self.salary == other.salary
        )

    def __hash__(self):
        return hash((self.name, self.dept, self.emp_id, self.hire_date, self.salary))


e = Employee('Two Drops', 'Coding Dept', 1001, '2020-03-15', 12000)
print(e)

    Output:

    Employee(name='Two Drops', dept='Coding Dept', emp_id=1001, hire_date='2020-03-15', salary=12000)

    Count them: this ordinary little "data class" takes over twenty lines. __init__ lists the fields once, __repr__ lists them again, __eq__ lists them again, and __hash__ lists them yet again – the same field names appear five times. Now imagine your class has 15 fields. The __init__ parameter list would be as long as a train, and you'd copy and paste self.xxx = xxx again and again. By the tenth one, you'd want to scream.

    This is what we call boilerplate code. It doesn't add any business value – it's only there because Python's syntax makes you write it. The person writing it hates it, and so does the person reading it, because the important information – "what fields does this class have?" – is buried in the repetitive noise of self.xxx = xxx.

    Is there a way to just declare the fields, and let Python do the rest?

    Yes. Python 3.7 gave us dataclass. From 3.10, it gained more modern switches like slots and kw_only. Beyond that, there's the third-party library Pydantic, which focuses on "data models with runtime validation". In this article, let's go from dataclass all the way to Pydantic, so your fingers never get tied in knots writing data structures again.

    What does your first dataclass look like?¶

    Let's rewrite the Employee class above with dataclass:

    from dataclasses import dataclass


@dataclass
class Employee:
    name: str
    dept: str
    emp_id: int
    hire_date: str
    salary: int


e = Employee('Two Drops', 'Coding Dept', 1001, '2020-03-15', 12000)
print(e)

    Output:

    Employee(name='Two Drops', dept='Coding Dept', emp_id=1001, hire_date='2020-03-15', salary=12000)

    Look – over twenty lines shrink to under ten. Just add the @dataclass decorator, and Python does all this for us:

    • It sees "class variables with type hints" like name: str and dept: str, and automatically treats them as fields
    • It automatically creates an __init__, with the parameters in the same order as the fields
    • It automatically creates a __repr__ that looks exactly like the hand-written "ClassName(field=value, field=value)" one
    • It automatically creates an __eq__ that compares the fields one by one

    All you have to do is write the field names and their types. dataclass does all the rest.

    Are the type hints required? Yes. They're how dataclass recognises fields. If you only write name = '' without name: str, dataclass won't recognise it – it treats name as a normal class attribute, and it won't go into the __init__ parameter list.

    Remember this: in a dataclass, name: str is a field declaration, and name = 'default' (with no hint) is a class attribute. They do completely different things.

    from dataclasses import dataclass


@dataclass
class Demo:
    a: int        # This is a field – it goes into __init__
    b: int = 10   # This is a field with a default value – it also goes into __init__
    c = 20        # Note: no type hint here, so it's a normal class attribute – NOT in __init__


d = Demo(1)
print(d)
print(d.c)

    Output:

    Demo(a=1, b=10)
20

    See? c doesn't appear in the repr, because it isn't a field at all – it's just a constant attached to the class.

    Comparing two dataclass objects¶

    dataclass creates __eq__ by default, so two objects with exactly the same field values are considered equal:

    from dataclasses import dataclass


@dataclass
class Employee:
    name: str
    dept: str
    salary: int


a = Employee('Two Drops', 'Coding Dept', 12000)
b = Employee('Two Drops', 'Coding Dept', 12000)
c = Employee('Two Drops', 'Coding Dept', 15000)

print(a == b)
print(a == c)
print(a is b)

    Output:

    True
False
False

    Look at the third line – a is b is False. == compares "are the field values equal?", while is compares "is it the very same object?". These are two completely different things – don't mix them up.

    If you don't want the automatic __eq__, pass eq=False:

    from dataclasses import dataclass


@dataclass(eq=False)
class Employee:
    name: str


a = Employee('Two Drops')
b = Employee('Two Drops')
print(a == b)

    Output:

    False

    Now == goes back to "comparing object identity", the same as is. I don't usually recommend turning it off – without it, the dataclass is hardly different from a normal class.

    Default values – a lazy starting value for a field¶

    Just like function parameters, dataclass fields can have default values:

    from dataclasses import dataclass


@dataclass
class Employee:
    name: str
    dept: str = 'Coding Dept'
    salary: int = 8000


e1 = Employee('Two Drops')
e2 = Employee('Xiao Ming', 'R&D', 15000)
print(e1)
print(e2)

    Output:

    Employee(name='Two Drops', dept='Coding Dept', salary=8000)
Employee(name='Xiao Ming', dept='R&D', salary=15000)

    Did you notice? It works just like function parameters – fields with default values must come after fields without them. Python will flat-out reject this:

    from dataclasses import dataclass


@dataclass
class BadOrder:
    qty: int = 1
    name: str   # Wrong! A field without a default can't come after one with a default

    Error:

    TypeError: non-default argument 'name' follows default argument

    What if the default value is a mutable object – like an empty list?

    from dataclasses import dataclass


@dataclass
class Team:
    name: str
    members: list = []   # Error straight away

    Error:

    ValueError: mutable default <class 'list'> for field members is not allowed: use default_factory

    This time Python acts like a responsible parent and stops you at the door. Why doesn't it allow this? Because if it did, every Team instance would share the same members list. Append to one, and every instance's members would change. This is a very old Python trap – so old that when dataclass was designed, this road was simply blocked.

    So how do you write it? Use field(default_factory=...).

    field() – advanced settings for fields¶

    field() is another star of the dataclasses module. It's for configuring fields in more detail. The most common use is the "mutable default" mentioned above:

    from dataclasses import dataclass, field


@dataclass
class Team:
    name: str
    members: list = field(default_factory=list)


t1 = Team('Team A')
t2 = Team('Team B')
t1.members.append('Two Drops')
print(t1)
print(t2)

    Output:

    Team(name='Team A', members=['Two Drops'])
Team(name='Team B', members=[])

    default_factory=list means: "every time an instance is created, call list() to get a brand-new empty list as the default". This way, each instance has its own list, and they don't interfere with each other.

    default_factory can take any callable with no arguments. For example:

    from dataclasses import dataclass, field


@dataclass
class Counter:
    name: str
    counts: dict = field(default_factory=dict)
    tags: set = field(default_factory=set)
    history: list = field(default_factory=lambda: ['First record'])


c = Counter('Click counter')
print(c)

    Output:

    Counter(name='Click counter', counts={}, tags=set(), history=['First record'])

    Look at the last one, history – default_factory=lambda: ['First record']. Returning a list with a starting value each time is also a common use.

    field() has a few other common arguments. Let's cover them all at once:

    from dataclasses import dataclass, field


@dataclass
class Product:
    name: str
    price: float
    discount: float = field(default=0.0)             # Same as = 0.0, but more explicit
    tags: list = field(default_factory=list)         # Mutable default
    internal_id: str = field(repr=False, default='') # Not shown in repr
    cache: dict = field(default_factory=dict, compare=False)  # Not used in == comparisons


p1 = Product('Phone', 2999.0, internal_id='SECRET-1', cache={'foo': 'bar'})
p2 = Product('Phone', 2999.0, internal_id='SECRET-2', cache={'baz': 'qux'})
print(p1)
print(p1 == p2)

    Output:

    Product(name='Phone', price=2999.0, discount=0.0, tags=[], cache={'foo': 'bar'})
False

    Let's look at the two most useful ones:

    • repr=False: this field won't appear in the repr. Good for sensitive information (passwords, tokens), or internal state you don't want cluttering your logs
    • compare=False: this field isn't used by __eq__. Good for helper fields that don't affect the object's business identity, like caches or temporary counters

    Why is p1 == p2 False? Because repr=False only hides the field when printing – it doesn't affect equality. The two internal_ids are different, so the objects aren't equal. Only compare=False stops a field being compared – that's why the different caches don't matter. To get True, you'd also need to give internal_id compare=False.

    Immutable dataclasses – frozen=True¶

    By default, dataclass instances are mutable – you can reassign their fields any time:

    from dataclasses import dataclass


@dataclass
class Point:
    x: int
    y: int


p = Point(1, 2)
p.x = 100
print(p)

    Output:

    Point(x=100, y=2)

    But sometimes you want an object to never change after it's created – things that should be read-only by nature, like "a coordinate", "an enum value" or "a config setting". That's when you use frozen=True:

    from dataclasses import dataclass


@dataclass(frozen=True)
class Point:
    x: int
    y: int


p = Point(1, 2)
print(p)

try:
    p.x = 100
except Exception as e:
    print(type(e).__name__, ':', e)

    Output:

    Point(x=1, y=2)
FrozenInstanceError : cannot assign to field 'x'

    Assigning raises a FrozenInstanceError. This protection happens at runtime – so even if a static checker doesn't stop you, it will blow up when it runs.

    frozen=True has another important side effect: Python also creates __hash__ for you, so the object can go into a set and be used as a dict key.

    from dataclasses import dataclass


@dataclass(frozen=True)
class Point:
    x: int
    y: int


p1 = Point(1, 2)
p2 = Point(1, 2)
p3 = Point(3, 4)

s = {p1, p2, p3}
print(len(s))

mapping = {Point(0, 0): 'origin', Point(1, 0): 'one step right'}
print(mapping[Point(0, 0)])

    Output:

    2
origin

    See? p1 and p2 have the same field values, so the set treats them as the same element – len(s) is 2, not 3. Point(0, 0) can also be used as a dict key, and a newly created Point with the same fields finds it exactly. That's "frozen + the hash that dataclass creates" working together.

    Can you hash it without frozen? By default: you can use eq=True, frozen=False but you'd have to explicitly add unsafe_hash=True – and I strongly advise against it. Once a mutable object is hashed into a set, if you change its fields, it gets "lost" in the set – the hash is still the old one, but the fields have changed, so you can never find it again. Don't step in that trap. If you need hashing, use frozen.

    from dataclasses import dataclass


@dataclass(frozen=True)
class CacheKey:
    user_id: int
    api_path: str


# A simple pretend cache
cache = {}
key = CacheKey(1001, '/api/profile')
cache[key] = {'name': 'Two Drops', 'avatar': 'xxx.png'}

# Later, any key with the same fields will hit the cache
print(cache[CacheKey(1001, '/api/profile')])

    Output:

    {'name': 'Two Drops', 'avatar': 'xxx.png'}

    This is a very typical use of frozen dataclasses – a compound key.

    __post_init__ – work something out after construction¶

    Have you needed something like this? I have an Order class with fields unit_price and qty. As soon as the object is built, I want it to automatically work out a total field (total = unit price × quantity). total shouldn't be passed in by the user – it's derived from the other fields.

    dataclass gives us a hook for this: __post_init__. It's called automatically right after __init__ finishes – perfect for derived calculations.

    from dataclasses import dataclass, field


@dataclass
class Order:
    unit_price: float
    qty: int
    total: float = field(init=False)   # init=False means it's not in the __init__ parameter list

    def __post_init__(self):
        self.total = self.unit_price * self.qty


o = Order(unit_price=12.5, qty=8)
print(o)

    Output:

    Order(unit_price=12.5, qty=8, total=100.0)

    There are two details here to focus on:

    1. total: float = field(init=False) – init=False keeps total out of the __init__ parameters. When building an Order, the user doesn't need to, and shouldn't, pass total
    2. __post_init__ is called automatically by dataclass. Its name must be exactly this – even the number of underscores must be right

    What if I want to validate fields during construction? That's also a job for __post_init__:

    from dataclasses import dataclass


@dataclass
class Employee:
    name: str
    salary: int

    def __post_init__(self):
        if self.salary < 0:
            raise ValueError(f'Salary cannot be negative, got: {self.salary}')
        if not self.name:
            raise ValueError('Name cannot be empty')


try:
    bad = Employee('Two Drops', -100)
except ValueError as e:
    print('Blew up:', e)

ok = Employee('Two Drops', 12000)
print(ok)

    Output:

    Blew up: Salary cannot be negative, got: -100
Employee(name='Two Drops', salary=12000)

    But note: writing validation in __post_init__ is only a stop-gap. Its real job is more about "derived calculations", and lots of validation logic in it starts to look awkward. When we get to Pydantic later, you'll see a tool that's truly built for validation.

    kw_only=True – force keyword arguments (Python 3.10+)¶

    First, look at this code:

    from dataclasses import dataclass


@dataclass
class Employee:
    name: str
    dept: str
    salary: int


e = Employee('Two Drops', 'Coding Dept', 12000)

    This way of calling is called passing by position. The three values go in, in field order, and they match up perfectly.

    But once there are lots of fields, problems start:

    e = Employee('Two Drops', 'Coding Dept', 12000)
# A month later, a field is added and the order changes:
# Employee(name, salary, dept, hire_date)
# The old code Employee('Two Drops', 'Coding Dept', 12000) still runs, but the meaning is completely wrong

    When the field order changes, all old code that passes by position silently passes the wrong values. Bugs like this – "the call looks right but everything's shifted" – are extremely hard to track down.

    kw_only=True (Python 3.10+) cures this. Add it, and every field must be passed by keyword:

    from dataclasses import dataclass


@dataclass(kw_only=True)
class Employee:
    name: str
    dept: str
    salary: int


# You must write name= dept= salary=
e = Employee(name='Two Drops', dept='Coding Dept', salary=12000)
print(e)

# Try to be lazy and pass by position? Error straight away
try:
    bad = Employee('Two Drops', 'Coding Dept', 12000)
except TypeError as err:
    print(err)

    Output:

    Employee(name='Two Drops', dept='Coding Dept', salary=12000)
Employee.__init__() takes 1 positional argument but 4 were given

    The calling code instantly becomes much easier to read – when you see name='Brother Shui', you know exactly which field each value belongs to.

    You can also put kw_only on a single field:

    from dataclasses import dataclass, field


@dataclass
class Order:
    unit_price: float
    qty: int
    coupon: str = field(default='', kw_only=True)


o = Order(12.5, 3, coupon='VIP10')
print(o)

    Output:

    Order(unit_price=12.5, qty=3, coupon='VIP10')

    unit_price and qty can still be passed by position, but coupon must be a keyword. This field-level kw_only is really handy for "optional extras that are easy to mix up when there are many fields".

    Note: the syntax above only exists in Python 3.10+. Before that, a dataclass could only allow positional arguments for the whole class or not at all. On Python 3.9, don't bother with this.

    slots=True – make dataclasses use less memory (Python 3.10+)¶

    Have you ever wondered how a normal Python object stores its attributes? Answer: in a dictionary called __dict__. Every object has its own __dict__, holding a mapping of field names to values.

    Dictionaries are flexible, but they have two costs:

    • Memory – an empty dictionary alone takes up several hundred bytes
    • Speed – looking things up in a dictionary is a tiny bit slower than direct indexing

    If your program creates millions of dataclass instances (for data processing, game development, financial calculations and so on), these two costs grow into real problems.

    slots=True (3.10+) is the cure:

    from dataclasses import dataclass


@dataclass(slots=True)
class Point:
    x: float
    y: float


p = Point(1.0, 2.0)
print(p)

# Try to assign a field that doesn't exist – it blows up
try:
    p.z = 3.0
except AttributeError as e:
    print('Blew up:', e)

    Output:

    Point(x=1.0, y=2.0)
Blew up: 'Point' object has no attribute 'z'

    slots=True does two things:

    1. It uses __slots__ = ('x', 'y') to tell Python that instances of this class may only have the attributes x and y – no __dict__
    2. Instances no longer store data in a dictionary, so memory use drops a lot, and attribute access gets slightly faster

    What's the cost? Flexibility. You can't add attributes to instances "on the fly" any more. But honestly, dataclasses are meant for "fixed fields" anyway, so this cost is totally acceptable.

    Remember this: dataclass + frozen=True + slots=True is the golden trio for value types.

    from dataclasses import dataclass


@dataclass(frozen=True, slots=True)
class Coord:
    x: float
    y: float
    z: float


c = Coord(1.0, 2.0, 3.0)
print(c)
print(hash(c))

    Output:

    Coord(x=1.0, y=2.0, z=3.0)
1234567890   # The real value will be different

    Unchangeable, hashable, memory-saving and fast to access. This is the standard way to write value objects in modern Python.

    Dataclasses and inheritance¶

    Dataclasses can be inherited too. But there's a long-standing problem to watch out for: a field without a default can't come after a field with a default – and this rule is especially easy to trip over with inheritance.

    First, an example that works:

    from dataclasses import dataclass


@dataclass
class Animal:
    name: str
    legs: int = 4


@dataclass
class Dog(Animal):
    breed: str = 'mixed breed'


d = Dog('Goldie', 4, 'Shiba Inu')
print(d)

    Output:

    Dog(name='Goldie', legs=4, breed='Shiba Inu')

    The child class automatically "joins on" the parent's fields. Dog.__init__'s parameters are name, legs, breed – parent fields first, child fields after.

    So when does it blow up? Look at this:

    from dataclasses import dataclass


@dataclass
class Animal:
    name: str
    legs: int = 4   # Has a default


@dataclass
class Dog(Animal):
    breed: str       # No default

    Error:

    TypeError: non-default argument 'breed' follows default argument

    Think about why. The parent's legs already has a default, and the child's breed has none. Joined together, you get name, legs=4, breed – which breaks the rule that "a field without a default can't come after a field with a default".

    Think of it in the order shown: for normal positional arguments, a field with no default can't come after a field with a default, so putting breed after legs=4 gives an error. Keyword-only fields follow different rules – and the kw_only=True fix below uses exactly that difference.

    How do you fix it? Choose one of three ways:

    1. Give the child's field a default too: breed: str = ''
    2. Remove the default from the parent's field (but you usually can't do this – it breaks existing calls)
    3. Use kw_only=True – the most elegant:
    from dataclasses import dataclass


@dataclass(kw_only=True)
class Animal:
    name: str
    legs: int = 4


@dataclass(kw_only=True)
class Dog(Animal):
    breed: str


d = Dog(name='Goldie', breed='Shiba Inu')
print(d)

    Output:

    Dog(name='Goldie', legs=4, breed='Shiba Inu')

    kw_only=True makes every field keyword-only, so the "positional order" limit disappears – and with it, the annoying "defaults can't come first" problem.

    From now on, when you meet dataclass inheritance, your first thought should be kw_only.

    More than dataclass – NamedTuple and TypedDict¶

    dataclass is the most common "lightweight data class" tool in Python, but it's not the only one. There are two common siblings: NamedTuple and TypedDict. They do similar jobs but have different purposes. Let's look at them briefly so you know they exist.

    NamedTuple – a tuple with names¶

    from typing import NamedTuple


class Point(NamedTuple):
    x: float
    y: float


p = Point(1.0, 2.0)
print(p)
print(p.x, p.y)
print(p[0], p[1])      # You can still index it like a tuple
print(tuple(p))

    Output:

    Point(x=1.0, y=2.0)
1.0 2.0
1.0 2.0
(1.0, 2.0)

    A NamedTuple is really "a tuple with field names". It's naturally immutable (tuples are immutable), has __hash__ built in, can be unpacked and indexed. But it isn't as flexible as a dataclass – it doesn't support things like default_factory or __post_init__.

    When to use NamedTuple: when what you want is "an immutable tuple with names", and it'll often be unpacked or indexed. For example: coordinates, RGB colour values, a row of database results.

    When to use dataclass: when you want a class – it might have methods, derived calculations, or need to be changeable.

    TypedDict – a dictionary with type hints¶

    from typing import TypedDict


class UserProfile(TypedDict):
    name: str
    age: int
    email: str


u: UserProfile = {'name': 'Two Drops', 'age': 28, 'email': 'liangdianshui@xxx.com'}
print(u)
print(u['name'])

    Output:

    {'name': 'Two Drops', 'age': 28, 'email': 'liangdianshui@xxx.com'}
Two Drops

    Note: the object made by TypedDict is a dictionary, not a class instance. u is still a dict. You access it with u['key'], not u.key. Its job is to "tell mypy, at the static type level, which keys this dictionary must have and what type each value is". At runtime it doesn't check anything.

    When to use TypedDict: when you're working with JSON or outside interfaces, already have a dictionary, and just want mypy to check that the keys and types match – without turning the dictionary into a class object.

    The limit of dataclass – it doesn't validate at runtime¶

    By now, you probably think dataclass is great. It is. But it has one very important weakness: it doesn't validate anything at runtime.

    Look at this code:

    from dataclasses import dataclass


@dataclass
class Employee:
    name: str
    age: int
    salary: float


# I'm passing the wrong types on purpose
e = Employee(name=123, age='twenty-eight', salary='eight thousand')
print(e)
print(type(e.name), type(e.age), type(e.salary))

    Output:

    Employee(name=123, age='twenty-eight', salary='eight thousand')
<class 'int'> <class 'str'> <class 'str'>

    See? I passed the number 123 for name, the string 'twenty-eight' for age and the string 'eight thousand' for salary – and the dataclass quietly accepted all of them. It doesn't look at your type hints at all. Hints like name: str and age: int are only for static checkers (mypy, pyright). At runtime, dataclass doesn't enforce them at all.

    For "internal code", this isn't a big deal, because you usually control the types yourself. But in situations like these, it's a big problem:

    • An HTTP endpoint receives JSON from a client
    • A YAML/TOML config file is parsed into a dictionary
    • A message from a message queue is turned back into data

    All this data comes from outside, and you can't be sure its field types are right. Accepting it with a dataclass is like pouring dirty water straight into your bowl. When you later try e.salary * 12 to work out a yearly salary, and find salary is the string 'eight thousand', tracking down which step caused it is so costly you'll want to smash your keyboard.

    So is there a tool that declares fields as elegantly as dataclass, AND checks types/rules at runtime?

    Yes. It's Pydantic.

    Enter Pydantic – data models with runtime validation¶

    Pydantic is the most popular data validation library in the Python world. It's at the heart of FastAPI, LangChain's interfaces, and the config classes of all sorts of SDKs. Its core idea is simple: when data crosses into your program, strictly check it against the declared schema, converting it when needed. After that, the code inside your program can use it with confidence.

    First, note one thing: Pydantic is a third-party library, not part of the standard library, so you need to install it:

    pip install pydantic

    All the Pydantic code blocks below are marked with a skip-ci comment (so the example-checking script skips them). Install it yourself before running them. The current main version is Pydantic v2, and this article uses v2.

    Your first BaseModel¶

    from pydantic import BaseModel


class Employee(BaseModel):
    name: str
    age: int
    salary: float


e = Employee(name='Two Drops', age=28, salary=12000.0)
print(e)

    Output:

    name='Two Drops' age=28 salary=12000.0

    Looks almost the same as dataclass, right? That's right – inherit from BaseModel, write fields with type hints, and Pydantic does everything else. It automatically creates __init__, __repr__ and __eq__, and it also does something dataclass doesn't – type validation and conversion.

    Look at this:

    from pydantic import BaseModel


class Employee(BaseModel):
    name: str
    age: int
    salary: float


# Note: I passed age as the string '28', and salary as the string '12000.5'
e = Employee(name='Two Drops', age='28', salary='12000.5')
print(e)
print(type(e.age), type(e.salary))

    Output:

    name='Two Drops' age=28 salary=12000.5
<class 'int'> <class 'float'>

    See? I passed age='28' as a string, but Pydantic turned it into an int. salary='12000.5' became a float too. This is Pydantic's smart conversion – if a type can sensibly be converted, it converts it for you.

    What if what you pass really can't be converted?

    from pydantic import BaseModel, ValidationError


class Employee(BaseModel):
    name: str
    age: int
    salary: float


try:
    e = Employee(name='Two Drops', age='abc', salary='not a number')
except ValidationError as err:
    print(err)

    Output (roughly):

    2 validation errors for Employee
age
  Input should be a valid integer, unable to parse string as an integer [type=int_parsing, input_value='abc', input_type=str]
salary
  Input should be a valid number, unable to parse string as a number [type=float_parsing, input_value='not a number', input_type=str]

    Beautiful, right? It doesn't just raise a ValidationError – it tells you which fields, why they're wrong and what it received. Dataclass can't do any of this.

    Building a model from a dict/JSON – model_validate and model_validate_json¶

    This is Pydantic's killer feature. Imagine you've written an HTTP endpoint. The front end POSTs some JSON, and you need to:

    1. Parse the JSON into a dictionary
    2. Check the field types / required fields inside it
    3. Turn it into your internal data type

    With dataclass, you'd have to write lots of validation code yourself. Pydantic does it in one line:

    from pydantic import BaseModel


class Employee(BaseModel):
    name: str
    age: int
    salary: float


# Parse from a JSON string
json_str = '{"name": "Two Drops", "age": 28, "salary": 12000}'
e = Employee.model_validate_json(json_str)
print(e)

# Parse from a dictionary
data = {'name': 'Xiao Ming', 'age': 30, 'salary': 15000}
e2 = Employee.model_validate(data)
print(e2)

    Output:

    name='Two Drops' age=28 salary=12000.0
name='Xiao Ming' age=30 salary=15000.0

    model_validate(d) builds a model from a dictionary, and model_validate_json(s) builds one from a JSON string. Both go through the full validation process. Missing fields, wrong types or broken rules all raise a ValidationError.

    The other way round, turning a model back into a dictionary/JSON is easy too:

    from pydantic import BaseModel


class Employee(BaseModel):
    name: str
    age: int
    salary: float


e = Employee(name='Two Drops', age=28, salary=12000.0)
print(e.model_dump())          # To a dictionary
print(e.model_dump_json())     # To a JSON string

    Output:

    {'name': 'Two Drops', 'age': 28, 'salary': 12000.0}
{"name":"Two Drops","age":28,"salary":12000.0}

    This "dictionary ↔ model ↔ JSON" triangle is the best part of Pydantic. Handling outside data becomes almost effortless.

    Field rules – the power of Field(...)¶

    Type checking is just the start. The really powerful part is rule (constraint) checking. For example, you'll often need:

    • A number within a range: 0 <= age <= 120, salary >= 0
    • A string with a length limit: 1 <= len(name) <= 50
    • A string that matches a regular expression
    • A valid email, URL or UUID

    Pydantic uses Field(...) to express these rules:

    from pydantic import BaseModel, Field, ValidationError


class Employee(BaseModel):
    name: str = Field(min_length=1, max_length=50)
    age: int = Field(ge=18, le=65)              # ge = greater than or equal, le = less than or equal
    salary: float = Field(gt=0)                  # gt = greater than
    rating: int = Field(ge=0, le=100, default=60)


# A normal one
e = Employee(name='Two Drops', age=28, salary=12000.0)
print(e)

# Age out of range
try:
    bad = Employee(name='Xiao Ming', age=10, salary=5000.0)
except ValidationError as err:
    print(err)

    Output (roughly):

    name='Two Drops' age=28 salary=12000.0 rating=60
1 validation error for Employee
age
  Input should be greater than or equal to 18 [type=greater_than_equal, input_value=10, input_type=int]

    Field(...) supports quite a lot of rules. The ones you'll use most are:

    • Numbers: gt, ge, lt, le, multiple_of
    • Strings: min_length, max_length, pattern (regex)
    • Lists: min_length, max_length
    • Defaults: default=..., default_factory=...
    • Aliases: alias='another_name' (for when the key in outside JSON is different from your internal field name)

    alias is used a lot. Here's an example:

    from pydantic import BaseModel, Field


class Employee(BaseModel):
    name: str
    employee_id: int = Field(alias='empId')   # Outside JSON uses empId; inside we use employee_id


e = Employee.model_validate({'name': 'Two Drops', 'empId': 1001})
print(e)
print(e.employee_id)

    Output:

    name='Two Drops' employee_id=1001
1001

    The outside JSON uses camelCase empId, and the inside Python uses snake_case employee_id. Each side stays natural, and alias connects them.

    Complex types like email and URL – pydantic.types¶

    Rules on numbers and strings aren't always enough. Pydantic also has some built-in meaningful types:

    from pydantic import BaseModel, EmailStr, HttpUrl, ValidationError


class User(BaseModel):
    name: str
    email: EmailStr
    homepage: HttpUrl


u = User(name='Two Drops', email='liangdianshui@example.com', homepage='https://example.com')
print(u)

try:
    bad = User(name='X', email='not-an-email', homepage='not-a-url')
except ValidationError as err:
    print(err)

    Output (roughly):

    name='Two Drops' email='liangdianshui@example.com' homepage=Url('https://example.com/')
2 validation errors for User
email
  value is not a valid email address: ...
homepage
  Input should be a valid URL, ...

    EmailStr needs an extra install of email-validator: pip install pydantic[email]. HttpUrl is built in and works straight away.

    Dataclass can't give you meaningful types like these directly – you'd have to use str and write your own regex checks. Pydantic packs these common cases into the library, which saves a lot of effort.

    A quick look at the Pydantic ecosystem¶

    Pydantic isn't just a validation library. A whole ecosystem has grown around "data modelling":

    • pydantic-settings: made for config classes. It loads settings from environment variables, .env files and command-line arguments, and validates them automatically. FastAPI apps usually use it for things like DATABASE_URL and SECRET_KEY. Install: pip install pydantic-settings
    • mypy + the Pydantic plugin: lets mypy correctly work out the field types of Pydantic models – brilliant together with IDE hints
    • FastAPI: Pydantic is at its heart. Request bodies are declared with BaseModel, validated automatically, and used to generate OpenAPI docs automatically
    • LangChain, the Anthropic SDK, the OpenAI SDK: they're full of Pydantic models inside – it has become the de facto standard for data modelling in Python

    You don't need to learn all of these at once. Just know they exist, and follow the trail when you meet a real need.

    dataclass vs Pydantic vs attrs – how to choose¶

    This is the part you care about most: "With all these tools, which one should I use?" Here it is in three lines:

    • dataclass: comes with the standard library, no dependencies, lightweight. Use it for data structures inside your program that you write and use yourself. Fast, but no runtime validation
    • Pydantic: third-party, needs installing. Use it at the data boundary – outside JSON, HTTP request bodies, config files and so on. Type checking, rules and smart conversion
    • attrs: the spiritual ancestor of dataclass. A third-party library that came before dataclass and has more features (like validators and converters). Since dataclass arrived, there are fewer reasons to use attrs, but it's still a good choice when you "need complex validation but don't want Pydantic's runtime cost"

    A more detailed guide:

    Situation Recommendation
    A "structured result" returned from a function dataclass
    Lots of small objects in memory (coordinates, cache keys) dataclass + frozen + slots
    Receiving HTTP request bodies / parsing outside JSON Pydantic
    App configuration (reading environment variables) pydantic-settings
    Writing FastAPI endpoints Pydantic (FastAPI requires it)
    You want complex validators but not Pydantic attrs

    Remember: dataclass handles the "inside", Pydantic handles the "outside". Draw this line clearly, and choosing tools won't get confusing.

    Mini project – Order + OrderRequest, a pretend ordering endpoint¶

    Enough theory. Let's write code close to a real situation: a pretend "place an order" endpoint.

    Here's the task:

    • The client sends JSON with a product ID, quantity, delivery address and user email
    • The server checks: quantity must be over 0, the email must be valid, and the address can't be empty
    • Once it passes, turn it into an internal Order object, automatically work out the total price, and create an order number

    We'll let Pydantic receive and validate the outside JSON, and let dataclass represent the internal business object. Each does its own job.

    1. First, define the internal Order (dataclass)¶

    import uuid
from dataclasses import dataclass, field


@dataclass(frozen=True)
class Order:
    order_id: str
    product_id: int
    qty: int
    unit_price: float
    address: str
    user_email: str
    total: float = field(init=False)

    def __post_init__(self):
        # A frozen class can't do self.total = ... directly, so we use object.__setattr__ to get around it
        object.__setattr__(self, 'total', self.qty * self.unit_price)


o = Order(
    order_id=str(uuid.uuid4()),
    product_id=1001,
    qty=3,
    unit_price=12.5,
    address='1 Example Road, Xihu District, Hangzhou',
    user_email='liangdianshui@example.com',
)
print(o)

    Output (order_id is different every time):

    Order(order_id='xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx', product_id=1001, qty=3, unit_price=12.5, address='1 Example Road, Xihu District, Hangzhou', user_email='liangdianshui@example.com', total=37.5)

    Look at the line in __post_init__: object.__setattr__(self, 'total', ...). This is the standard way to write a derived field in a frozen dataclass. Once it's frozen, self.xx = yy is refused – but the derived field must be written once after construction, so we have to get around the __setattr__ block.

    2. Then define the outside OrderRequest (Pydantic)¶

    from pydantic import BaseModel, Field, EmailStr


class OrderRequest(BaseModel):
    product_id: int = Field(gt=0)
    qty: int = Field(gt=0, le=100)
    unit_price: float = Field(gt=0)
    address: str = Field(min_length=1, max_length=200)
    user_email: EmailStr


# Pretend JSON sent from the front end
payload = '''
{
    "product_id": 1001,
    "qty": 3,
    "unit_price": 12.5,
    "address": "1 Example Road, Xihu District, Hangzhou",
    "user_email": "liangdianshui@example.com"
}
'''

req = OrderRequest.model_validate_json(payload)
print(req)

    Output:

    product_id=1001 qty=3 unit_price=12.5 address='1 Example Road, Xihu District, Hangzhou' user_email='liangdianshui@example.com'

    If the front end sends a bad payload (for example, a negative quantity), Pydantic tells you straight away what's wrong:

    from pydantic import BaseModel, Field, EmailStr, ValidationError


class OrderRequest(BaseModel):
    product_id: int = Field(gt=0)
    qty: int = Field(gt=0, le=100)
    unit_price: float = Field(gt=0)
    address: str = Field(min_length=1, max_length=200)
    user_email: EmailStr


bad_payload = '''
{
    "product_id": 1001,
    "qty": -1,
    "unit_price": 12.5,
    "address": "",
    "user_email": "not-an-email"
}
'''

try:
    OrderRequest.model_validate_json(bad_payload)
except ValidationError as err:
    print(err)

    Output (roughly):

    3 validation errors for OrderRequest
qty
  Input should be greater than 0 ...
address
  String should have at least 1 character ...
user_email
  value is not a valid email address: ...

    Three fields report errors at the same time, and each error's location and reason is listed clearly. This is what Pydantic looks like as it stops dirty data at the boundary.

    3. Turn the outside request into an internal Order¶

    import uuid
from dataclasses import dataclass, field
from pydantic import BaseModel, Field, EmailStr


@dataclass(frozen=True)
class Order:
    order_id: str
    product_id: int
    qty: int
    unit_price: float
    address: str
    user_email: str
    total: float = field(init=False)

    def __post_init__(self):
        object.__setattr__(self, 'total', self.qty * self.unit_price)


class OrderRequest(BaseModel):
    product_id: int = Field(gt=0)
    qty: int = Field(gt=0, le=100)
    unit_price: float = Field(gt=0)
    address: str = Field(min_length=1, max_length=200)
    user_email: EmailStr


def create_order(payload_json: str) -> Order:
    """Boundary layer: validate the JSON with Pydantic first; if it passes, turn it into an Order business object"""
    req = OrderRequest.model_validate_json(payload_json)
    return Order(
        order_id=str(uuid.uuid4()),
        product_id=req.product_id,
        qty=req.qty,
        unit_price=req.unit_price,
        address=req.address,
        user_email=req.user_email,
    )


payload = '''
{
    "product_id": 1001,
    "qty": 3,
    "unit_price": 12.5,
    "address": "1 Example Road, Xihu District, Hangzhou",
    "user_email": "liangdianshui@example.com"
}
'''

order = create_order(payload)
print(order)
print(f'Order total: {order.total}')

    Look at this structure:

    • OrderRequest (Pydantic) guards the boundary. All dirty data coming in from outside must get past it first
    • Order (dataclass, frozen) lives inside. Once built, it can't change, so business code can safely pass it around, put it in a set, or use it as a dict key

    This is exactly how "dataclass handles the inside, Pydantic handles the outside" looks in practice. In real projects – FastAPI endpoints, message queue consumers or command-line tools – you can use this pattern: validate at the boundary with Pydantic, represent things inside with dataclass.

    A quick reminder – common dataclass and Pydantic traps¶

    We've covered theory and practice. Finally, here are a few traps that are really easy to fall into:

    Trap 1: dataclass fields must have type hints¶

    Remember? name: str is recognised as a field; name = '' is not.

    from dataclasses import dataclass


@dataclass
class Bad:
    a = 1     # No hint, so not a field
    b: int = 2


print(Bad())
# You'll see a isn't in the repr, because dataclass doesn't recognise it at all

    Output:

    Bad(b=2)

    Trap 2: mutable defaults must use default_factory¶

    You can't write tags: list = []. You must write tags: list = field(default_factory=list). Python flat-out rejects the first one.

    Trap 3: once frozen, you can't write derived fields normally – use object.__setattr__¶

    As in the Order example above.

    Trap 4: Pydantic v1 and v2 use different API names¶

    Lots of old tutorials use v1. Common equivalents:

    v1 v2
    obj.dict() obj.model_dump()
    obj.json() obj.model_dump_json()
    Model.parse_obj(d) Model.model_validate(d)
    Model.parse_raw(s) Model.model_validate_json(s)
    validator decorator field_validator decorator

    If you see short API names like .dict() and .json(), it's probably old v1 code. Today you should use v2's model_* family.

    Trap 5: dataclass type hints are just "documentation"¶

    Never use dataclass as if it were Pydantic. As we said, dataclass doesn't validate at runtime. Its type hints are only for mypy/IDEs. If you need validation, either write it yourself in __post_init__, or switch to Pydantic.

    Summary¶

    Let's look back at what we covered in this article:

    • dataclass is Python's standard answer for writing "data classes" – one line of @dataclass automatically creates __init__ / __repr__ / __eq__. Goodbye, boilerplate
    • field() is the Swiss Army knife for fields – default_factory solves mutable defaults, init=False plus __post_init__ creates derived fields, and repr=False / compare=False control printing and comparison
    • frozen=True makes a dataclass immutable – as a bonus, it creates __hash__ automatically, so it can go in a set or be a dict key. Essential for "value types"
    • __post_init__ is the construction hook – used for derived calculations and validation (though validation there is only a stop-gap)
    • Python 3.10+ added kw_only=True and slots=True – the first forces keyword arguments, which is especially friendly for inheritance; the second uses __slots__ instead of __dict__, saving memory and improving speed
    • NamedTuple is "a tuple with names", TypedDict is "a dictionary with types" – two lightweight options besides dataclass, each with its own sweet spot
    • dataclass doesn't validate at runtime – that's its biggest limit. Dirty outside data gets accepted as-is
    • Pydantic fills that gap – inherit from BaseModel, and you get type checks, rule checks, smart conversion and JSON conversion
    • Pydantic uses Field(...) for rules – arguments like gt, ge, lt, le, min_length, max_length and pattern describe field rules clearly
    • Meaningful types like EmailStr and HttpUrl handle common checks in one line
    • "dataclass handles the inside, Pydantic handles the outside" – the most important sentence for choosing your architecture in future
    • The mini project showed a real pattern – validate at the boundary with OrderRequest, represent the business object inside with Order. Each one shines in its own place

    This article is quite dense. You don't need to digest it all at once. Start using the dataclass part now. For the Pydantic part, come back to it when you really meet a situation where "outside data comes in and needs checking".

    In the next article, we'll talk about another topic that's very common and easy to get wrong – context managers (the with statement). Starting from the most common form, with open(...) as f, we'll go through the __enter__ / __exit__ protocol, contextlib and async context managers. See you next time.

    Are the default lists in two records the same list?¶

    Let's use a dataclass to save a study record, and add a list of review notes. Each record should have its own list:

    from dataclasses import dataclass, field


@dataclass
class StudyRecord:
    subject: str
    minutes: int
    notes: list[str] = field(default_factory=list)


first = StudyRecord('Python', 15)
second = StudyRecord('Reading', 10)
first.notes.append('Reviewed')
print(first.notes)
print(second.notes)

    Output:

    ['Reviewed']
[]

    default_factory=list means "when a default is needed, call list to make a new list". Add a note to the second record yourself, and check that it doesn't change the first one. You can compare this with the shared default argument problem from the functions chapter – but the rules for building defaults are different in the two places, so you can't just copy the syntax from one to the other.

    Another thing to be clear about: having field hints and an automatically created __init__ does not mean every input automatically goes through business validation. A normal dataclass won't reject a string just because you wrote minutes: int. When you need validation, write it explicitly. If you use Pydantic, understand its actual behaviour according to its version, model settings and conversion rules.

    This example only needs the standard library, so you can run it now. Do the third-party library examples after you've set up the right environment on your computer. First be clear about which boilerplate you want to get rid of and which inputs still need checking, then choose your data model.
